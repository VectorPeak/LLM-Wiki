## 0x01. 我读了60篇Agent Memory论文，这8篇真的推荐你看
> 发布日期：2026-05-05  
> 原文链接：[我读了60篇Agent Memory论文，这8篇真的推荐你看](https://mp.weixin.qq.com/s/TXsY89xIJX-VDsC5WGpH2Q)

我最近在整理Agent方向的论文，从HuggingFace Daily Papers里筛了最近4个月的175篇出来。

 其中"记忆"这个子方向，一个分类就有60篇。

 阿东自己在做Agent相关的产品，记忆模块是我踩坑最多的地方。上下文爆炸、跨会话丢状态、旧信息覆盖新信息——这些问题我都遇到过。挑了8篇我觉得真正值得花时间看的。

 不是综述，是推荐。每篇我会说清楚 它解决什么问题、方法上有什么亮点、以及我自己的判断，可以深挖的idea。
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibI6neOhXQyAkDyW01a6aJurqUFrrfgHenGIaYgngG2u0iaibeHEHzGtj5PfKwWf4T4D32UDXgPe89D9sUhh5m2rNSR4Rwoic6KEc/640?from=appmsg)
### 先说一个我越来越确定的判断
 读完这60篇论文，我最大的感受不是"哪个模型又变强了"，而是：

 Agent记忆系统的进步，主要不靠模型能力提升，靠的是系统设计。

 这个判断来自一篇综述——《Externalization in LLM Agents》(arXiv: 2604.08224，51 stars)。
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNicW17uLeicz8dhDAyuqq2XlM4faypBDztlGSINGzocEeMQ7eFibFMkOtMSWHnzonQfM6OKH2KKP1tytwdzCJPRmC2wWCMzFkQzKo/640?from=appmsg)
 它把memory、skills、protocols、harness engineering统一放在一个框架下讨论，核心观点是： **很多Agent变强，靠的是把认知负担从模型内部搬到了外部基础设施上。** 模型没换，周围的系统变了，效果就上去了。

 我自己做Agent产品的时候也有类似的体感。我们最大的一次效果提升，不是升级了模型，而是把记忆从"全塞进prompt"改成了分层存储+按需检索。模型还是那个模型，但任务成功率直接涨了一截。

 这篇综述值得通读，它帮你建立一个看Agent系统的全局视角：不要只盯着模型参数，要看模型之外的东西。

### 第一类：简单的记忆设计，可能比复杂的更好用
#### Memanto：类型化语义记忆干掉了知识图谱
 论文：arXiv: 2604.22085
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNicEI1k0ib3qnuicEmsLVHwCcz0m7gIbpZQrcwiavBGudEyNSpkmBXMxXnACRnzDvPnX7vuP2ib42n4eE2D76VqJOG2n5fc8McX4ibOM/640?from=appmsg)
 我之前也试过用知识图谱做Agent记忆。实体抽取、关系维护、多跳查询——整套搞下来，维护成本很高，而且LLM做实体抽取本身就不稳定，经常出错。

 Memanto的做法我觉得挺聪明的： **它不用知识图谱，而是预定义了13种记忆类型，加上自动冲突解决和时间版本控制。** 检索用的是一个不需要索引的信息论搜索引擎，写入零延迟，检索延迟低于90ms。

 结果呢？在LongMemEval上89.8%，在LoCoMo上87.1%，超过了它评估的所有混合图谱和向量检索系统。而且只需要单次检索查询。

 **我的判断是：对于大部分Agent应用场景，类型化的结构化记忆 + 高效检索，比动态知识图谱更实用。** 知识图谱的理论上限可能更高，但工程复杂度和出错概率也更高。先把简单方案做到位，再考虑要不要上图谱。

### 第二类：Agent需要学会"忘记"，这比"记住"更难
 我自己做记忆模块的体感是，"存"从来不是最难的，"什么时候该忘、怎么忘"才是。

#### RoMem：用相位旋转让过期记忆自动失效
 论文：arXiv: 2604.11544
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNicibLJ82SB84icIXDqc36mjBjPmLKYRFfUL7toH6aptcr4ynPOp6HsQkFj44q0H5AW6WkTCJTXllEwpedziahDaNBUMST0yLZIGLg/640?from=appmsg)
 这篇论文的思路我很喜欢。传统做法是给记忆打时间戳，然后用规则判断过不过期。RoMem换了个角度： **它根据关系本身的语义来预测变化速度。** "出生地"这种关系几乎不变，旋转速度就慢；"担任职位"这种关系经常变，旋转速度就快。

 过期的事实不需要删除，它会在向量空间里自然"旋出相位"，检索时排名自动下降。

 在ICEWS05-15上MRR达到72.6，在LoCoMo上优于混合基准，还能zero-shot泛化到金融领域。

 **我觉得这个方向很有潜力。** 现在大部分Agent记忆系统处理时间的方式都太粗暴了——要么全保留，要么按时间窗口硬删。RoMem提供了一个更优雅的中间方案：让记忆自然衰减，而不是二元的"记住/删除"。

#### LightThinker++：把记忆管理变成可学习的行为
 论文：arXiv: 2604.03679
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNibb8mCicmqibE1OxyoAjNLTWxZhz6Rj2Nko4tG4JT9fwa6eCVqQOKFibTxJp9QlO8S2LYe1DMO3CBrfFkKkFRkbtNzDTCHO6ycF8k/640?from=appmsg)
 这篇解决的是另一个很头疼的问题： **长程推理时上下文爆炸。** LLM在复杂推理中会生成很长的中间过程，token开销和推理时间快速上升。LightThinker++的做法是引入显式的记忆操作原语——write、summarize、retrieve、discard——然后训练模型学会什么时候该用哪个操作。

 结果：峰值token使用减少70%，推理时间减少26%，准确率损失很小。在超过80轮的长程Agent任务中，内存占用减少60%-70%，平均性能还提升了14.8%。

 这篇论文让我意识到一件事：记忆管理不应该是工程师在系统层面硬编码的规则，而应该是模型自己学会的行为。

 我们现在做Agent的时候，上下文管理基本都是手写规则——用固定的摘要策略。但不同任务、不同阶段需要保留的信息完全不一样。让模型自己学会"什么值得记、什么可以扔"，这个方向我觉得是对的。

### 第三类：记忆存了不等于能用，要能自我修复
 大部分Agent系统的记忆是"写入后就不管了"。写进去的时候可能就有问题，后面也没有机制去检查和修复。这两篇论文在解决这个问题。

#### MemMA：记忆也需要自我修复的闭环
 论文：arXiv: 2603.18718
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibwQ3Ix3GXDmWZvRduKmOCibydQZtxz0jsX2WvTlZY0mvwqvricibsWkVn25cxGmmlNkdhhibicBuEkIOsPETBLrBQSiacgdETYF4aoM/640?from=appmsg)
 MemMA把记忆系统拆成了三个协作的Agent：Meta-Thinker负责规划记忆策略，Memory Manager负责构建记忆，Query Reasoner负责检索。

 但真正让我觉得有意思的是它的"后向路径"： **系统会自动生成探测性问答对，去验证当前记忆能不能正确回答关键问题。如果回答失败，就触发修复动作。** 你想想，这其实就是给记忆系统加了单元测试。写入一条记忆之后，自动生成几个问题测一下，能答对才算写入成功。答不对就补写、重组或者修正索引。

 **我觉得这个思路应该成为Agent记忆系统的标配。** 我们写代码都知道要写测试，但做记忆系统的时候，大部分人写进去就完了，从来不验证。

#### Omni-SimpleMem：自动化研究发现，记忆系统最大的问题是bug
 论文：arXiv: 2604.01007
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibfMDACIMW4BRaHTITOuSgtmxepALGu1KjGIyyppicTf6chqB4bgAWyWphBnmZM8Eufnt7lpqAMfzgZZXxUsNCr3oib8aFFbtoI4/640?from=appmsg)
 这篇论文的方法论让我印象很深。作者没有手动调记忆系统，而是搞了一个自动化研究流水线，从一个朴素的baseline开始，自动跑了大约50个实验。流水线自己诊断失败模式、提出架构修改、修复数据管线bug。

 最终结果：LoCoMo的F1从0.117提升到0.598，提升411%。

 **但最让我震惊的是提升的来源分布：bug修复贡献了+175%，架构变化贡献了+44%，prompt engineering贡献了+188%。** 也就是说，最大的两块提升来自修bug和改prompt，不是什么高深的算法创新。

 我自己做Agent系统的时候也是这样。很多时候效果不好，不是方法不对，是数据管线有bug、prompt写得不够精确、或者某个边界条件没处理好。 **先把工程做扎实，比追新算法重要得多。** ### 第四类：记忆的终局在哪

 最后两篇，一篇是工程突破，一篇是方向性思考。

#### MSA：把Agent记忆扩展到1亿token
 论文：arXiv: 2603.23516
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNibStFep4EcNOabYthlS6uAvBy6xQ0h6iaw1bPHrrLHdQDLabNVeZseMJKicGCHZgrT4WbuhLFflUv8fXGmQ1Iv74pHbTNL9egvmw/640?from=appmsg)
 Memory Sparse Attention，结合稀疏注意力、文档级位置编码、KV cache压缩和记忆并行，实现了训练和推理的线性复杂度。

 **从16K扩展到100M token，性能退化低于9%。** 在2块A800 GPU上就能跑1亿token的推理。在长上下文benchmark上超过了前沿LLM、SOTA RAG系统和领先的记忆Agent。

 1亿token是什么概念？大概是几个月的完整交互历史，或者一整个代码仓库加上所有文档。

 我觉得这篇论文代表了一个方向： **把长期记忆从外部检索系统拉回到端到端可训练的注意力架构里。** RAG的检索质量始终是个瓶颈，如果模型本身就能"看到"足够长的历史，很多检索问题就不存在了。

 当然，1亿token的推理成本还是很高。短期内RAG和端到端长记忆可能会共存——高频短期记忆放模型内部，低频海量知识放外部检索。

#### Continuity Layer：从"记忆"到"连续性"
 论文：arXiv: 2604.17273
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNib3Vp8CuO4ForDCyTsT2ibxoSicibYr8pryQbUNMgav19iavme3BuaN4rvKWJiaOsPEVhJ6ggaPx7nibzHhic8UFNILYZvD5NRuLcZC1Q/640?from=appmsg)
 这篇star不多，但提出的问题我觉得很关键。

 作者区分了三个概念：memory、retrieval、continuity。他认为现在的Agent记忆系统只做到了前两个——能存、能搜——但没有做到真正的"连续性"。

 什么是连续性？ **你关掉一个会话，下次打开的时候，AI不只是"记得你说过什么"，而是能延续之前形成的理解。** 不是重新读一遍历史记录再理解一次，而是直接从上次的认知状态继续。

 这个区分很重要。现在大部分Agent的"记忆"，其实只是"能检索到历史文本"。模型每次读取这些文本，都要重新理解一遍。真正的连续性，应该是理解本身被保存和恢复。

 这篇更像是一个架构层面的思考，没有给出完整的实验验证。但它提出的问题指向了Agent记忆的下一个阶段：不只是"记住"，而是"延续"。

### 我的判断
 读完这60篇论文，我对Agent Memory这个方向有几个判断。

 知识图谱在大部分场景下是过度设计，Memanto这类简单方案会被更多人采用。记忆管理会从手写规则变成可学习的行为。LightThinker++这个方向会有更多后续工作。模型会学会自己决定记什么、忘什么。

 更远的事我不太确定，但有一个趋势我比较看好：记忆和推理的边界会越来越模糊。MSA这类工作在探索的方向——把记忆容量做到足够大，让模型直接"看到"而不是"检索到"——可能会改变我们设计Agent系统的方式。

 还有一个贯穿始终的观察： **这个领域最大的提升空间，往往不在算法创新，而在工程质量。** 修bug、改prompt、优化数据管线，这些不性感的工作，贡献的效果可能比一篇新论文还大。

 如果你也在做Agent相关的工作，这8篇论文真的建议花时间看看。不一定每篇都要精读，但至少了解一下它们在解决什么问题、用了什么思路。

 这是系列的第一篇，后面还有自进化篇、规划篇、世界模型篇。如果你感兴趣，可以关注后续更新。

 阿东，大模型算法工程师，OPC创业者。

## 0x02. 我从8篇Agent规划论文里，看到了规划的三个层次
> 发布日期：2026-05-08  
> 原文链接：[我从8篇Agent规划论文里，看到了规划的三个层次](https://mp.weixin.qq.com/s/RTx-uJP8zm1EBq7XkwNWBg)

![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8ibJKzxGdrdHg3wDke6YibXrUBWWXzvlXYqZzvianAL7zGqOib2AibpIDhBRSLWxdBM8AUQWt4ubvkILPRlQGA4lP5FvPDUImyJl8c/640?from=appmsg)
 上一篇聊自进化，核心判断是：Agent变强靠的不是"变聪明"，而是把做过的事变成可复用的能力。

 写完之后我在想一个问题： **技能有了，怎么决定什么时候用哪个？** 这就是规划。

 Memory解决"记住什么"，自进化解决"学会什么"，规划解决"怎么排兵布阵"。一个Agent能记住100个技能，不代表它知道面对一个复杂任务时该先用哪个、后用哪个、什么时候该放弃当前路线换一条。

 我从论文库里挑了8篇，按三个层次展开：怎么往前看、约束下怎么规划、怎么从执行中学。

 先说我的核心判断： 规划能力的瓶颈不在"想不出计划"，而在"计划和现实对不上时怎么办"。

### 怎么往前看：从反应式到前瞻式
 大部分Agent现在还是反应式的。看到当前状态，推理下一步。这就像开车只看引擎盖前面一米，遇到路口才想往哪拐。

#### ProAct：教Agent学会"往前看几步"
 论文：arXiv: 2602.05327(27 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8EWpBXkZuV1pHkUgVemI2u8fYUFKMBNtby0nF9j9cYX9JIBbMF1ddagguWnMG1dlNqhH5HicoBDkQoheJql8CqG5W5G7n1AJeE/640?from=appmsg)
 ProAct把搜索树的知识蒸馏成推理链。

 做法是这样的：先用树搜索(MCTS那种)在训练时探索最优路径，然后把搜索过程转化成LLM能理解的推理轨迹(他们叫GLAD)，再用强化学习训练模型学会这种前瞻式思考。

 **结果有点意外：一个4B模型，超过了所有开源baseline，接近闭源SOTA。** 一个小模型学会了"想远一步"，就能打很多大模型。

 这说明一个问题：模型大小不是规划能力的决定因素。 **关键是有没有被教过"怎么想远一步"。** 大部分模型训练数据里缺的不是知识，是"多想一步"的思维模式。

#### TodoEvolve：让模型自己设计规划系统
 论文：arXiv: 2602.07839(6 stars)
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPN8m8JWWfdmStYsic8ZJ2kdaiayk2yEibaeSSyjsXeOSibtb2Qc7MrgmQBE6VhHvRhJAmnOnIexjDSmmDTb9RY3ckxtvBohwJUJgEKk/640?from=appmsg)
 ProAct是教模型怎么规划。TodoEvolve更激进： **让模型自己学会设计规划架构。** 你不用手动设计"先分解任务→再分配工具→再执行→再检查"这套流程。TodoEvolve根据任务特点，自动生成适合的规划模块组合。

 结果：在5个Agent benchmark上持续超过手工设计的规划模块，API成本还更低。

 **这是元规划。规划怎么规划。** 听起来绕，但逻辑清晰：既然我们不知道什么规划架构最好，让模型自己去搜索。跟AutoML一个思路。

 坦率讲，这篇star很少，实际落地我也没见到案例。但方向我觉得有意思： 未来可能不是"人设计规划系统，Agent来执行"，而是"Agent自己设计规划系统，人来监督"。

#### ACG Survey：Agent工作流的统一框架
 论文：arXiv: 2603.22386(57 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibeE3eydKlahH4V5iaW4iayExftibOk4Ilv63aDMCDMmsiagiaTOLaaGelTMGbxjgnoiaOX7WVE1G7wV9gY8DfeFHibM4oRCibj0qrB2wA/640?from=appmsg)
 这篇是综述，但我觉得有必要提。它给Agent工作流提了一个统一分类：Agentic Computation Graphs(ACG)。

 三类：静态模板(写死的流程图)、运行时动态生成(边跑边决定下一步)、执行轨迹(事后复盘用的记录)。

 **这个分类我觉得特别实用。** 做Agent系统的时候，经常纠结"到底是预定义workflow还是让Agent自由发挥"。ACG的框架帮你想清楚：不是二选一，同一个系统里可以混用不同层次的控制。

 简单任务用静态模板，复杂任务用运行时动态生成，出了问题用执行轨迹回溯。

### 约束下怎么规划：现实世界不是无限资源
 实验室里的Agent可以不计成本地调API、不考虑时间限制。现实世界不行。

#### TAPE：LLM规划+传统求解器，成功率涨了21个百分点
 论文：arXiv: 2602.19633(8 stars)

 WECHATIMGPH_5

 这篇的洞察很直接： **LLM单独做规划，经常违反硬约束。加个传统求解器进来，问题就解决了大半。** 做法是：LLM负责理解任务和生成候选方案，外部求解器检查约束是否满足，约束解码器确保执行过程不越界。

 结果：Sokoban、ALFWorld、GSM8K-Hard这些任务上，硬约束场景成功率涨了21个百分点。弱模型上更明显，+20个百分点。

 **我们是不是太迷信"让LLM自己搞定一切"了？** 很多规划问题，传统算法已经有成熟解法。LLM的优势是理解模糊需求和灵活推理，不是精确计算。两者结合，比让LLM硬算靠谱得多。

#### DeepPlanning：当前Agent在全局约束规划上严重不足
 论文：arXiv: 2601.18137(35 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN9sloo1YKlnrz2OEQVP8SAGG9ywvZcDjV2jGicOOH4W2oqOGVrT7ribIiamu2b0S1YJ7Yfdqrric59aOJMS0R2fuM6lv3mEJuHYPq0/640?from=appmsg)
 这篇来自Qwen团队，做了一个专门测全局约束规划的benchmark。

 什么叫全局约束？比如"5天旅行，总预算8000，每天至少一个景点，不能连续两天坐飞机"。每一步决策都受全局条件限制，不是看当前一步就能定的。

 **结果很不好看：即使最强的frontier模型，在这类任务上表现也很差。** 但有两个发现有用：显式推理模式(让模型一步步说出约束检查过程)和并行工具调用能显著提高性能。

 这跟TAPE的结论互相印证： **LLM不擅长在脑子里同时追踪多个约束。** 得把约束外化，要么交给求解器，要么让模型显式地一条条检查。

#### INTENT：API调用也有成本，规划得考虑预算
 论文：arXiv: 2602.11541(2 stars)
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPN9XvBFhSoZgrSVk0l8sCf8uNAhlZZvN4qDXsHeIv0kkfSkmiajkUAfpJTFlLe6Zx6U1oiaFr4eVqVmPUHW2HufTNMyp5AMrqkvj4/640?from=appmsg)
 这篇star很少，但解决的问题非常实际。

 做Agent系统的人都知道，每次调API都有成本。一个规划如果调了20次工具，每次都是GPT-4级别的推理，费用很可观。 **INTENT让Agent在规划时就考虑预算约束。** 它用了一个"意图感知的层次化世界模型"来预测未来工具调用的成本，在不超预算的前提下找最优执行路径。

 结果：严格满足预算硬约束的同时，任务成功率显著提高。

 **这个方向被严重低估了。** 实际部署Agent系统，成本控制绕不过去。一个Agent不考虑成本地调API，即使任务完成了，ROI也可能是负的。

### 怎么从执行中学：规划不是一次性的
 前面两个层次是"怎么制定计划"。这个层次不一样，是"计划执行完之后怎么变得更好"。

#### HCAPO：执行完一个计划，哪些步骤真的起了作用？
 论文：arXiv: 2603.08754(5 stars)
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNic9w1Wg1fpJ5ZMmXLeHSiaHtTU6T7IYciaFm1YiaP7pxzONfTvKUUQJsJy6xIk1EGvyuGUVIhYAOYBrgyDEPnEPHX4K30tEZkFqKA/640?from=appmsg)
 一个10步的计划执行完了，有些步骤是关键的，有些多余，有些甚至有害。 **HCAPO用事后推理来判断每一步的真实贡献。** 就像项目复盘。不是看"做了什么"，是看"哪些做法真的影响了结果"。

 结果：WebShop上成功率+7.7%，ALFWorld上+13.8%(基于Qwen2.5-7B-Instruct vs GRPO)。

 这个方向我觉得特别重要。 **大部分Agent系统现在是"执行完就完了"，不回头看哪些步骤有效。** 同样的错误反复出现，同样的低效路径反复走。

#### daVinci-Agency：239条真实PR链，47%性能提升
 论文：arXiv: 2602.02619(53 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNicrulohYFZhEWG4rIjZG6P3yH6cxb75B9qhFnQcT29rGOY8gX5xH2bf7sjGj0XgMrVLlka4q28tvc5OuZiaflusboeE809Z6vTI/640?from=appmsg)
 这篇解决一个很实际的问题： **训练Agent做长程规划，数据从哪来？** daVinci-Agency的答案很聪明： **从真实的软件开发PR链里提取。** 一个PR从开始到合并，经历代码阅读→修改→测试→review→修复→再测试，本身就是一条自然的长程规划轨迹。

 只用了239条这样的轨迹(平均每条85k token、116次工具调用)，fine-tune GLM-4.6之后，Toolathlon上47%的相对提升。

 ==239条数据，47%提升。好的规划训练数据不需要多，需要真。==

 我自己做系统也有类似感受。花时间搞几百条高质量的真实案例，比搞几万条合成数据有用得多。

### 我的判断
 写完这8篇，几个想法。

 **"往前看"的能力可以被蒸馏。** ProAct证明小模型也能学会前瞻规划。规划能力不是大模型的专利，是一种可以被教会的思维模式。做Agent系统的人，不一定需要最贵的模型。

 **LLM不应该独自承担规划的全部。** TAPE和DeepPlanning都在说同一件事：LLM擅长理解需求和灵活推理，传统算法擅长约束求解和精确计算，结合起来才行。纯LLM规划在简单任务上够用，复杂任务不够。

 **成本约束是必选项，不是可选项。** INTENT解决的问题不性感，但每个做Agent产品的人都会遇到。

 **从执行中学习才是闭环。** HCAPO和daVinci-Agency从不同角度说明：规划系统不能只往前看，还得回头看。知道哪些步骤有效、从真实轨迹中学习，规划才会越来越好。

 把三篇文章放在一起看：

 **Memory是基础设施，自进化是能力积累，规划是调度中枢。** 三者缺一不可。有记忆没规划，Agent记住了很多但不知道什么时候该用。有规划没记忆，每次从零开始排计划。有规划有记忆但不会自进化，能力永远停在原地。

 下一篇是世界模型篇，聊Agent怎么理解环境、预测后果。感兴趣的话可以关注后续更新。

 阿东，大模型算法工程师，OPC创业者。

## 0x03. 我从7篇自进化论文里，看到了Agent的下一步
> 发布日期：2026-05-06  
> 原文链接：[我从7篇自进化论文里，看到了Agent的下一步](https://mp.weixin.qq.com/s/R8H3QZ2C-sJ1KHjEmfkyDg)

上一篇我聊了Agent Memory方向的8篇论文 [ 我读了60篇Agent Memory论文，这8篇真的推荐你看 ](https://mp.weixin.qq.com/s?__biz=MzI0OTcyMzcxNg==&mid=2247488211&idx=1&sn=d6428edb26f61160ec64475e25c56010&scene=21#wechat_redirect) ，核心判断是：Agent变强靠的是系统设计，不是模型升级。

 写完那篇之后我一直在想一个问题： **记忆存下来了，然后呢？** 存了不等于会用，会用不等于能进化。一个Agent能记住你说过什么，跟它能从过去的经验里学到新技能，这是两件完全不同的事。

 这篇聊自进化。我从论文库里挑了7篇，按三个方向展开：从轨迹中蒸馏技能、AI加速AI的闭环、学会压缩自己。

 先说我的核心判断： 自进化的关键不是"让Agent变聪明"，而是让Agent把做过的事变成可复用的能力。

### 从轨迹中蒸馏技能：做过的事不能白做
 这是我最关注的方向。Agent每天执行大量任务，产生大量轨迹数据。这些轨迹里藏着"怎么做"的知识，但如果不提炼出来，下次遇到类似任务还是从头推理。
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNibXEwZXf7nTicr1TuvopHHGaP2uHEwicDX1roEmPBQJcMPNHyO823oe7ibCJKhGasNyvqIbFebHPtPsu69KT2EDONo62BRGVu6y80/640?from=appmsg)
#### Trace2Skill：小模型蒸馏的技能，反过来让大模型变强
 论文：arXiv: 2603.25158(52 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8kf6SSK8a8Aibw3s1bnva2Xzjo6Gab2ynFMaMf6RO4G2mSz5dYSnOMwgV4nDEfMicOjMls1BZZmEibvibUkCkOfx8J6lX8MO7vLAo/640?from=appmsg)
 这篇的思路让我有点意外。

 常规想法是大模型教小模型。Trace2Skill反过来： **先让多个Agent跑同一类任务，收集成功轨迹，然后从这些轨迹里归纳出通用技能。** 有意思的是结果。蒸馏出来的技能不只是让小模型能用，反过来给大模型用也有效。Qwen3.5-35B基于自身轨迹演化出的技能，让Qwen3.5-122B在WikiTableQuestions上提升了57.65个百分点。

 我觉得这说明一个问题：大模型不是"什么都会"，它只是"什么都能推理"。 **把高频操作固化成技能，比每次都让模型从头推理高效得多。** 你不会每次开车都重新思考怎么踩刹车，Agent也不应该每次都重新推理怎么操作Excel。

#### Memento-Skills：Agent设计Agent
 论文：arXiv: 2603.18743(58 stars)
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPN9I8XuIGnsOyXswMAVT8nJKg8icAibRvicHUQxSbLZMXZz6UEI1ZTCJydYhWxpz70aIBAv5ic616hEhiaZqqXOODWq8rFHvCicicSAn4k/640?from=appmsg)
 Trace2Skill是从轨迹里提炼技能。这篇更进一步， **让Agent自己设计新的Agent**。

 做法是：观察任务执行过程，识别出可复用的子流程，然后把这些子流程封装成独立的"技能Agent"。技能存储格式是markdown。对，纯文本，不是代码，不是模型权重。

 结果：overall accuracy提升116.2%。

 **markdown作为技能存储格式这个选择我觉得很聪明。** 可读、可编辑、可版本控制、任何LLM都能直接理解。不需要专门的技能执行引擎。

 我们自己做Agent的时候，很多"技能"其实就是一段精心写好的prompt加上几个工具调用的组合。把这些东西结构化存下来，本身就是一种进化。只是大部分团队没有把这件事系统化地做。

#### MemSkill：记忆操作本身变成可学习技能
 论文：arXiv: 2602.02474(63 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibdeJReLCpPlWd7WXJIc9TKUGcrX4TKHlyBqMp8KNpIHIkcXYRdVvexlKhw7XRutxcXR0nEs4cmw1trRM96t2ALwGGRicOJU988/640?from=appmsg)
 前面两篇是从任务轨迹里提炼技能。MemSkill换了个角度： **它把"怎么管理记忆"这件事本身也变成了可学习的技能。** 什么时候该存、存什么格式、怎么索引、什么时候该清理。这些记忆操作不再是硬编码的规则，而是Agent从经验中学到的行为模式。

 这就形成了一个自我强化的循环。Agent执行任务，产生经验，从经验中学会更好的记忆管理方式，下次任务表现更好，又产生更高质量的经验。

 我上一篇提到LightThinker++让模型学会记忆操作，MemSkill是同一个方向的延伸，但更彻底。 **不只是学会"记什么忘什么"，而是学会"怎么组织整个记忆系统"。** 坦率讲，这个方向目前还比较早期，实际部署的时候稳定性是个问题。但方向我觉得是对的。

#### SSL表示：技能从文本变结构
 论文：arXiv: 2604.24026(5 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibZTXYXQa2eG0YszbcKW23G6fVqoICYqUNnpbTChdTvqkp8lqTaP1GPc8YzzicvbISUqVQ5nPFkAoHKM93uBMCjqicAbz5HrS9fI/640?from=appmsg)
 这篇star很少，但解决的问题很实际。

 前面几篇论文的技能都是文本形式的。文本好理解，但有个问题： **当技能库变大之后，检索匹配的准确率会下降。** "用浏览器搜索信息"和"用搜索引擎查找资料"描述的是同一个技能，但文本相似度不高。

 SSL(Scheduling-Structural-Logical)把技能拆成三层结构化表示：什么时候调用、执行流程是什么、具体动作和资源是什么。这样语义相近但表述不同的技能就能被正确匹配。

 MRR从0.573提升到0.707。

 **这个提升看起来不大，但在实际系统里影响很大。** 技能检索的准确率直接决定了Agent能不能在正确的时机调用正确的技能。检索错了，后面的执行全白费。

 我觉得随着技能库规模增长，这类工作会越来越重要。现在大家的技能库还小，文本匹配够用。等到了几百上千个的时候，没有好的结构化表示，系统会退化得很快。

### AI加速AI的闭环：用Agent优化Agent
 第一类是Agent从自己的经验里学技能。这一类更激进： **用AI系统来设计和优化AI系统本身。** #### ASI-Evolve：learn-design-experiment-analyze

 论文：arXiv: 2603.29640(28 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8h5vZY1OSEQKUaUCkzuvVXNuLhDk1Vwsv8ZdAkoTvwF3uewzb9jcbHvC3WFQhV6e75Kk2UYzeIRagIJDKrY1DnOXg724P1308/640?from=appmsg)
 这篇做的事情是用Agent来做AI研究。

 四步闭环：学习现有文献，设计新架构或方法，跑实验验证，分析结果并迭代。整个流程自动化，Agent自己决定下一步探索什么方向。
![image](https://mmbiz.qpic.cn/mmbiz_jpg/cQwYPia4EPN8SN6MUOsTTSY9eVwf40OplMGEUvSzvXJJ2vjA2Wc78cQEw2GicLr0icarX13a8teN3rfqPBUMoFLeuR2EJFnGJiaRBApYX1mRR88/640?from=appmsg)
 结果：在架构搜索任务上超过DeltaNet +0.97，在数据筛选任务上MMLU提升+18。

 **我对这类工作的态度是：短期内它更像是一个高效的超参搜索工具，长期看它可能真的能做出人想不到的设计。** 现阶段的局限很明显。它能在已有的设计空间里搜索最优组合，但很难跳出这个空间提出全新的范式。不过话说回来，人类研究者大部分时间做的也是在已有空间里搜索组合，真正的范式突破本来就是极少数。

#### PACEvolve：解决进化搜索的三大失效模式
 论文：arXiv: 2601.10657(20 stars)
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibGHTO6nWGfBe97dfRSS1qKiauP8cATNff3FBW1RZ6H8HMJ4kVA8NkIOTcTMpdopAs5UnGLlWhEqqMxy8dsrfz18ibmzib6IPia2JA/640?from=appmsg)
 ASI-Evolve是让Agent做研究，PACEvolve解决的是进化搜索本身的问题。

 进化搜索(用LLM生成代码变体，然后选择表现好的继续进化)是个很火的方向，但实际跑起来经常失效。PACEvolve识别了三个主要原因：

 搜索空间坍缩，所有变体越来越像，多样性消失。评估噪声，小数据集上的评估结果不稳定，选错了方向。进化停滞，找到一个局部最优就出不来了。

 它针对这三个问题分别设计了对策，最终在Modded NanoGPT上超越了之前的记录。

 ==我觉得这篇论文的价值不在于具体的结果，而在于它系统性地分析了"为什么进化搜索会失败"。== 做过类似工作的人应该都有体感。LLM进化搜索理论上很美好，实际跑起来经常不work。知道为什么不work，比知道怎么work更有用。

### 学会压缩自己：用更少的token做更多的事
#### TACO：自动学习压缩规则
 论文：arXiv: 2604.19572(21 stars)
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPN8swlS4yw9g1Ieia7HmXbKpocdrMEVialFoTF91ibMwh5tN6wNkYD9icRibPGLsIfBaplYhVctX5GHxV69YQ8yZ3DjtnoRZSFvOWlgg/640?from=appmsg)
 最后这篇解决的问题很直接： **Agent的上下文太长了，能不能自动学会压缩？** 不是人工写摘要规则，不是固定的截断策略。TACO让Agent从终端反馈(任务成功/失败)中自动学习：哪些信息可以压缩、怎么压缩、压缩到什么程度。

 结果：token使用降低10%，性能不降反升。

 10%听起来不多。但如果一个Agent每天处理几万次请求，每次省10%的token，累积下来的成本节省很可观。而且性能还提升了，说明之前那些被压缩掉的信息，不只是"不需要"，可能还是"干扰项"。

 **这让我想到一个更大的问题：我们现在给Agent塞的上下文，有多少是真正有用的？** 我自己做系统的时候，经常是"不确定要不要放，那就放进去吧"。但信息过载对模型来说也是负担。

 TACO的思路是对的：让Agent自己学会什么该留什么该扔，比人工制定规则更靠谱。不同任务、不同阶段需要的信息完全不一样，人工规则覆盖不了所有情况。

### 我的判断
 写完这7篇，我对自进化方向有几个想法。

 **技能蒸馏会成为Agent系统的标配。** 现在大部分Agent每次都从头推理，太浪费了。Trace2Skill和Memento-Skills展示的路径，从轨迹中提炼可复用技能，会被越来越多的系统采用。ROI太明显了：做过的事不用重新做。

 **AI优化AI目前更像是高效的搜索工具。** ASI-Evolve和PACEvolve的结果很好，但它们还是在人类定义的搜索空间里找最优解。高效搜索本身很有价值，但离"AI自主做出突破性发现"还有距离。这个距离有多远，我不确定。

 == **压缩和进化是同一件事的两面。** == TACO表面上在做压缩，实际上在做的是"学会区分什么重要什么不重要"。这跟技能蒸馏的逻辑一样，都是从大量经验中提炼出精华。

 如果把Memory篇和自进化篇放在一起看，我觉得有一条线越来越清晰：

 **Agent的进化路径：记住，整理，提炼，复用。**![image](https://mmbiz.qpic.cn/mmbiz_jpg/cQwYPia4EPN8ORzVrzPVbYoynGDs0Yz5vghg58XFibF9yjgjW7XjicicWIL8oYeoF3hQhx08DO8krrhxtDmh6LEeBiaxyd0ymwXm0kH6aPZCjZ1Q/640?from=appmsg)
 Memory解决前两步，自进化解决后两步。这两个方向不是独立的，是同一条路径的前后两段。

## 0x04. Agent Memory 到底怎么做？从 10 种学术方案到工业实践，完整拆解
> 发布日期：2026-05-16  
> 原文链接：[Agent Memory 到底怎么做？从 10 种学术方案到工业实践，完整拆解](https://mp.weixin.qq.com/s/xIkccIT_M89sz4y3_H8etg)

![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8Fb2JibNBhicZicMLicgFrOp93wzggFibObuPsjcj6q1r4GAJAsPP3V5J2FgIo4nf4I5rSsC0yicMzQ5ycicdcXEkkumd3ic3AZHywXqo/640?wx_fmt=png&from=appmsg)
 阿东最近在给自己的 Agent 系统加长期记忆，踩了不少坑。

 起因是我观察到一个现象：Agent 产品越来越多，但几乎所有 Agent 都还是"金鱼记忆"。Cursor、Windsurf、Claude Code 每次新开会话，之前聊过的项目背景、做过的架构决策、踩过的坑，全忘了。企业想把 Agent 用到客服、销售、研发流程里，第一个卡点就是——这东西记不住事。

 Memory 落地难，原因不是技术不行，而是没有统一框架。学术方案一堆，工业实践各搞各的，大家连"Memory 到底该记什么、怎么组织、什么时候取"都没对齐。

 于是我花了两周时间，把我认为不错的 Agent Memory 方案过了一遍。读了一篇统一框架论文(arXiv: 2604.01707)，翻了 10 种学术方案的原始论文，又把 ChatGPT、Claude、Letta、Hermes、Cursor、Windsurf 的官方文档都扒了一遍。

 这篇文章把研究过程、技术判断和选型逻辑完整分享出来。内容比较长，建议收藏。

### 0. 先说结论
 **Agent Memory 不是"把历史对话塞进向量库"。** 它是一套上下文管理机制：什么信息值得留下、怎么组织、什么时候取出来、取出来后怎么影响 Agent 的推理和行动。

 核心不是"存更多历史"，而是让 Agent 在正确时刻拿到正确的过去信息，并且不被错误、过期、冗余的记忆拖累。

 如果你现在要做 Agent Memory，我的建议是： **文件记忆 + 显式规则 + 结构化 item + 混合检索 + 定期压缩**。大多数场景做到这里够用。

 Memory 值不值得单独做成一个系统，坦率讲有争议。Memory 的形态完全取决于 Agent 怎么用。客服 Agent、Coding Agent、Research Agent、个人助理，需要记住的东西完全不一样。底层 LLM 越强，对粗糙记忆和长上下文噪声的容忍度也越高。

 但从架构选型角度看，把不同方案拉到统一框架下比较仍然有价值。只有拆成组件，才知道不同系统到底在比什么。

#### 0.1 Memory 不是 RAG
 先区分三个东西。

 **上下文** 是模型当前能看到的信息。 **RAG** 是从外部知识库里找相关材料。 **Memory** 是 Agent 从过去交互、任务和用户反馈中沉淀出来的可复用经验。

 举个例子。用户问："上次我们为什么不用 Supabase RLS 那个方案？"

 RAG 会去项目文档里搜"Supabase RLS"，可能搜到一堆技术文档。Memory 应该直接知道：之前讨论过这个方案，当时因为权限策略过复杂、测试成本高，所以暂时放弃了。

 **RAG 解决"知识在哪里"。Memory 解决"过去发生了什么、现在应该怎么接着来"。** Agent Memory 其实就是对 context 的精细管理。记忆不是孤立的东西，它要跟具体业务问题走。很多方法做着做着就扩展成 RAG 平台或 Agent 框架的一部分，已经偏离了 Memory 本身。
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNicTBPHSML83bwFAetMKWYRwQMlFZL2DG4R0RiankW0VJoD1KnaVyFPusibRWyZL0foC8KO3Hj6NNxeTgqAAp1e8coMwnAtiaRapAM/640?from=appmsg)
#### 0.2 四组件框架：所有方案都逃不开这四件事
 不管是 A-MEM、MemGPT、Mem0、Zep，还是 ChatGPT Memory、Claude Memory Tool、Hermes，拆开看都在做四件事：
 1. **信息提取**：从交互中判断什么值得记
 2. **记忆管理**：对已有记忆做合并、更新、关联、遗忘
 3. **记忆存储**：决定用什么结构保存
 4. **信息检索**：在需要时把相关记忆找回来

 写入路径和读取路径是两条不同的流。

 写入：交互日志 → 提取 → 更新/合并/遗忘 → 存储

 读取：当前任务 → 查询重写/意图检测 → 检索 → 重排/过滤 → 注入上下文 → Agent 响应

 很多系统的问题出在哪呢？只做了存储和检索，没有认真做提取和管理。结果记忆越积越多，越来越像一个塞满垃圾的向量库。我自己第一版就犯了这个错。
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8pByY7sdNxfAcialnOOPPc6kQGbTcxEXlvGHDib7AIDIXyQylTMfDY9z2UzFehx8HmISzBEfmicvnFMhDNvS16XkicC1XZLZD9rYI/640?from=appmsg)
#### 0.3 记忆应该分六类
 不要把所有历史都叫 Memory。实际工程里，至少得分清楚六种东西。

 **短期记忆** 服务当前任务。"现在正在修支付回调 bug。""刚跑测试失败，错误是 TypeError。"只在当前 session 内有效。

 **情节记忆** 记录发生过什么。"2026-05-12 讨论过迁移 Supabase，因为 RLS 复杂度暂缓。""上次部署失败是因为环境变量没同步到 preview environment。"带时间、事件和决策。

 **语义记忆** 记录稳定事实。"项目用 Next.js + Prisma + PostgreSQL。""主分支叫 main，部署走 GitHub Actions。"

 **用户画像** 记录偏好。"用户偏好中文回答。""写笔记喜欢先给判断再展开。"ChatGPT 把 Memory 分成 saved memories 和 chat history 两种，用户可在设置中管理。

 **技能记忆** 记录怎么做事。"处理 Vercel 部署问题时，先看 build logs，再看环境变量，再看 Node 版本。"

 **规则记忆** 比偏好更硬。"不要自动提交代码。""不要删除迁移文件。"AGENTS.md、CLAUDE.md、.cursor/rules 都属于这类。

 这里有个我觉得很多人忽略的区分： **Rules 是确定性的、必须遵守。Memories 是概率性的、需要判断是否适用。** Cursor 和 Windsurf 都把这两者分开了，不是没有原因的。
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNibgpUMFyX09HRfNtxkEzTJm7l8bKckbJggGuB2MaNJkkibxQ8h8LvxoctL1gWAZPEROZTcJZMra6ibeUWeYfCGhOJuYMhlyMUiba0/640?from=appmsg)
#### 0.4 信息提取：三种路线
 信息提取是 Memory 系统的入口。问题很直接：从原始对话、工具结果、用户行为里，哪些东西值得进入记忆系统？

 **直接归档** 最简单，保存原始消息加时间戳。优点是信息完整，缺点是噪声大、存储膨胀、检索成本高。MemoryBank 和 MemGPT 偏这一类。

 **摘要式提取** 用 LLM 从一轮或多轮对话中提取摘要、关键词、标签。A-MEM 会为新记忆生成包含上下文描述、关键词和标签的综合笔记，并通过动态链接构建知识网络。Mem0 也是从持续对话中动态提取显著信息。 **摘要式提取适合大多数工程场景**，在完整性和成本之间比较平衡。

 **图式提取** 用 LLM 抽取实体、关系、时间，构建知识图谱。Zep/Graphiti 就是典型代表，动态综合非结构化对话和结构化业务数据，同时保留历史关系。适合企业关系数据、CRM、多跳推理。

 但图式提取有天然问题： **三元组化会损失语义**。一句话里的语气、犹豫、上下文暗示，很难变成"主语-谓语-宾语"。图谱不是越早上越好，除非你真的需要关系推理。
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNicLUq6Kl9M2KibnUADYBjPK96SQHsMHCXCw7FFeDhI9RP4S9Sf2kbT7YMr482PF9iaA4QRG13xicz7sYmiaeEdlGC9MAvplSp6L9vc/640?from=appmsg)
#### 0.5 记忆管理：五类操作
 信息进入系统后，不应该只是被保存。管理操作可以拆成五类。

 **关联**：在相关记忆之间建立连接。"用户喜欢简洁回答""用户写技术笔记""用户讨厌营销腔"，这三条单独看是散的，一起看能更好指导写作风格。A-MEM 通过动态链接建立记忆网络，Zep 通过实体图谱建立关联。

 **整合**：把碎片化记忆合并成更稳定的摘要。多次对话里用户都说"不喜欢太油腻的表达"，系统可以整合成一条："用户偏好自然、克制、判断明确的中文表达。"这类记忆比多条散落原文更好用。

 **跨层转换**：把短期记忆迁移成长期记忆。MemoryOS 采用短/中/长三层架构，短期到中期按 FIFO 迁移，中期到长期结合访问频率和最近性评分。关键是： **不是所有东西都应该一步进入长期记忆。** **更新** 有三种范式：

| 更新方式 | 做法 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 规则驱动 | 按时间衰减、访问频率更新 | 可控、便宜 | 僵硬 |
| LLM 驱动 | 用模型判断合并、改写、冲突 | 灵活 | 成本高、不稳定 |
| Agent 驱动 | Agent 自己调用工具决定写/改/删 | 自主性强 | 最难调试 |

 MemoryBank 的艾宾浩斯遗忘曲线属于规则驱动。MemTree 用 LLM 做聚合更新。MemGPT/Letta 偏 Agent 自主工具调用。

 **过滤** 就是删除或降权无效记忆：过期信息、重复信息、低价值信息、错误信息、当前 scope 不适用的信息。如果没有过滤机制，Memory 系统会越用越脏。
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNibK9KVJZ4agbPsiaQxvVbg0jRAHmaL2fHIMV0prq74xgg9lMbI7V9q3VoeZzDuRXRicLBAI8wegWD2jWJNbk1RIOZdFEhcBjx4f0/640?from=appmsg)
#### 0.6 记忆存储：五种结构
 **扁平向量存储** 最常见。把 memory item 做 embedding，放进 FAISS / Qdrant / Milvus / pgvector，按语义相似度检索。简单成熟，但关系推理弱、时间推理弱、精确匹配弱。

 **混合存储** 在生产里更常见。数据库存正文和元数据(事实源)，向量索引做语义召回，全文索引做 BM25/FTS，图索引做实体关系。 **不要让向量库成为唯一事实源，否则更新、删除、审计会很麻烦。** **图存储** 适合实体关系和时间变化。Zep/Graphiti 就是典型，因为企业知识经常动态变化：客户状态、交易进展、组织关系、历史决策。传统 RAG 适合静态文档，企业 Agent 需要持续整合对话和业务数据。

 **树存储** 是 MemTree 的思路。叶子节点保存细节，上层节点保存抽象摘要。既保留原始信息，又能在高层做概念召回。但维护成本高，对话越长，插入时需要更新路径上的摘要。

 **分层存储** 是 MemGPT、MemoryOS、MemOS 的方向。Active Context → Short-term → Mid-term → Long-term → Archive。来自操作系统的思路：上下文窗口像内存(贵、小)，外部存储像磁盘(大、便宜)，需要调度。

 **文件存储** 是工业界最常用的。MEMORY.md、USER.md、rules 文件。简单、可读、可版本控制。
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNicn6rDpna6RicrsVPZJ8OZ1Xt6icYa5xIDw4sYFHx0ID2gtzJHVnGPXNhjYT9nprT9VBEzWDdfRGic2J08DXEH9eWByWQsLx7gcia0/640?from=appmsg)
#### 0.7 信息检索：混合检索 + 排序公式
 检索阶段四种范式：

| 检索方式 | 机制 | 适合场景 | 问题 |
| :--- | :--- | :--- | :--- |
| 词汇检索 | BM25、FTS | ID、文件名、错误码 | 语义泛化弱 |
| 向量检索 | embedding + ANN | 语义相似问题 | 精确性不稳定 |
| 结构检索 | 图遍历、多跳 | 关系推理、时间链路 | 图维护贵 |
| LLM 辅助 | query rewrite、rerank | 模糊问题、复杂意图 | token 成本高 |

 生产系统里通常是混合流程：

 当前任务 → 意图识别/Query Rewrite → BM25 召回 + 向量召回 + 图谱扩展 → 候选合并 → Rerank → 过滤过期/冲突/低置信 → 注入 Prompt

 我自己用的排序公式：
```text
final_score =
  0.35 * semantic_similarity
+ 0.20 * lexical_match
+ 0.15 * recency
+ 0.15 * importance
+ 0.10 * scope_match
+ 0.05 * confidence
```
**这个公式不是固定的。** Coding Agent 要提高 lexical_match 权重(函数名、错误码很重要)。个人助理提高 recency 权重。企业系统提高 graph relevance 和 temporal validity 权重。
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN93nWA1Eg0h593uoceTLekDKRhicLIrib532IFEnqN0CYzftiaJW2hb8AgosDibPxTLhVGY7QmISVeZviaScK9Ctx4ibyTPZaiaV0C6CE/640?from=appmsg)

#### 0.9 工业界怎么做？五个实践
 学术方案喜欢做加法。工业界反而在做减法。

#### ChatGPT：产品化个人记忆
 ChatGPT Memory 重点不是做开发者可编程的记忆数据库，而是产品级个性化。官方文档里，Memory 有两个设置：Reference saved memories(用户明确让 ChatGPT 记住的信息)和 Reference chat history(参考过去聊天改善未来回答)。

 重点是：用户可控、个性化、跨会话体验、偏好和稳定事实、可以关闭/管理/删除。

 它走的路线偏"把相关 memory 拼进 context，让模型自己消化"，不是复杂 RAG 检索。

#### Claude Memory Tool：把存储交给开发者
 Claude API 的 Memory Tool 很有工程启发。官方文档说，Claude 可以通过 /memories 目录在会话之间存储和取回信息。启用后，Claude 会在开始任务前检查记忆目录，可以创建、读取、更新、删除该目录下的文件。

 这个工具是 client-side 的：Claude 发起工具调用，应用程序在本地执行。所以 **开发者控制记忆存在哪里、怎么存**。

 很 Unix philosophy：不给黑盒 memory service，给清晰的文件工具接口。你自己决定后端是本地文件、数据库、加密存储还是企业权限系统。我觉得这个设计思路很对。

 核心价值是 just-in-time context retrieval：不预先加载所有信息，而是把学到的东西存在 memory 里，需要时再取回来。对长期运行 Agent 很重要：跨 session 项目上下文、从历史决策中学习、构建长期知识库、重复工作流的持续改进。

#### Letta(MemGPT 延续)：分层记忆 + Sleep-time Compute
 MemGPT 的核心来自操作系统：有限上下文窗口相当于 RAM，外部存储相当于 disk，Agent 需要学会把信息换入换出。

 Letta 进一步提出 memory blocks，把上下文窗口拆成有标签的区块(persona、human、task state)，可被 API 读取、更新、删除，可在多个 Agent 之间共享。

 另一个重要概念是 **Sleep-time Compute**。官方博客解释：sleep-time compute 是让 Agent 在空闲时间处理信息、形成新连接、重写 memory state，而不是只在对话时处理。

 这点工程价值很大：在线对话时 Agent 要快；记忆整理时 Agent 要认真。这两个目标冲突，Sleep-time 把它们解耦了。

 适合个人助理、长期项目 Agent、代码库反思、多 Agent 共享知识、需要持续改进的工作流。

#### Hermes：文件记忆 + 插件记忆
 Hermes 的设计很克制。内置 persistent memory 核心是 MEMORY.md 和 USER.md。如果需要更深的持久记忆，可以启用外部 memory provider 插件(Honcho、Mem0、Hindsight 等)。外部 provider 是 additive，不替代内置 memory。

 这是一个很好的二层架构：第一层内置文件记忆(简单、稳定、可读)，第二层外部 provider(语义搜索、知识图谱、自动事实提取)。

 几个现实的设计决策：

 • MEMORY.md 和 USER.md 有容量边界，满了后 Agent 会整合条目

 • session 中写入磁盘的 memory 不会立刻出现在系统提示词里，要等下次 session 启动才快照进去

 • prompt cache 很重要，不能每轮都打破缓存

 • 外部 provider 是增强，不是基础依赖

#### Cursor/Windsurf：Rules + Memories 分层
 Coding Agent 的 Memory 和通用聊天 Agent 不一样。它面对的是代码库、文件、终端、错误、项目规范。很多"记忆"其实是规则和约定。

 Cursor 把 Rules 定位为 persistent instructions，包括 Project、Team、User Rules 和 AGENTS.md。

 Windsurf 的 Cascade 则明确有 Memories 和 Rules 两套机制：Memories 用于跨对话共享和持久化上下文，可由 Cascade 自动生成；Rules 是用户手动定义的全局、工作区或系统级规则。

 **在 Coding Agent 里，rules 通常比 memories 更重要。** 项目规范、代码风格、禁止操作、测试命令，最好显式写下来，不要让 Agent 从对话中"猜"。

#### 0.10 写入协议：什么时候该记？
 我自己给 Agent 设了一个明确的 Memory Write Protocol：

 **只有在以下情况写入长期记忆：** -
 1. 用户明确要求记住
 2. 信息会在未来多次影响任务表现
 3. 信息是稳定偏好、项目事实、长期限制、重要决策或可复用流程
 4. 信息有明确来源，不是临时情绪、一次性草稿或不确定猜测

 **写入前必须判断：** -
 • 是否已经存在相似记忆？

 • 是否和旧记忆冲突？

 • 是否只属于当前项目(scope)？

 • 是否应该设置过期时间？

 • 是否需要用户确认？

 • 是否涉及敏感信息？

 **不要写入：** -
 • API key、密码、token 等敏感信息

 • 一次性任务细节

 • 未确认的猜测

 • 大段原文

 • 很快变化的信息(除非带上时间戳和有效期)

 这个协议比"自动记住一切"安全得多。

#### 0.11 检索协议：什么时候该查记忆？
 **在以下情况先检索记忆：** -
 1. 用户提到"之前""上次""我们当时""继续"
 2. 当前任务涉及长期项目、个人偏好、历史决策
 3. 需要恢复未完成任务
 4. 需要避免重复踩坑
 5. 当前问题和某个已知项目、客户、代码库相关
 6. 回答会受到用户偏好或项目规则影响

 **检索后：** -
 • 只注入最相关的 3-8 条

 • 优先使用同一 scope 的记忆

 • 新记忆优先于旧记忆

 • 高置信记忆优先于低置信记忆

 • 如果存在冲突，明确标出冲突，不要擅自合并

#### 0.12 不同场景怎么选型？
#### 个人助理
 推荐：Saved memory + User profile + 少量可检索历史 + 用户可见可删。不推荐一上来做图谱。重点是边界和控制权。

#### Coding Agent
 推荐：Rules + Memory 分层、AGENTS.md / CLAUDE.md / .cursor/rules、代码库索引、会话日志检索、技能记忆、错误和决策记录。不推荐把所有代码历史都当成 memory。 **重点是项目规则、代码事实、可复用流程。** #### Research Agent

 推荐：RAG + citation store、Research log、Hypothesis memory、Decision memory、Source credibility metadata、长期主题摘要。可以考虑图谱，但要保留原始来源。重点是证据链，不是用户画像。

#### 企业 Agent
 推荐：Temporal knowledge graph、CRM/ticket/document integration、Entity resolution、Access control、Audit log、Memory expiration。Zep/Graphiti 这类时间知识图谱适合企业动态知识，处理结构化业务数据和非结构化对话，保留历史关系。 **重点是权限、时间、实体关系和审计。** #### 长期陪伴/角色 Agent

 推荐：短/中/长期分层、情节记忆、用户偏好、主题摘要、遗忘曲线、情绪和关系事件时间线。但要非常注意心理安全和隐私边界。

#### 0.13 七个常见坑
 **坑一：把 Memory 做成无限上下文。** 更多历史不等于更好。过多无关信息会让模型被噪声干扰，推理质量反而下降。我试过把最近 50 轮对话全塞进去，效果反而变差。

 **坑二：只用向量库。** 向量检索对语义相似有效，但对精确匹配不稳定。代码里的函数名、错误码、文件路径、版本号，都需要 BM25/FTS 精确匹配。我现在是混合检索，向量负责语义，BM25 负责精确。

 **坑三：没有 scope。** 全局偏好、项目事实、临时状态混在一起，会造成记忆污染。用户在 A 项目里说"不用 Tailwind"，不代表所有项目都不用 Tailwind。记忆必须带 scope。

 **坑四：没有过期机制。** 旧记忆如果不降权，会污染新任务。应该引入 expires_at、last_accessed_at、valid_from/valid_to、status(active/superseded/archived)。

 **坑五：自动提取太激进。** LLM 很容易把一次性表达提炼成长期偏好。用户说"这次写短一点"，不代表以后永远要短。

 **坑六：图谱过早上场。** 图谱适合关系推理，但也会带来实体消歧、关系抽取、时间维护、冲突合并等一堆问题。没有明确图推理需求，就先别上。

 **坑七：不可见不可删。** 用户不知道 Agent 记了什么，就很难信任它。产品级 Memory 必须可查看、可编辑、可删除、可关闭。

#### 0.14 我的实战选型：三层架构
 研究完这些方案，我给自己的 Agent 选了三层：

 **Layer 1：显式规则(优先级最高)** 稳定、短小、明确。比如：默认用中文回答、不要营销腔、先给判断再展开原因、代码修改前先说明风险。这些是硬约束，不需要 Agent 去"回忆"，直接写在 rules 里。

 **Layer 2：稳定文件记忆** 类似 Claude Memory Tool 和 Hermes 的做法，用 markdown 文件保存稳定事实：
```text
/memories
  USER.md
  PROJECT.md
  MEMORY.md
  DECISIONS.md
  SKILLS.md
```
好处：可读、可改、可审计、可版本控制。出了问题打开文件就能看到 Agent 到底"记住"了什么。

 **Layer 3：可检索历史记忆** 把对话和决策变成结构化 item。推荐 schema：
```json
{
  "id": "mem_123",
  "type": "preference | fact | decision | task_state | skill | warning",
  "scope": "global | project | session",
  "content": "用户偏好技术笔记先给判断，再展开原因。",
  "source": {
    "conversation_id": "conv_456",
    "timestamp": "2026-05-15T15:30:00+09:00"
  },
  "importance": 0.82,
  "confidence": 0.91,
  "expires_at": null,
  "status": "active",
  "conflicts_with": []
}
```
检索时结合 BM25 + 向量相似度 + 时间新鲜度 + scope 匹配 + 重要度 + 置信度。

 **不要一上来就做 GraphRAG 或 MemoryOS。** 只有当你真的遇到跨 session 多跳推理、实体关系持续变化、企业级权限审计这些问题时，再考虑图谱和分层 OS。

#### 0.15 从 MVP 到高级版的路线图
 **阶段 1：文件记忆。** 几个 markdown 文件，USER.md 和 PROJECT.md。最简单也最值得先做。你会发现光是这一步，Agent 的跨会话体验就好很多了。

 **阶段 2：结构化记忆。** 把记忆拆成 item，带类型、scope、来源、重要度。这样能按条管理，能过期，能删除。

 **阶段 3：混合检索。** BM25 + Vector + Rerank。到这一步大多数场景已经够用了。

 **阶段 4：分层记忆。** 短期任务状态、中期项目摘要、长期稳定事实分开。

 **阶段 5：图谱/时间线。** 只有关系和时间变化很重要时再上。

 **阶段 6：Sleep-time 整理。** 参考 Letta 的思路，把记忆整理放到空闲期，不阻塞当前对话。

 我目前在阶段 3，暂时没有往图谱走的需求。大多数人做到阶段 2-3 就够用了。

#### 0.16 几条跨方案经验
 **分层/树状结构通常更强。** 扁平向量库只能找相似条目，树和分层结构可以同时保留"概念"和"细节"。对多跳推理尤其重要。

 信息完整性比结构化抽象更重要。图谱看起来更高级，但结构化提取容易丢信息。原始对话里的语气、上下文、否定、条件、时间范围，经常无法完整进入三元组。 **摘要式 + 原文可追溯，比纯图谱更稳。** 关联机制是多跳推理的命门。如果每条记忆都是孤立的，系统很难回答"这件事和上次那个决策有什么关系"。A-MEM 的动态链接、Zep 的图谱、Mem0 的相似记忆更新，都在增强关联能力。

 时间推理不能只靠存储结构。需要时间戳、有效期、版本、事件链、最近性权重、冲突处理。用户以前喜欢 A 现在不喜欢了，客户上个月是 active 现在 churn risk，这类问题不能只靠向量检索。

 还有一个容易忽略的： **索引维护成本很容易被低估。** 图越大去重越难，树越深插入越贵，记忆越多冲突越多，自动更新越多调试越难。论文里看不到这些成本，但生产里直接体现在延迟、账单和线上 bug 上。

#### 0.17 最后说一句
 Agent Memory 这东西，很容易被讲得很玄。什么"让 AI 像人一样积累经验"，什么"记忆操作系统"。

 但做工程的人知道， 先做最简单的版本，遇到真实问题再加复杂度。这个原则在 Memory 这件事上尤其适用。

 **Memory 的价值是让 Agent 少忘关键事、少重复犯错、少被错误历史误导。** 一个好的记忆系统，应该让 Agent 更稳定，而不是更神秘。

 如果你也在做 Agent Memory 相关的事情，欢迎来聊。我会持续分享实战过程中的真实经验，包括踩的坑。毕竟这东西目前还没有标准答案，大家都在摸索。
