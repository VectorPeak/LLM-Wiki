### 后续主要更新方向
### 1. Agent 应用方向
#### 1.1 Agent Loop 的理解
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN9ZjltfGcwqcc5mia9Ql7t9YRgL9PRDKLheW01SicFyDmnbhdq7nEacJ7jYhIWPgoQ4pATlfRic9Rp6SGcvaDbXCBPRl0VeOAb9fU/640?from=appmsg)
 很多人把 ReAct、Plan & Execute、Multi-Agent、CodeAct 当成并列模式，但我个人理解，它们本质上并不平行。

 真正的底层范式仍然是 ReAct Loop：模型观察上下文 → 推理 → 决定行动 → 调用工具 → 根据结果继续。Plan & Execute 是在此之上增加了规划与执行的分层；Multi-Agent 是一种协作组织方式；CodeAct 是把行动表达成代码执行，提升可控性和可复现性。

 所以面试中不能只背概念，要能讲清楚：PlanAct 为什么出现？Multi-Agent 解决的是能力拆分还是协作问题？CodeAct 相比普通 Tool Call 有什么优势和风险？

 更深的追问会涉及 LoopSession 和 LoopTurn 的设计——一个 LoopTurn 通常包含 Model Call 和 Tool Call，复杂场景下还有 Batch Tool Call、多轮上下文压缩、Interrupt、Steer 等机制。

 如果涉及 HITL，还需要理解 StopReason 设计、PreTurn / MidTurn / PostTurn 三个干预点，以及 Stop-Resume 和 Hang-Wait 两种不同的交互模式—— **这些细节暴露你是否真正写过 Agent。**
#### 1.2 上下文工程 + 成本工程
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNibfMeBywmhRRljdZWKFK8UNvaPssH580QxKeZsjGwQrOvjMRbEvrO1XuHJ63WWu4iaicf2mduibbY7SYYkH92CJa6JL1tU0qpcW54/640?from=appmsg)
 Agent 的上限很大程度取决于上下文设计。面试官经常问：上下文太长怎么办？历史轨迹怎么压缩？哪些信息应该进 prompt？如何避免模型被无关信息干扰？

 这里不是回答"做 RAG"就够了，而是要能讲出分层设计：

 • 短期上下文：当前任务、当前轮对话、工具返回结果

 • 长期上下文：用户偏好、项目记忆、历史经验

 • 工作上下文：文件、代码、终端状态、执行轨迹

 • 压缩上下文：对多轮交互进行摘要、抽取、归档

 大多数候选人说"摘要压缩"就停了。面试官接着会问： **KV Cache 友好的上下文结构你是怎么设计的？** system prompt 保持稳定、工具定义放前面、历史对话放后面——这是降低推理成本的实际手段。Prefix Caching 的使用场景、结果缓存的适用边界，也是这一层的考点。

 真正区分候选人段位的是成本视角：能不能说出具体的优化幅度？头部产品已经做到比 naive 方案低 5-10 倍，靠的是智能路由(简单任务走小模型、复杂任务走大模型)+ Prompt 瘦身 + 上下文压缩 + Prefix Caching 组合拳，而不是单点优化。面试官一问"你们 token 成本怎么控制"，能说出数字的候选人和说不出的，差距一目了然。

#### 1.3 工具设计与 Skill 范式 ⚓ 幂等性设计 + 权限管理 = 基本功
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN9a56HiamD58mNLP2dKrsxicYb3AULntynCibIgV8v947RwcRtibrD3rJbNnuJWO6L0X8qWB8tMAF1LGaK7f751Uv1SGhOBoX6k5hw/640?wx_fmt=png&from=appmsg)
 很多 Agent 系统已经不再简单依赖大量 Agent 路由，而是走向 **One ReActLoop × N Skills** 的形态。

 Skill 不只是工具函数，而是一套完成任务的方法、流程、约束和上下文组织方式。好的 Skill 能被模型正确发现和调用、支持渐进式披露、可以嵌套和组合、能被评测和自我优化。

 简单说：Tool 解决"能不能做"，Skill 解决"怎么高质量地做"。

 工具设计的压轴题通常是： **模型面对语义相近的多个工具，选错了怎么办？** 比如同时有 search_web 和 search_internal_docs，模型经常选错。解法不止一个——改 tool description、加 router 层、用 few-shot 引导——面试官想听的是你踩过这个坑，并且有自己的取舍理由。

 工具的幂等性设计和权限管理是基本功：同一个工具被重复调用时不会产生副作用，Agent 对外部系统(文件、数据库、API)的访问权限有明确边界——这些在面试中经常作为追问出现。

#### 1.4 多模型路由与 Fallback
 这一块是很多候选人的盲区，但高段位岗位几乎必问。

 核心能力是：同时对接多个模型 API(GPT-5、Claude、豆包、开源模型)，根据任务类型和成本预算做智能路由；主模型不可用时自动切换，切换过程对用户透明。

 国内常用模型的能力边界也要有基本判断——Kimi 的长上下文、豆包的价格优势、千问的代码能力、GLM 的中文理解、MiniCPM 的端侧部署——不需要背参数，但要能说出适用场景和局限性。

 面试中的追问通常是：路由策略怎么设计？怎么避免路由本身成为瓶颈？Fallback 切换后上下文如何保持一致性？

#### 1.5 记忆系统设计(Memory)
 三层架构(Working / Episodic / Semantic)是框架，真正的难题是： **谁来决定什么值得存入 Episodic Memory？** 两种答案面试官都听腻了：模型自己判断、或者规则触发。他们想追问的是：模型判断的误判率有多高？你怎么测？规则触发遗漏了哪些关键 case？能回答这些，才说明你真的做过记忆系统，不是停在设计层。

#### 1.6 Agent 评测 + 治理审计
 Agent 一定是评测驱动的。Agent 的问题往往不是单次回答错了，而是多轮过程中的路径偏移、工具选择错误、上下文污染、任务完成度不足。

 三个最容易被问到却最难答好的问题：

 **golden dataset 怎么来？** 人工标注成本极高，自动生成质量不可信，有没有半自动的构建方法？

 **LLM-as-a-Judge 的偏差怎么处理？** position bias、verbosity bias——这些偏差不处理，评估结果本身就是不可信的。

 **任务完成率高但用户满意度低，这个 gap 怎么解释？** 能区分"模型做对了"和"用户觉得有用"，才说明你的评估体系是成熟的。

 评测之外， **治理审计** 是另一个高段位考点——每个 Agent 做了什么操作、调用了什么工具、消耗了多少 token，全程可追溯。异常行为检测(Agent 是否在预期范围内操作，越界行为的自动告警)和用户反馈闭环(如何把负反馈转化为系统改进的信号)，这些才是生产级 Agent 系统和 demo 的真正分水岭。

 我的理解是：Trajectory 本身就是最重要的评测对象，也是治理的原始数据。评测和审计是同一件事的两面。

### 2. Harness & Framework 方向(壁垒更高，人才更稀缺)
 相比 Agent 应用，Harness 方向的真实面经会更少，但我个人感受是这个方向的壁垒反而更高。

 **传统八股正在弱化。** 面试官更关心的是：你是否真的做过 AI 系统？你对模型能力边界有什么判断？你是否理解从模型到产品之间的工程鸿沟？面试重点正在从"知识点记忆"转向"经验密度和思考深度"。

 **手撕代码正在淡化，但工程判断更重要。** 目前仍然比较常见手撕，但很多 AI 初创公司更倾向于让你使用 AI Coding，观察你怎么拆问题、怎么验证、怎么和模型协作。

#### 2.1 两类框架的分野
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPN8PxWcp6TceyFf9cYibxxxHoyA1lkBNGkkIiawib1nInHSxLGHJlFR6X9CAtYabQhFoASFv5SNUkyIxExS5GiaV9icdE6GicbNOl4dbw/640?wx_fmt=png&from=appmsg)
 **Outbox Agent** (主动出击型)：LangChain → AutoGPT → DeepAgent 这条线，核心是编排——任务拆解、工具调用、执行轨迹、可控性。

 **Inbox Agent** (环境内嵌型)：Claude Code、Codex、Cursor、OpenCode 这条线，核心是 Harness——模型被嵌入真实工作环境，Harness 决定它能"看到"什么、"摸到"什么。

 不只要知道这些产品名字，还要理解它们背后的设计取舍。

#### 2.2 真实产品的 Harness 设计
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN9RnkxQyQ6ZdtSvxzJibyH74CfPVlP6SECq2fPpoyOdwPVZ8y8Qsy0TeEuw3umn2icE4pBbRJCYKsvy5HRkiciaVaFiaNaJE1cnOg1c/640?from=appmsg)
 **Claude Code(AGENTS.md 机制)**：Harness 核心设计是"知识写进文件、按需注入上下文"——不靠微调写进权重，今天写进去，明天生效，零训练成本。本质是即插即用的知识扩展机制。

 考点：注入时机怎么判断？层级冲突(子目录 vs 根目录的 AGENTS.md)怎么解决？AGENTS.md 自身膨胀怎么处理？

 考点：Hook 失败本身怎么处理？同步 Hook 还是异步 Hook？Hook 链的执行顺序怎么管理？

 **Devin / OpenHands(沙箱设计)**：Harness 核心在沙箱——Docker 隔离保证安全边界，文件系统快照 + Git 版本追踪让每步操作可回滚。沙箱不是"安全加固"，是 Agent 敢于试错的前提：没有回滚能力，Agent 只能小心翼翼；有了快照，Agent 才能大胆执行、失败即恢复。这是 demo 到生产最关键的工程跨越。

 考点：快照粒度怎么设计？沙箱冷启动延迟怎么优化？资源上限触发后如何优雅降级？

 **Cursor / Windsurf(上下文工程极致化)**：代码库索引、AST 解析、增量更新，确保模型每次拿到"刚好够用"的上下文。KV Cache 友好设计在这里体现得最明显。

 考点：索引失效怎么处理？大型 monorepo 的上下文裁剪策略？

#### 2.3 产品化经验——从工程到产品的最后一公里
 这一块是 Harness 方向高段位候选人和普通候选人的最后分水岭。

 Agent Workspace 的产品形态理解——用户如何编排自己的工作流、管理 Agent 权限、查看执行轨迹——这不是 PM 的问题，而是工程师是否真正站在用户视角想过系统设计。

 AI Native 交互的前端实现也经常被问到：流式输出怎么做？思考过程可视化怎么设计？来源引用如何在 UI 层呈现？这些细节决定了 Agent 产品的体验上限。

 用户反馈闭环是最容易被忽略但最有价值的设计：如何把用户的负反馈转化为系统改进的信号？点踩之后发生了什么？这个闭环是否真正接入了评测体系？能把这条链路讲清楚的候选人，说明他不只是在做功能，而是在做产品。

#### 2.4 Harness 与模型能力强绑定
 Harness 通常离模型更近，所以不是纯工程框架问题。

 你还需要理解：KV Cache 的作用、Prefill 和 Decode 的性能瓶颈、P&D 分离对推理系统的影响、模型工具调用能力如何训练、Self-Improvement 如何形成闭环。

 如果只懂上层框架，完全不理解模型能力变化，就很难判断一个 Harness 设计到底是短期 workaround，还是长期趋势。

 ==Harness 方向考的只有一件事：你有没有在生产环境里，把一个裸模型变成一个真正能干活的 Agent？==

### 3. 准备重点
 1. 理解 Agent Loop，而不是只背 ReAct / PlanAct / Multi-Agent 名词
 2. 系统学习 Context Engineering，包括上下文选择、压缩、KV Cache 友好设计
 3. 掌握成本工程：智能路由、Prefix Caching、多模型 Fallback，能说出具体优化幅度
 4. 理解 Tool、Skill、Hook、Middleware 的边界和设计原则
 5. 掌握 Agent Eval + 治理审计，尤其是 Trajectory Eval 和用户反馈闭环
 6. 熟悉真实 AI Coding 产品和 Agent Framework 的设计取舍
 7. 补充模型推理、KV Cache、P&D 分离、Self-Improvement 等底层知识
 8. 多形成自己的判断，而不是只复述业界概念

 最后，我最大的感受是：AI Native 面试越来越不像传统面试，它更像是在判断一个人是否真正进入了这一轮技术范式变化。

 代码会越来越容易生成，但判断力、系统设计能力、评测意识、对模型演进的理解，会变得越来越稀缺。

 ==Harness 方向考的只有一件事：你有没有在生产环境里，把一个裸模型变成一个真正能干活的 Agent？==

 模型决定下限，Harness 决定上限。

## 0x02. Agent 面试，项目是 20 分，讲项目是 80 分
> 发布日期：2026-05-21  
> 原文链接：[Agent 面试，项目是 20 分，讲项目是 80 分](https://mp.weixin.qq.com/s/ksGMZ8tcjRVBlQf378fEzQ)

近一年我帮人改过上百份带"Agent 项目"的简历，模拟面试也做了不少场。一个让我自己都意外的发现：项目做得不错但讲得很差的人，几乎拿不到 offer。同样的项目讲清楚的人，反而能拿到手软。

 项目只是入场券，讲项目才是关键。这个判断到 2026 年不但没变，门槛还拉高了。

### 先说面试官真正在判断什么
 现在没有面试官在乎你是不是自己写的代码。Claude Code 帮你搭框架、Cursor 帮你补逻辑、AutoResearch 帮你跑实验——工具就是工具，用得好才是能力。

 但工具生成不了 **判断**。

 你的 Agent 在第 6 步崩了，Claude Code 给你三个修法，你选哪个？你的奖励模型在开放域一直被hacking，AutoResearch 跑完实验给你五条结论，哪条是真的、哪条是噪声？这个判断 AI 给不了你，因为它不知道你的业务约束、你的数据分布、你上周改了什么。

 所以面试官现在真正在卡的是： **你能不能驾驭 AI 工具，还是被 AI 工具驾驭。**![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPN8IKFiaadWUCOOCdpuPmRYeclpA3Z6q0qEZqWOSsFlXQZnYjdm0iblCeKabRC6zum3OPzIEia0OElNBLFhfiaJZEiaibeRjnbAibibXqia0/640?from=appmsg)
 两个候选人都用 Claude Code 搭了 Agent，都跑了消融实验。一个能说"第三组实验结论我不信，因为测试集分布和训练集有泄漏"；另一个把 AI 输出的数字直接贴进简历。面试官一眼就能分出来——而且现在更容易分，因为人人都有工具，工具反而成了照妖镜。

### 两条路先分清楚
 算法岗(RL 训练、reward 设计、数据工程)和开发岗(Agent 系统设计、生产化、评估体系)，侧重点差别很大。很多人第一步就错：简历同时投两边，说辞混着写，两边都觉得你不专业。

 开发岗也会考训练侧的基本原理——你用的模型为什么在你的任务上表现好或差，微调和提示词工程怎么选，模型升级后效果退步的原因分析。两条路有交集，但准备方向要先确定。
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPN8jSgGYUWRbicnOqqYQgGmBSyNdGtiblrfiboSCmArFtVN8puxicqLbszOhl2GsT45Btk8BCN6Swoic99QYSHMibqlPsmUt9rzYUmUFY/640?from=appmsg)
### 算法岗：面试官在问什么
#### 推理训练是 2026 年招人最多的方向
 各家都在卷，但大部分候选人卷的是同一件事：跑通了 GRPO 基础流程。AI 工具让这件事变得更容易了，也让它变得更不值钱了。面试官早就不在这里区分人了。

 真正被考察的是 **你对训练结果的判断力**。自动化实验框架能帮你跑完一百组消融实验，但你能不能看出哪组数据有问题、哪个结论站不住脚，这才是核心。

 具体到考察点： **开放域Reward怎么设计**。数学和代码的可验证奖励已经成熟，难的是没有标准答案的场景——逻辑分析、复杂决策。你用生成式奖励还是判别式，用ORM还是RPM，三者怎么加权、怎么避免互相干扰？AI 能帮你实现任何一种，但选哪种、为什么选，要你自己说清楚。

 字节的高频考题：给你一个具体的奖励作弊案例，你怎么诊断、怎么修。重复刷检索奖励、模糊回答骗大模型评判器、格式正确内容空洞——这些你能讲出来几个，每个背后的机制你理不理解？

 **长推理链的崩溃分析** 也是很见水平的考察维度。推理链超过十步以后，策略崩溃的根因往往不在强化学习算法本身，在奖励稀疏性和键值缓存管理。AI 工具能告诉你训练曲线长什么样，但它不知道你的任务为什么在第 12 步特别容易崩。你能不能定位到这一层，是高级和初级工程师的分界线。

#### Agentic Search训练
 传统 RAG pipeline 的纯算法岗在萎缩，现在的核心是用 RL 训练模型学会搜索，把搜索能力内化为推理的一部分，而不是外挂检索模块。

 面试真正问的：你的引用准确率和幻觉率是多少？用了什么奖励信号优化这两个指标？幻觉锚定(搜到了正确信息但回答时仍然编造)这个问题碰到过吗，根因在哪？

 有传统搜索背景的人转型做这个方向非常有优势，供不应求。

#### Agent Tool Use 训练
 面试官问的核心：你的 Agent 在真实环境的任务成功率是多少？失败案例的根因分析做了哪些？奖励信号怎么和任务成功率对齐的？

 环境交互式数据合成是新的考点：不是静态构造工具调用轨迹，而是让模型在沙盒环境中实际执行工具链，基于执行结果自动生成正负样本。你做过这件事吗？

### 开发岗：面试官真正在意什么
#### 自研 harness 是第一道门槛
 很多简历写"自建执行框架约 600 行 Python"，但 600 行里放了什么，没人讲清楚。AI 辅助编程让写出 600 行变得更容易了，也让这句话变得更不可信了。面试官想听具体细节，任何一个都能拉开差距。

 **agent loop 的终止逻辑** 是个好例子。谁来决定停止？max steps 阈值、模型自己输出 done 信号、外部 verifier 判断，你选的是哪种，为什么不选另外两种？Claude Code 能帮你实现任何一种，但这个选择背后的 trade-off 你得自己说清楚。mock 面试时问这个问题，大部分人愣住，因为框架帮他们做了决定，自己从来没想过。

 **上下文管理** 也是必问的。每一步之后上下文长什么样？什么时候截断，什么时候压缩摘要，关键观测结果怎么保留不被截掉？有没有观测预算机制——某个工具的输出超过 N 个 token 就只把摘要喂回模型，原文存轨迹里供后续获取？

 **错误恢复路径** 也绕不开。工具超时、工具报错、模型编造不存在的工具名、参数格式错误，每一种处理路径不一样。工具包装层的格式校验、返回结构化错误信息让模型自我修正，这块讲清楚了基本就过了工程考察。

 轨迹持久化和成本守卫也是必须覆盖的。每一步的输入/输出/费用/延迟都落盘，这是你能做调试的前提，不是可选项。

#### Memory 系统：考法已经不是"向量检索"
 "context window 是短期，vector DB 是长期"——这是 2023 年的答案。2026 年面试官想听 **分层 memory 架构** 的设计。

 四层：工作记忆是当前任务的草稿区，每步更新；情景记忆是历史交互的关键事件压缩，按相似度召回；语义记忆是用户画像、偏好、领域知识的长期沉淀；工作区记忆是执行深度调研或长代码任务时任务级别的进度跟踪。

 每一层的写入时机和读取触发条件都不一样。更深的问题是 **选择性遗忘**：过时的、矛盾的、低价值的信息怎么处理？召回污染(召回了过时记忆把模型带偏)怎么检测？

 mem0、Zep 用过没有，能不能讲清楚背后的设计原则，而不只是会调接口。
![image](https://mmbiz.qpic.cn/sz_mmbiz_png/cQwYPia4EPNicEkMoOQvPgxnuBlLvHxIypNR3k64xFjKfyx9zelGpbgD6oudbKO19DSg80ZibKkIqiaPyiczGb1u3kuhChUiaD4aQgepD7tGZ6gKI/640?from=appmsg)
#### 上下文工程：比向量检索更根本的问题
 Anthropic 推"上下文工程"这个词，本质是说：与其建复杂的记忆系统，不如先把上下文窗口里的内容编排好。这是个有立场的设计选择。

 根据当前任务状态实时决定哪些信息进入上下文、哪些裁剪；多 Agent 并发时每个 Agent 拿到的上下文是否完整且一致；相同信息用更少 token 表达——这些才是具体考察点。

 能讲清楚自己站哪边、为什么，就是高级工程师的信号。

#### 多 Agent 编排：最爱的送分题也是最爱的陷阱
 2026 年考察频率最高的设计题：Agent A 执行到一半失败了，怎么处理？整个任务回滚吗？

 满分答案需要覆盖：重试策略(指数退避还是立即重试)、部分结果的保留还是丢弃、后续 Agent 对前序输出的依赖程度、回滚的粒度(操作级还是任务级)。

 状态一致性这里有个常见误区：很多候选人直接回答"加锁"，面试官反而会追问为什么不重新设计架构。工业界的主流做法是通过架构设计规避并发修改——把共享状态收归一个调度者统一管理，各子 Agent 只读不写。说"加锁"往往是设计问题的信号，不是解决方案。

 **断点续传** 是从演示到生产的核心分水岭。长时间任务中断后怎么恢复，任务状态怎么持久化，演示不需要，生产不能没有。

#### 可扩展性：容易被忽视的考点
 开发岗高频但容易被忽视的一类设计题：你现在这个系统，如果并发量从每天 300 个查询变成 30 万个，会在哪里先崩？你怎么改造？

 这涉及异步任务队列的引入时机、模型推理的批处理策略、成本随规模的变化曲线。能说清楚自己系统的瓶颈在哪里，比说"我做了很多优化"有说服力得多。

#### 工具协议：不是考你知不知道名词
 MCP、A2A 协议现在是基础知识，但面试考察的不是"你听没听说过"。真正的考察方向是：描述字段怎么写才能让模型准确理解调用时机？碰到过模型误用工具吗，根因在描述不清楚还是在模型能力？工具调用的幂等性怎么保证？

#### 评估体系：被忽视的差距来源
 振动编程时代一个新的风险：AI 帮你跑完了评估，你敢不敢对结论负责。

 面试官想听 **分层评估**：最终答案准确率只是最粗的一层。中间是轨迹级别——每一步工具选择对不对、参数对不对。更细的是大模型评判加人工抽检，以及针对具体维度的专项评估器。

 **回归测试** 也是必考的：Agent 逻辑或底层模型升级后，有没有标准测试集快速验证没退步？线上升级时怎么用流量灰度保证不翻车？

 ==能回答"你的 Agent 比人工处理准确率提升了多少、怎么量化这个提升"的候选人，和只会把 AI 输出的数字直接贴进简历的人，差距非常大。==

### 一个能直接用的简历模板
 两条路都可以套，核心是每一行都有数字，每一行都能展开聊五分钟——而且是你真的能解释清楚的数字，不是 AI 帮你算出来但你说不明白的数字。

 **算法岗范例：** **字节跳动 | 豆包大模型团队 | 大模型算法实习生** 2024.10—2025.06

 • **负责部分**：参与豆包 Agent 推理能力训练，负责开放域 reward 设计与 PRM 训练，参与 Agentic Search 链路优化

 • **实习内容 1**：针对开放域推理场景(逻辑分析、复杂决策)缺乏 verifiable reward 的问题，设计 ORM + PRM + LLM-Judge 三路融合奖励方案，通过分层门控解决多 reward signal 冲突；在内部 benchmark 上推理准确率提升 6.2pp，同时将 reward hacking rate 从 18% 压到 4%

 • **实习内容 2**：分析长推理链(10 步以上)训练中 policy collapse 的根因，定位到 reward 稀疏性而非 RL 算法本身，引入 PRM 做 step-level credit assignment，配合渐进式 chain length curriculum；长链路任务 pass rate 提升 11pp，rollout 效率通过 trajectory cache 优化提升 3.8 倍

 • **实习内容 3**：负责 Agentic Search 中 citation grounding 的 reward 设计，解决 hallucination anchoring 问题(模型检索到正确信息但回答时仍编造)，citation 准确率从 71% 提升至 89%，hallucination rate 从 23% 降至 7%

 **开发岗范例：** **美团 | 平台技术部 | Agent 工程实习生** 2024.10—2025.06

 • **负责部分**：参与智能客服 Agent 平台建设，负责 Agent 执行引擎、memory 系统和评估体系，支撑售后、物流、售前三条业务线

 • **实习内容 1**：自研 Agent harness(约 800 行 Python)替代 LangChain，实现 tool wrapper 层统一 schema validation + 结构化错误回传机制，工具调用失败率从 12% 降至 2.3%；设计 observation budget 机制(单工具 output 超 2k token 自动压摘要)，配合 cheap-first 模型路由，单次会话 cost 从 $0.08 降至 $0.034

 • **实习内容 2**：针对用户跨 session 重复提供订单信息的问题，设计两层 memory 方案——working memory 管 session 内结构化状态，episodic memory 在 session 结束时提取关键事件(订单号、处理结果)存入用户档案；跨 session 信息重复率从 82% 降至 15%，相关会话平均处理时长缩短 40%

 • **实习内容 3**：建立三层评估体系——trajectory-level 规则校验(关键操作必须有用户确认步骤)、LLM-as-judge 每日 5% 抽检、340 条 golden case 覆盖高频场景与历史 bad case；上线后 P0 事故从季均 2-3 次降至 0

### 5 个直接废掉项目的坑
![image](https://mmbiz.qpic.cn/mmbiz_png/cQwYPia4EPNicIEliakvoa9b5KicASoJhznSSAXYEAWzujnOYBbWZw4tYI7rOptBl7OWYI6R4ZOeKo8HicKxm6w2SVpOntgZlKzn5r124iaAQsUT4/640?from=appmsg)
 **用了 LangGraph 但讲不清楚为什么用。** AI 帮你搭的框架，你说不清楚为什么选它，等于暴露了这个决定不是你做的。框架的取舍逻辑(状态管理复杂度、调试可见性、断点续传支持)要讲得出来。

 **GRPO 跑通了但没做过开放域奖励设计。** AutoResearch 帮你跑完了实验，但奖励函数是谁设计的，设计背后的判断是什么，面试官会直接问。没有真实判断的推理训练项目，说服力很弱。

 **记忆系统只是接了个向量数据库。** 接向量数据库是检索增强生成，不是记忆系统。做"记忆"项目，要能讲清楚分层设计、写入策略、选择性遗忘，否则面试官会直接归类为检索项目。

 ==没有轨迹就没有消融实验，没有消融实验就没有你能负责的数字。== AI 能帮你跑出数字，但数字背后的判断要你来做。没落盘轨迹，回头想解释数字解释不清楚。

 **多 Agent 系统但讲不清楚失败恢复。** 简历上写了多 Agent 系统，第一个问题必然是"某个 Agent 挂了怎么处理"。答案是"重新跑一遍"说明没想过生产场景，答案是"加锁"说明架构设计有问题。

### 最后
 振动编程时代，做项目的门槛降低了，讲项目的门槛反而提高了。

 以前面试官要判断"你会不会"，现在判断的是"你能不能对 AI 帮你做的事情负责"。项目越容易做，就越容易有人做出来又说不清楚，面试官就越容易通过"讲项目"这一关把人筛掉。

 所以结论还是那句话，只是理由变了：

 **有你能解释的数字 = 有项目。AI 跑出来但你说不清楚 = 没项目。** 阿东，大模型算法工程师，OPC创业者。
