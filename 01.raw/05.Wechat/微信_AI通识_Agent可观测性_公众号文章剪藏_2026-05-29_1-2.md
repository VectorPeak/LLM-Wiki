## 0x01. Hermes Agent 黑箱困境：多租户场景下的可观测性实战
> 发布日期：2026-05-28  
> 原文链接：[Hermes Agent 黑箱困境：多租户场景下的可观测性实战](https://mp.weixin.qq.com/s/KNPfgW3badB6IzO5ZCl4EQ)

### AI Agent 黑箱困境：多租户场景下的可观测性实战
 **作者：AI通识** 上周五，线上用户反馈："AI 回答质量变差了，一直在打转。"

 你打开日志，看到的是一行行抽象的 token 数字和错误码。到底哪一步出了问题？是 prompt 不对？是工具返回了脏数据？还是上下文窗口爆了？

 **看不见的过程，正在成为 AI 产品最大的技术债。** 今天聊一个我们内部刚刚完成技术方案设计的场景：多租户 AI Agent 平台的可观测性系统怎么搭。

### 1. 为什么 AI Agent 的可观测性比普通微服务更难
 传统微服务的可观测性，有成熟的套路：请求 → 服务 → 数据库，每一层都能打点，日志格式固定，Trace ID 一路透传。

 但 AI Agent 完全是另一回事。

 一个用户 query 进来，Agent 内部可能是这样的路径：
```yaml
用户: "帮我查一下北京今天的天气"
  → 第一次 LLM 调用(判断要调用工具)
  → 工具调用: search_weather(北京)
  → 第二次 LLM 调用(总结工具结果)
  → 回复用户
```
这只是最简单的情况。实际生产环境中，一次 query 可能触发十几次 LLM 调用、七八种不同工具、相互之间有依赖关系。

 **你面对的不是一条请求链，而是一棵动态生成的执行树。** 多租户场景下更复杂——128 个用户共享同一个 Agent 池，每次调用都要搞清楚：是谁在问、走了哪条路径、花了多少 token。

 没有可观测性，就是盲开。

#### 1.2 我们到底想看见什么
 经过内部讨论，我们列了四层需求，从基础到进阶：

 **第一层：原始记录** ● 模型每次调用的输入(prompt)和输出(response)

 ● 工具的名称、参数、执行结果、耗时

 ● 五维度 token：input / output / cache_read / cache_write / reasoning

 ● 每次 API 调用的费用明细

 **第二层：Trace 调用树** ● 用户一次 query = 一条完整 Trace

 ● Trace 下面挂：Generation(LLM 调用)和 Span(工具调用)

 ● 同一次 session 里多轮对话，能关联到一起

 **第三层：量化指标** ● 服务响应速度：P50 / P95 / P99

 ● Token 消耗趋势：按用户、按模型、按时间

 ● 工具错误率：哪个工具最容易挂

 ● 上下文压缩频率：session rotation 次数

 **第四层：高级能力** ● 异常检测：同工具连续失败、空响应循环、API 调用逼近上限

 ● 决策归因：Agent 为什么选了这个工具而不是另一个

 ● 启发式评估：自动判断这次执行到底算成功还是失败

 前两层是必须有的，后两层是做得好的加分项。

#### 1.3 核心技术选型：Hermes Plugin Hook + Langfuse
 我们选择了一个改动最轻的方案： **不碰 Hermes 源码，在 Gateway 层通过 Plugin Hook 机制接入 Langfuse。** 先说 Hermes 的 Hook 体系。

 Hermes Agent 在每次关键操作节点上留了回调口子，外部可以注册插件来监听。核心有 6 个：

| Hook 名称 | 触发时机 |
| :--- | :--- |
| on_session_start | Session 首次创建时(全新 session) |
| pre_api_request | 每次 LLM API 调用前 |
| post_api_request | 每次 LLM API 调用后 |
| pre_tool_call | 每次工具执行前 |
| post_tool_call | 每次工具执行后 |
| on_session_end | Session 结束时 |

 这 6 个 Hook 覆盖了 LLM 调用和工具执行的全生命周期。

 **但有一个细节要注意**： on_session_start 只在"全新 session 创建时"触发一次。如果用户在同一个 session 里连续发多条消息，后续消息不会再触发这个 Hook。

 我们的方案是用 pre_api_request 的 api_call_count 参数来判断——等于 0 就是这次 query 的第一次 LLM 调用，在这个时候创建 Trace，而不是依赖 on_session_start。这样每次用户 query 都是一条独立的 Trace，层级最清晰。

 数据流是这样的：
```text
用户 query
  → pre_api_request(api_call_count=0)
      → 创建 Trace
      → 创建第一个 Generation(input=prompt)
  → post_api_request
      → 补全 Generation(output=response, usage, cost)
  → 工具调用
      → post_tool_call → 创建 Tool Span
  → pre_api_request(api_call_count=1)
      → 第二个 Generation(续接同一 Trace)
  → ……
  → on_session_end
      → 启发式评估 → 写 Score
      → flush → Langfuse
```
Langfuse 负责数据的存储和可视化，我们不需要自建数据库。

#### 1.4 异常检测：让 AI 打转时你能知道
 AI Agent 有一类很难缠的问题： **打转(loop)和反复重试**。

 比如，Agent 一直调用同一个工具、一直返回错误，但外部完全看不见。

 我们在 Hook 里内置了三条检测规则：

 **规则一：同工具连续失败** ● 检测逻辑：同一个工具连续 N 次(默认 3 次)返回含 error 的结果

 ● 触发后：写入 trace metadata + 告警日志

 **规则二：API 调用逼近上限** ● 检测逻辑：单轮 API 调用次数达到上限的 80%

 ● 触发后：写入 trace metadata

 **规则三：空响应循环** ● 检测逻辑：连续 N 次(默认 2 次)LLM 返回空内容

 ● 触发后：写入 trace metadata

 这些异常事件会挂在 Trace 上，在 Langfuse Dashboard 里可以直接看到：这次执行有没有异常、是哪条规则触发的、严重程度如何。

#### 1.5 成本估算：每次对话花了多少钱
 每个企业级 AI 产品都要回答这个问题：谁在花钱、花了多少。

 我们的方案是复用了现有的 billing/ 模块，里面有完整的分段落价计算逻辑(input / output / cache_read / cache_creation 四类)，从数据库里的 models 表读取定价配置。

 在 post_api_request Hook 里，每次 LLM 调用结束后，从返回的 usage 字段拿到 token 数量，调用 calculate_cost() 算出这一次的费用，写入 Langfuse 的 cost_details。

 Langfuse 自带成本聚合看板，按用户、按模型、按时间段都能看。不需要额外开发。

#### 1.6 多租户隔离：128 个用户共享同一个 Agent 池，怎么追踪
 这是整个方案里最容易被忽略、但又最关键的点。

 多租户场景下，所有用户的请求共享同一批 Agent 实例。如果可观测数据没有租户隔离，就会串台：A 用户的 Trace 里出现了 B 用户的工具调用记录。

 我们的做法是：每次 Hook 触发时，从 ThreadContext(线程级上下文隔离机制)读取当前请求的 user_id、session_key、channel、is_scheduled 等信息，写入 Langfuse Trace 的 metadata 字段。

 Langfuse 支持按 metadata 字段过滤查询，所以可以在 Dashboard 上直接按 user_id 筛选：只看某个用户的所有 Trace。

#### 1.7 一句话总结
 **你不需要改造 Hermes 源码，只需要注册 6 个 Hook，AI Agent 的每次执行过程就能自动写入 Langfuse。** 一次 query = 一条 Trace = 一次完整的思考 + 工具调用 + 成本记录。

 看不见的过程，被完整记录下来；看不见的成本，有数可查。

 **你的团队现在能回答这四个问题吗？** 1. 过去 24 小时，哪个用户的 Token 消耗最高？
 2. 过去一周，哪几个工具的错误率超过了 50%？
 3. 上周五那次用户反馈"AI 在打转"，Agent 到底调了哪些工具、循环了几次？
 4. 换一个 prompt，这次执行会不会比上次好？

 如果四个问题里有任何一个答不上来，是时候考虑给 AI Agent 装上"黑匣子"了。

## 0x02. Hermes Agent 可观测性方案系列（01）——Langfuse 深度解析
> 发布日期：2026-05-29  
> 原文链接：[Hermes Agent 可观测性方案系列（01）——Langfuse 深度解析](https://mp.weixin.qq.com/s/nwpNnKOmkTzKrLDlGkq7Eg)

Langfuse 深度解析：为什么 AI Agent 的可观测性需要专用工具

 **作者：AI通识** 你可能用过 New Relic、Sentry、Datadog APM。这些工具对微服务很有效——一个请求进来，层层打点，每一层都能埋点，每一步都能计时。

 **但 AI Agent 完全不是一回事。** 一个 AI Agent 的执行路径不是一条链，而是一棵动态生成树：LLM 判断要调用工具 → 工具返回结果 → LLM 再判断 → 再调用。没有固定链路，节点数量不固定，调用顺序也不固定。

 传统 APM 工具看不懂这棵树。

 这就是 Langfuse 解决的问题。

### 1. Langfuse 是什么
 Langfuse 是一个专注于 LLM 应用的可观测平台，核心解决一个问题： **你的 AI 应用在做什么、消耗了多少、花了多长时间、效果到底怎么样**。

 它不是通用 APM，也不是日志管理系统。它是专门为 AI 应用设计的。

 GitHub stars 超过 15k(数据截止 2025 年 Q4)，开源版本可以自建，官方也提供托管云服务。支持 Python / JS/TS SDK，对 LangChain、LlamaIndex、Hermes 都有原生集成。

#### 1.2 核心概念：Trace、Generation、Span、Event、Score
 Langfuse 的数据模型设计得很克制，只有 5 个核心概念：

### 1. Trace — 一次完整执行
 **定义**：从用户输入到最终输出的完整执行过程。

 对应关系：

 ● AI Agent 里：用户一次 query = 一条 Trace

 ● LangChain 里：一个 chain execution = 一条 Trace

 **关键字段**：
```text
trace_id       # 全局唯一 ID
session_id     # 会话 ID(可自定义)
user_id        # 用户 ID(用于多租户)
metadata       # 自定义元数据(模型名、channel、是否定时任务等)
```
**重要语义**：Trace 是 **根节点**，下面的 Generation 和 Span 都是它的子节点。

#### 1.2 Generation — 一次 LLM 调用
 **定义**：每次对大模型的 API 调用。

 **关键字段**：
```text
model              # 模型名称
input              # 请求消息(prompt)
output             # 模型输出(response + reasoning + tool_calls)
usage_details      # token 消耗(五维度)
cost_details       # 费用明细
metadata           # 自定义元数据(API 耗时、finish_reason 等)
```
**典型使用场景**：

 ● 记录每次 LLM 调用的 input 和 output

 ● 抓取 reasoning 过程(如果模型支持)

 ● 统计 token 消耗和费用

 ● 关联到具体的工具调用(tool_calls 字段)

#### 1.3 Span — 一个操作单元
 **定义**：一个有时间跨度的操作，可以嵌套。

 Langfuse 里 Span 有几种类型：

| 类型 | 用途 |
| :--- | :--- |
| span (通用) | 任意有耗时的操作，如 RAG 检索、外部 API 调用 |
| tool | 工具执行(Agent 调用工具) |
| buffer | 流式输出的中间过程 |

 **关键字段**：
```text
name          # 操作名称(如 "Tool: read_file")
input         # 输入参数
output        # 输出结果
metadata      # 自定义元数据(工具耗时、tool_call_id 等)
start_time    # 开始时间
end_time      # 结束时间
```
**Span vs Generation 的区别**：

 ● Generation 专属于 LLM 调用

 ● Span 是更通用的操作单元，可以是 RAG 检索、工具执行、外部 API 等

#### 1.4 Event — 瞬时事件
 **定义**：没有时间跨度的瞬时事件。

 典型使用场景：

 ● 异常事件：Anomaly detected

 ● 决策事件：Decision made

 ● 人工标注：Human feedback

 Event 的典型 metadata：
```json
{
  "rule": "tool_repeat_failure",
  "tool_name": "search_weather",
  "streak": 3,
  "severity": "high"
}
```
#### 1.5 Score — 评估分数
 **定义**：对一次 Trace 或 Generation 的质量评分。

 **关键字段**：
```text
name           # 评分维度(如 "heuristic"、"user_feedback"、"llm_judge")
value          # 分值(0-1 或 0-100)
comment        # 评分说明
```
**典型使用场景**：

 ● 启发式自动评估(无最终回复 = 0，高异常 = 0)

 ● 用户点赞/点踩(1 = 好，0 = 差)

 ● LLM-as-Judge 评估(用另一个模型打分)

#### 1.3 为什么不用 OpenTelemetry 或传统 APM
 这是我们内部讨论最多的一个问题。

 **传统 APM 的假设**：
 1. 请求路径是固定的(HTTP → Router → Service → DB)
 2. 每层边界清晰，可以打点
 3. 调用是同步的，有明确的父子关系

 **AI Agent 的实际情况**：
 1. 执行路径是动态生成的(LLM 自己决定下一步做什么)
 2. 工具调用数量不固定(可能 0 次，可能 20 次)
 3. LLM 调用之间有条件依赖("如果搜索结果为空，则改用维基百科")
 4. 流式输出时，完整 response 要等很久才能拿到

 **OpenTelemetry 的局限**：

 ● OpenTelemetry 的 trace 模型是"父子 Span"，适合同步调用链

 ● AI Agent 的 LLM 调用 → 工具执行 → LLM 调用的循环，不符合简单的父子关系

 ● OpenTelemetry 没有 Generation 概念，不知道如何记录 token 消耗和 reasoning 过程

 ● OpenTelemetry 的数据模型需要手动维护 trace hierarchy，AI Agent 的动态性导致这个维护成本极高

 **Langfuse 的优势**：

 ● 原生支持"LLM 调用"这个概念(Generation)，直接记录 input/output/usage

 ● Trace 结构天然支持动态生成树，工具调用作为 Span 挂在 LLM 调用下面

 ● 内置 cost 估算和 token 统计，不需要自己拼装

 ● Dashboard 原生支持 LLM 应用的场景(latency by model、token by user)

 **结论**：如果你的 AI 应用只需要看"请求是否成功"，OpenTelemetry 可以满足。如果你想看到"AI 到底在想什么、用了多少 token、哪个工具最容易出错"，Langfuse 是目前最成熟的专用品。

#### 1.4 Langfuse 的数据模型如何映射到 AI Agent 场景
 这是我们方案设计时的核心映射表：

| AI Agent 概念 | Langfuse 对象 |
| :--- | :--- |
| 用户一次 query = 完整执行过程 | **Trace** |
| 每次 LLM API 调用 | **Generation** |
| 每次工具执行 | **Span (type=tool)** |
| 上下文压缩事件 | **Span (type=span)** |
| 子 Agent 调用 | **Span (type=span)** |
| 异常事件 | **Event** |
| 启发式评估结果 | **Score** |

#### 1.5 Langfuse 的局限
 说清楚局限很重要，没有工具是万能的。

 **局限一：没有实时告警** Langfuse 是一个数据存储和可视化平台，不做实时告警。检测到异常后，你需要自己对接飞书/邮件/Slack 等通知渠道。方案里我们通过日志告警( logger.warning)解决，不另建通知系统。

 **局限二：重跑能力弱** Langfuse 支持查看历史 Trace，但没有"重跑"功能。改了 prompt 之后，想对比新旧效果，需要自己触发重跑。R-2 和 R-3(回放与对比)在需求文档里标注为后续版本。

 **局限三：托管版有可用性风险** 如果你们用 Langfuse 官方托管版，服务宕机则数据丢失。方案里我们在 Hook 内做了 fail-open(Langfuse 写入失败不影响 Agent 主流程)，本地日志做兜底。

#### 1.6 Langfuse vs 其他 AI 可观测性方案横向对比
| 方案 | 专注领域 | 开源 | 自托管 | Token 统计 | 成本估算 | Dashboard | 适合场景 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Langfuse** | LLM 应用 | ✅ | ✅ | ✅ | ✅ | ✅ | AI Agent、可观测性优先 |
| **Phoenix (Arize)** | LLM / ML | ✅ | ✅ | ✅ | ❌ | ✅ | 需要 LLM Evals 能力 |
| **Weights & Biases** | ML 实验 | ✅ | ❌ | ✅ | ❌ | ✅ | ML 训练 + AI 应用 |
| **OpenTelemetry** | 通用 APM | ✅ | ✅ | ⚠️ 需扩展 | ❌ | ❌ | 已有 APM 基础设施 |
| **Datadog LLM OPS** | 云服务 | ❌ | ❌ | ✅ | ✅ | ✅ | 使用 Datadog生态 |

 结论：Langfuse 是 AI Agent 场景下性价比最高的选择，开源自托管没有厂商锁定，成本估算原生支持。

#### 1.7 Langfuse SDK 核心 API 三行代码入门
 Langfuse 的 SDK 设计很简洁，三行代码就能开始记录：
```python
from langfuse import Langfuse

langfuse = Langfuse(
    public_key="pk-lf-xxx",
    secret_key="sk-lf-xxx",
    base_url="https://cloud.langfuse.com"
)

### 创建 Trace
trace = langfuse.trace(
    session_id="user_session_123",
    user_id="user_456",
    metadata={"channel": "feishu", "is_scheduled": False}
)

### 记录 LLM 调用
generation = trace.generation(
    name="llm_call_1",
    input={"messages": [{"role": "user", "content": "你好"}]},
    model="claude-sonnet-4",
    metadata={"provider": "openai"}
)

### 模拟 LLM 返回
generation.update(
    output={"content": "你好！有什么可以帮你的？", "reasoning": "用户打招呼"},
    usage_details={"input": 10, "output": 20},
    cost_details={"total": 0.002}
)
generation.end()

### 记录工具调用
span = trace.span(
    name="Tool: search_weather",
    input={"city": "北京"}
)
span.update(output={"temperature": "25度", "weather": "晴"})
span.end()

### 写评分
trace.score(name="heuristic", value=1.0, comment="正常完成")

### 发送数据
langfuse.flush()
```
这就是整个 Langfuse 可观测性的核心—— **trace → generation/span → score → flush**。
