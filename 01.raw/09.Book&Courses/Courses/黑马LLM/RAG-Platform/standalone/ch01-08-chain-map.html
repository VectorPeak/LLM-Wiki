05-11 章：从用户问题到可信回答的完整流程闭环

这张地图只覆盖第 05 到第 11 章。第 05-08 章完成“判断问题、生成检索计划、改写追问、执行真实 Milvus 检索”， 第 09-11 章把这些能力接入 QAService 和 RAG Pipeline，补齐 FAQ 高置信直出、文档检索、上下文构建、Prompt Profile 选择、 LLM 流式生成、引用增强、历史写入和结束事件。闭环终点是一次完整问答请求返回稳定答案，并把本轮问答写入历史，供下一轮追问继续使用。

完整闭环总图

这张图保留 05-11 章完整闭环，并把容易漏讲的辅助输入和收口分支一起画出来：中间是在线主链路，上方是场景、版本、过滤、Prompt 和历史，下方是 prepare_retrieval 展开、Hybrid Search 细节、提前收口与异常收口。

读图顺序：先读中间主链路 1-16，再读上方辅助输入 17-22，最后读下方展开节点 23-26 与 A-D 收口分支。

05-07：判断、计划、改写 08：真实 Milvus 检索 09-10：服务入口与 Pipeline 闭环 11：Prompt Profile 决定回答口径
读图方法： 先按中间主链路 1-16 读完整在线问答，再看上方 17-22，理解场景、版本、过滤、Prompt 和历史如何作为辅助输入；最后看下方 23-26 与 A-D，理解检索准备展开、Hybrid Search 细节以及提前/异常收口。
1

用户问题进入系统

输入不只是 query，还包括 source_filter、session_id 和历史会话标识；这些字段决定后续是否限定来源、是否可追问改写、最终历史写到哪里。

2

QAService 服务入口

QAService.stream_query() 是 Web/API 层调用的稳定服务门面，先校验 source，再把请求交给 rag.stream_query() 产生事件流。

3

Pipeline 入口

rag.stream_query() 开启一次完整问答流程，先发 start 事件，然后按路由、检索、上下文、生成、收口的顺序推进。

4

创建请求上下文

create_query_context() 生成 RAGQueryContext，集中保存场景、数据域、active_kb_version、trace_id、session_id 和运行阶段信息。

5

第 05 章：查询路由

decide_route() 先做低成本确定性判断：问候、越界、转人工、source 边界和 FAQ 精确命中可以提前收口；只有 retrieval 才继续进入检索链路。

6

检索准备入口

prepare_retrieval() 是 05-07 和 11 章能力的汇合点，内部完成意图、source、历史改写、检索计划、查询变体和 Prompt Profile 选择。

7

参数包回到 Pipeline

RetrievalPreparation 把 intent、plan、rewritten_query、query_variants、prompt_profile、effective_source_filter 和 history 统一交还给主流程。

8

FAQ 检索

search_faq() 调用 get_faq_store().search_many() 查询 FAQ collection。这里既服务 FAQ 标准答案直出，也为最终上下文提供 FAQ 证据。

9

FAQ 高置信判断

get_faq_direct_answer() 根据精确匹配或阈值判断是否可以返回标准答案；命中时不调用 LLM，直接进入 FAQ 标准答案收口分支。

10

文档检索

FAQ 不能直出且计划允许文档检索时，search_doc() 调用 get_doc_store().search_many() 查询文档 collection，补齐长文档证据。

11

上下文筛选与拼装

select_context_docs() 从 FAQ 和 Doc 命中中挑选最终证据，build_context() 把这些证据拼成 Prompt 可用的上下文文本。

12

上下文是否足够

如果没有可用证据或分数不足，Pipeline 返回信息不足答案；只有 context_docs 足够可信时，才允许进入 LLM 生成。

13

LLM 流式生成

stream_llm_answer() 基于已组装的 Prompt 生成答案，并持续产出 token 事件，前端或调用方可以边生成边展示。

14

引用增强

enforce_answer_citations() 在生成完成后检查和补强参考来源，保证最终答案可以回溯到检索证据。

15

写入会话历史

history.add_turn() 把本轮用户问题和系统答案写入历史。下一轮“那审批呢”这类追问，才能读取上一轮上下文完成改写。

16

结束事件

finish_success() 返回 answer、sources、intent、retrieval_info、trace 和耗时指标。到这里，一次问答请求才算完整闭环。

17

场景与数据域

场景配置决定有效来源、collection、Prompt 和数据路径；DataScope 进一步约束租户、数据集、可见性和角色范围。

18

Active 知识库版本

resolve_active_kb_version() 从 MySQL 中读取当前场景的 active 版本，后续 FAQ/Doc 检索都必须带上 kb_version 过滤。

19

检索过滤条件

build_source_expr() 把 source_filter、valid_sources、kb_version 和 DataScope 组合成 Milvus 查询表达式，确保只查允许访问的数据。

20

Prompt Profile 选择

build_answer_prompt_profile() 根据问题类别优先、意图兜底选择回答模板，控制 FAQ、知识问答、费用、合规、排障等不同回答口径。

21

历史消息读取

history.get_context_messages() 为 FOLLOW_UP 改写和 Prompt 填充提供历史。它是辅助输入，不是独立收口路径。

22

Prompt 组装

prepare_answer() 把 Prompt Profile、用户问题、历史和检索上下文组装为 system_prompt/user_prompt，随后交给 LLM。

23

意图与有效 source

classify_intent() 产出 IntentResult，resolve_effective_source_filter() 决定最终生效的 source 过滤，避免用户输入和意图冲突。

24

历史改写

rewrite_query_if_needed() 使用最近历史把 FOLLOW_UP 短问题改写成独立问题，例如把“那审批呢”改写为围绕上一轮主题的完整问题。

25

检索计划与查询变体

build_retrieval_plan() 决定 FAQ/Doc、top_k、阈值、rerank 和上下文数量；generate_query_variants() 生成多路查询表达提升召回。

26

Milvus Hybrid Search 内部

每个 collection 内部执行 Dense + BM25 Sparse 混合检索，再做多变体合并、按文档去重和 rerank，输出统一的 RetrievalResult。

A

直接收口

问候、越界、转人工和 source 边界提示不查 Milvus，也不调用 LLM，直接通过 _finish_with_single_answer() 返回确定性答案。

B

FAQ 标准答案收口

FAQ 命中足够可靠时返回 FAQ 标准答案。这条路径仍会写历史和发 finish 事件，但不会走文档检索和 LLM 生成。

C

信息不足收口

检索后没有足够证据时返回信息不足答案，避免模型在无上下文支撑时编造。这条路径同样会写历史并结束请求。

D

异常收口

finish_error() 处理流程中的异常，返回可恢复错误事件，保证调用方能收到明确失败原因，而不是连接无声中断。

节点函数说明

这张表按大图编号解释每个节点里的函数、字段和分支值。讲课时可以先看大图串主线，再用这张表展开每个代码名在业务闭环中的职责。

节点 图中名称 函数 / 字段 作用说明
1 用户问题 query / source_filter / session_id / history query 是本轮问题；source_filter 限定资料来源；session_id 决定历史读写位置；history 为追问改写和 Prompt 提供上下文。
2 QAService QAService.stream_query() / validate_source() stream_query() 是服务层统一入口；validate_source() 校验前端传入的 source 是否属于当前场景，避免无效来源进入 Pipeline。
3 Pipeline 入口 rag.stream_query() / start_event() rag.stream_query() 执行完整问答主流程；start_event() 告诉调用方请求已经进入 Pipeline，后续会持续输出事件。
4 请求上下文 create_query_context() / RAGQueryContext create_query_context() 创建请求级状态对象；RAGQueryContext 保存 query、scenario、DataScope、active_kb_version、trace_id、retrieval_info 等运行数据。
5 查询路由 decide_route() / direct_answer / source_boundary / faq_exact / retrieval decide_route() 判断问题下一步走哪条路；direct_answer 表示问候、越界、转人工等确定性直答；source_boundary 表示用户选择的来源和问题明显不匹配；faq_exact 表示 FAQ 精确命中可直接返回；retrieval 表示没有确定性答案，需要进入完整检索。
6 检索准备 prepare_retrieval() 把第 05-07 章和第 11 章能力合在一起：读取历史、分类意图、解析 source、按需改写追问、生成检索计划、生成查询变体，并选择 Prompt Profile。
7 参数包 RetrievalPreparation / intent / plan / variants / profile RetrievalPreparation 是检索和生成共用的数据包；intent 保存意图；plan 保存检索策略；variants 保存多路查询；profile 保存回答模板。
8 FAQ 检索 search_faq() / get_faq_store().search_many() search_faq() 是 Pipeline 的 FAQ 检索步骤；search_many() 对多个 query variant 查询 FAQ collection，返回 FAQ 命中结果。
9 FAQ 高置信 get_faq_direct_answer() / 阈值 / 精确匹配 get_faq_direct_answer() 判断 FAQ 命中是否足够可靠。精确匹配或分数超过阈值时直接返回 FAQ 标准答案，不再调用 LLM。
10 文档检索 search_doc() / get_doc_store().search_many() search_doc() 是 Pipeline 的文档检索步骤；search_many() 查询文档 collection，补齐制度、流程、材料、表格等长文档证据。
11 上下文筛选 select_context_docs() / build_context() select_context_docs() 从 FAQ 和 Doc hits 中筛选最终证据；build_context() 把证据拼成 Prompt 可读取的上下文文本。
12 上下文足够 context_docs / min_context_score context_docs 为空或分数过低时，系统返回信息不足；只有证据足够时才进入 LLM，避免无依据生成。
13 LLM 生成 stream_llm_answer() / token_event() stream_llm_answer() 调用大模型流式生成答案；token_event() 把生成中的 token 持续返回给调用方。
14 引用增强 enforce_answer_citations() 检查答案是否带有可追溯来源；模型漏写引用时补充来源，引用不可信时回退为更保守的回答。
15 写历史 history.add_turn() 把本轮用户问题和最终答案写入会话历史，下一轮 FOLLOW_UP 才能基于历史完成改写。
16 结束事件 finish_success() 输出成功结束事件，携带 answer、sources、intent、retrieval_info、trace、metrics 等诊断信息。
17 场景 / 数据域 scenario / DataScope / tenant / roles / visibility scenario 决定场景配置和 collection；DataScope 决定租户、数据集、角色、可见性等数据访问范围。
18 Active 版本 resolve_active_kb_version() / MySQL active 指针 / kb_version resolve_active_kb_version() 从 MySQL 中解析当前场景的线上知识库版本；kb_version 会进入检索过滤，保证只查当前版本。
19 检索过滤 build_source_expr() / source / kb_version / DataScope build_source_expr() 把来源、版本和数据域条件组合成 Milvus 表达式，确保检索只命中当前用户允许访问的数据。
20 Prompt Profile build_answer_prompt_profile() / 类别优先 / 意图兜底 根据问题类别优先选择模板，类别不明确时再按意图兜底，保证费用、合规、排障、FAQ、知识问答等回答口径不同。
21 历史消息 history.get_context_messages() / FOLLOW_UP 读取最近会话消息；当意图是 FOLLOW_UP 时，为问题改写提供上一轮主题，也可进入 Prompt 作为对话上下文。
22 Prompt 组装 prepare_answer() / system_prompt / user_prompt prepare_answer() 把 Prompt Profile、问题、历史和检索上下文组装成 LLM 输入；system_prompt 控制角色和规则，user_prompt 承载问题和证据。
23 意图与 source classify_intent() / resolve_effective_source_filter() / IntentResult classify_intent() 判断 FAQ、知识问答、追问等意图；resolve_effective_source_filter() 计算最终生效 source；IntentResult 是后续计划和 Prompt 的输入。
24 历史改写 load_history / rewrite_query_if_needed() load_history 提供最近对话；rewrite_query_if_needed() 把“那审批呢”这类短追问改成可以独立检索的问题。
25 计划与变体 build_retrieval_plan() / generate_query_variants() / run_faq / run_doc build_retrieval_plan() 决定是否查 FAQ/Doc、top_k、阈值、rerank 和上下文限制；generate_query_variants() 生成多种表达，提高召回。
26 Hybrid Search Dense / BM25 Sparse / merge_hits_by_document() / rerank_hits() Dense 捕捉语义相似，BM25 Sparse 捕捉关键词匹配；多变体结果会按文档合并去重，再用 rerank 精排，最终输出 RetrievalResult。
A 直接收口 direct / boundary / _finish_with_single_answer() 问候、越界、转人工和来源冲突不查 Milvus、不调用 LLM，直接用统一收口函数返回确定性答案并写历史。
B FAQ 标准答案 FAQ direct / _finish_with_single_answer() FAQ 高置信命中后直接返回标准答案，跳过文档检索和 LLM，但仍保持历史写入和 finish 事件一致。
C 信息不足 build_insufficient_context_answer() 没有足够证据时构造信息不足答案，明确告诉用户当前知识库无法支持回答，避免模型编造。
D 异常收口 finish_error() 捕获 Pipeline 异常并返回错误事件，调用方能看到失败原因和 trace，而不是只看到连接中断。

每章交付闭环

每章都交付一个能被下一章消费的明确产物，05-11 章组合后形成一次完整问答请求的闭环。

05 意图分类与路由入口

闭环目标：把用户问题变成可解释的路由结果和检索意图。

  • decide_route() 处理 direct_answer、source_boundary、faq_exact、retrieval。
  • classify_intent() 输出 IntentResult，标记是否需要追问改写。
  • resolve_effective_source_filter() 处理前端 source 与意图推断 source。
  • 交付给第 06 章：IntentResult 与有效 source。

06 检索策略与动态计划

闭环目标：把“需要检索”变成“按什么策略检索”。

  • infer_question_category() 识别费用、合规、排障、总结等问题类别。
  • is_table_query() 判断是否偏向表格资料。
  • build_retrieval_plan() 输出 RetrievalPlan。
  • 交付给第 07/08/10 章：run_faq、run_doc、top_k、阈值、rerank、variants 开关。

07 查询改写与变体生成

闭环目标：把追问补全成独立检索问题，并生成多路查询表达。

  • history.get_context_messages() 读取压缩历史和最近消息。
  • rewrite_query_if_needed() 对 FOLLOW_UP 调用 LLM 改写。
  • generate_query_variants() 结合结构化 LLM 输出和配置化规则生成变体。
  • 交付给第 08 章：rewritten_query 与 query_variants。

08 Milvus 混合检索

闭环目标：按照计划执行真实 Milvus FAQ 与文档检索。

  • get_faq_store() / get_doc_store() 取得真实 collection store。
  • build_source_expr() 拼接 source、kb_version、DataScope 过滤条件。
  • search_many() 对每个 query variant 执行 Dense + BM25 Sparse Hybrid Search。
  • 交付给第 10 章：FAQ / Doc RetrievalResult。

09 QAService 核心编排

闭环目标：提供稳定服务门面，让 API 或脚本只调用服务方法。

  • get_qa_service() 集中创建服务实例。
  • QAService.stream_query() 委托 rag.stream_query() 产出事件流。
  • QAService.debug_retrieval() 复用检索半链路用于诊断。
  • 交付给第 10/12 章：稳定的问答服务入口。

10 RAG Pipeline 主流程

闭环目标：把 05-09 章能力串成在线问答的 Stage 0-7。

  • stream_query() 串联 route、prepare、FAQ、doc、answer、save、end。
  • search_faq() 与 get_faq_direct_answer() 实现 FAQ 高置信直出。
  • prepare_answer() 构建上下文、来源和 Prompt 输入。
  • 交付结果：token 事件、finish_success、历史写入和 trace 信息。

11 Prompt 工程与 Profile 系统

闭环目标：根据意图、问题类别和场景选择稳定回答口径。

  • PromptProfile 保存 system_template、user_template、reason。
  • build_answer_prompt_profile() 按问题类别优先，再按意图兜底。
  • _scenario_prompt_context() 注入 assistant_name、business_domain、support_contact。
  • 交付给第 10 章：可直接填充上下文和问题的 PromptProfile。

16 10 RetrievalPreparation 历史、意图、source、改写、计划、变体、profile 检索参数包 下游检索和回答准备只消费这个对象，不重复做判断。

对象解释

RouteDecision 是第 05 章低成本路由结果：如果已有答案，直接进入收口。

IntentResult 是第 05-06 章之间的桥：它告诉策略层问题类型和是否需要改写。

RetrievalPlan 是第 06 章核心产物：它只描述检索策略，不执行检索。

RetrievalPreparation 是第 10 章的参数包：把第 05-07、11 章产物合并给第 08/10 章消费。

RetrievalResult 是第 08 章检索结果对象：FAQ 和 Doc 两路各有一份。

AnswerPreparation 是进入 LLM 前的最后对象：包含上下文、来源和最终 Prompt。

关键分支边界

这些分支是 05-11 章最容易讲混的位置，建议明确区分。

direct_answer 分支

第 05 章 decide_route() 可直接返回问候、感谢、越界、转人工等确定性答案。

这类请求不会进入第 06-08 章检索，也不会调用 LLM 生成。

source_boundary 分支

当用户选择的 source 与问题明显不匹配时，系统先返回边界提示。

这样避免带着错误过滤条件继续查 Milvus。

retrieval 分支

只有 route=retrieval 才进入 prepare_retrieval()。

此后才会执行意图识别、检索计划、追问改写、查询变体和 Prompt Profile 选择。

FOLLOW_UP 改写分支

“那审批呢”这种问题依赖上一轮历史，必须先改写成独立问题再检索。

第 07 章的输出会同时影响 FAQ 和 Doc 两路检索。

FAQ 高置信直出

第 08 章只负责返回 FAQ RetrievalResult；第 10 章用 get_faq_direct_answer() 判断是否直出。

如果直出，直接返回标准答案，不调用 LLM。

FAQ 与 Doc 两路检索

run_faq 和 run_doc 由第 06 章 RetrievalPlan 决定。

FAQ/Doc 是两个 collection；Hybrid Search 指单个 collection 内 Dense + BM25 Sparse。

信息不足分支

文档召回后，若没有候选通过阈值或上下文为空，第 10 章返回确定性信息不足。

这个分支不调用 LLM，避免没有证据时生成幻觉答案。

Prompt Profile 优先级

第 11 章先按问题类别选择风险模板，再按意图选择 FAQ/知识/追问模板，最后才用默认模板。

模板选择发生在 prepare_retrieval()，模板填充发生在 prepare_answer()。

历史闭环

不管是直答、FAQ 直出、信息不足还是 LLM 生成，只要成功收口都会写入历史。

下一轮请求再读取历史，形成完整多轮问答闭环。

讲解顺序建议

按这条线讲，可以把 05-11 章从“分散功能点”收束成“一个问题如何被可靠回答”。

  1. 先从服务入口讲起

    用第 09 章说明外部只需要调用 QAService.stream_query()，内部细节由 Pipeline 接管。

  2. 再进入 Pipeline 上下文

    第 10 章先创建 RAGQueryContext，把场景、数据域、版本、trace、session 都放到一个请求对象里。

  3. 第 05 章先判断，不急着检索

    先处理 direct_answer、source_boundary、FAQ 快路径和 retrieval 路由，避免所有问题都一股脑查库。

  4. 第 06 章把意图变成计划

    RetrievalPlan 决定 FAQ/Doc 是否执行、查多少、阈值多高、是否重排、是否启用变体。

  5. 第 07 章处理追问和多表达

    依赖历史的短追问先被改写，再生成 query variants，为真实检索提升召回覆盖面。

  6. 第 11 章提前选好回答口径

    Prompt Profile 随 RetrievalPreparation 一起向后传递，生成前不再临时让模型自己决定回答风格。

  7. 第 08 章执行真实 Milvus 检索

    FAQ 和 Doc 分别查询自己的 collection；每个 collection 内部执行 Dense + BM25 Sparse Hybrid Search。

  8. 第 10 章收口成最终答案

    FAQ 高置信直出时不调用 LLM；否则构建上下文、填充 Prompt、流式生成、补强引用、写历史、发结束事件。

闭环边界： 05-11 章讲完后，闭环不是停在检索结果，而是一次请求能经过服务入口、路由、计划、改写、真实检索、上下文、Prompt、生成、引用和历史写入，最终返回可追溯的答案。
