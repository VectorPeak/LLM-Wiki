    10.2 多 Agent 能力迁移场景¶

    学习目标¶

    • 掌握一套"把业务拆成多 Agent"的通用方法论
    • 通过 5 个真实场景，理解每个 Agent 的业务逻辑、对应范式与编排方式
    • 建立"EduAgent 的四种范式如何换皮迁移"的迁移直觉
    • 能把任一场景组织成简历项目的构思起点

    💡 本节不写代码，讲的是**架构与业务逻辑的迁移**。你在 EduAgent 里学到的四种范式（并行 / RAG / HitL / 状态机+SSE）和集成方法（路由 + 编排），在这些场景里几乎可以原样套用。

    10.2.0 迁移方法论：怎么把一个业务拆成多 Agent¶

    拿到任何一个业务需求，按下面四步就能拆出一套多 Agent 架构：

    第一步：找"角色"。 问自己——如果这件事交给一个团队做，会有哪些不同专业的人？每个"专业角色"通常对应一个 Agent。比如客服团队有"答疑的、查订单的、处理退货的、升级投诉的"，这就是四个 Agent 的雏形。

    第二步：给每个角色定范式。 看这个角色的工作性质，套 EduAgent 的四种范式：

    工作性质 范式 EduAgent 出处
    一个输入要从多个维度同时评估 并行评审 简历六维（第 4 章）
    需要基于私有知识/文档回答 RAG QA（第 5 章）
    关键决策必须人来把关 Human-in-the-Loop 试卷批改（第 6 章）
    有明确阶段的多轮交互 状态机 + 多轮 模拟面试（第 7 章）

    第三步：定编排方式。 看角色之间是什么关系：

    • 互斥（一次只需一个）→ 路由分发（统一入口 LLM 路由，8.4）
    • 有先后依赖（前者输出是后者输入）→ 串联 Pipeline（前序 structured 注入后序 context，8.3）
    • 同时进行（互不依赖）→ 并行 fan-out（第 4 章）

    第四步：补地基。 不管什么场景，都需要：取模型（get_llm）、记忆（MemorySaver+thread_id）、容错（with_retry 三层兜底）、统一入口（路由 + SSE）。这些是 EduAgent 第 3、8 章造好的、可直接复用的地基。

    📎 一句话：业务 = 一组角色，角色 = 一个 Agent + 一种范式，系统 = 路由/串联/并行把角色编排起来，再架在通用地基上。 下面五个场景，全是这套方法论的应用。

    10.2.1 场景一：智能客服中台¶

    业务背景与痛点¶

    电商 / SaaS 的客服每天面对海量咨询：售前问产品、售后查订单、要退换货、闹投诉。痛点是——这些诉求性质完全不同，用一个大 Prompt 硬接会四不像：查订单需要调订单系统、退换货有审批规则、投诉要安抚还可能转人工。强行塞进一个 Agent，既容易答错，又无法接业务系统。多 Agent 中台正好对症：先听懂用户要什么，再派给对的专业 Agent。

    Agent 拆解（含业务逻辑）¶

    ① 意图路由 Agent（范式：LLM 路由 + 规则前置拦截，对应 8.4） - 业务逻辑：先用规则拦截"你好/谢谢/人工"这类高频元话术（零 Token）；再用 LLM 判断诉求类别（FAQ / 订单 / 退换货 / 投诉 / 转人工），同时判紧急度。 - 关键业务规则：含"投诉、差评、曝光、12315"等高危词，或情绪强烈 → 直接标高优先级、优先转人工通道。 - 输入：用户消息 + 会话历史；输出：{intent, urgency, route_to}。

    ② FAQ 问答 Agent（范式：RAG，对应第 5 章） - 业务逻辑：从"产品手册 + 政策库 + 历史工单"知识库检索，增强生成答案，附引用来源。 - 关键业务规则：检索不到可靠依据时，不编造，转人工而非硬答（降级策略，对应 3.5 兜底思想）。 - 输入：问题；输出：答案 + 来源 + 置信度。

    ③ 订单状态 Agent（范式：多轮状态机，对应第 7 章） - 业务逻辑：多轮收集订单号/手机号 → 调订单系统 API → 播报物流状态 → 追问是否需要进一步操作。 - 关键业务规则：订单号缺失时进入"追问"阶段（状态机的 collect 状态）；查到异常单（超时未发货）自动给补偿话术。 - 输入：用户消息 + 已收集槽位；输出：订单状态卡片 + 下一步建议。

    ④ 退换货流程 Agent（范式：Human-in-the-Loop，对应第 6 章） - 业务逻辑：发起申请 → 规则自动审核（在保期/未拆封/金额阈值）→ 满足则自动通过、超阈值或异常则 interrupt 暂停转人工审批 → resume 后执行退款/换货。 - 关键业务规则：金额 > 500 或属"已使用"类目 → 强制人工审批（HitL 不可绕过）；自动通过的也要写审计日志。 - 输入：订单 + 退货原因；输出：审批结果 + 退款指令。

    ⑤ 投诉升级 Agent（范式：HitL 安全兜底，对应第 6 章） - 业务逻辑：情绪识别 + 诉求归类 → 先安抚 → 高危（威胁曝光/群体投诉）立即 interrupt 转人工坐席，并把上下文摘要一并交接。 - 关键业务规则：这是"安全红线"角色，宁可多转人工，不可漏判。

    编排方式¶

                  用户消息
                 │
        ┌────────▼─────────┐
        │ 意图路由 Agent     │  路由分发为主
        └───┬───┬───┬───┬──┘
       FAQ  订单  退换货  投诉
        │    │     │      │
       RAG  状态机  HitL审批  HitL转人工
                   │
         退换货前先走 FAQ 确认政策 → 再发起流程（局部 Pipeline）

    主体是**路由分发**；退换货场景里"先 RAG 确认政策、再发起退货流程"是一段**串联 Pipeline**（前序政策结论注入后序流程 context）。

    与 EduAgent 的映射¶

    意图路由 = unified_chat 路由（8.4）；FAQ = QA 图（第 5 章）；订单/退换货 = 面试状态机（第 7 章）+ 试卷 HitL（第 6 章）换皮；全部架在第 3 章地基 + 第 8 章集成之上。几乎是 EduAgent 的同构迁移。

    简历一句话¶

    基于 LangGraph + FastAPI 构建多 Agent 智能客服中台：规则前置拦截 + LLM 意图路由分发至 FAQ-RAG / 订单状态机 / 退换货 HitL 审批四类 Agent，SSE 流式响应，三层兜底保障高可用，客服人工介入率下降 X%。

    10.2.2 场景二：合同 / 法律审查助手¶

    业务背景与痛点¶

    企业法务每天审大量合同，痛点是**一份合同要同时从多个维度看**（法律风险、合规性、财务条款、权责对等），靠人逐条读既慢又容易漏，且需要法条/判例支撑、最终还得律师拍板。这天然是"多维并行 + 知识增强 + 人工把关"的组合。

    Agent 拆解（含业务逻辑）¶

    ① 条款拆解 Agent（范式：结构化抽取，地基 get_structured_llm 3.4） - 业务逻辑：把合同 PDF 切成结构化条款列表（每条带编号、类型、原文位置），为后续并行审查做准备。 - 关键业务规则：保留每条的原文 span（页码 + 字符偏移），后续所有问题都要能定位回原文（对应简历审查的"原文定位"思想）。

    ② 多维审查 Agent（范式：并行评审，对应第 4 章） - 业务逻辑：对拆解后的条款，四个维度并行**评审—— - 法律风险维：识别"无限责任、单方解除、管辖地不利"等风险点； - 合规维：对照行业监管要求（如数据合规、劳动法）； - 财务维：付款条件、违约金、税费承担是否对等； - 权责维：双方义务是否对称，有无"霸王条款"。 - 关键业务规则：每个维度独立打分（0-100）+ 风险等级（高/中/低）+ 原文定位 + 修改建议；四维 fan-out 并行执行，最后 fan-in 聚合。 - 这就是第 4 章简历六维并行的直接迁移：**把"六个评分维度"换成"四个审查维度"，图结构几乎不变。

    ③ 法条检索 Agent（范式：RAG，对应第 5 章） - 业务逻辑：针对识别出的风险点，从"法律法规库 + 判例库 + 企业合同模板库"检索支撑依据，让审查意见有法可依。 - 关键业务规则：引用必须可溯源（法条编号/判例案号），检索不到则标"需人工核实"。

    ④ 修订建议 Agent（范式：增强生成） - 业务逻辑：综合四维审查 + 法条依据，生成可直接采纳的修订条款（红线对比形式）。

    ⑤ 律师复核 Agent（范式：HitL，对应第 6 章） - 业务逻辑：高风险条款的修订 interrupt 暂停，交律师确认/改写，resume 后定稿。 - 关键业务规则：风险等级"高"的条款**必须**律师确认才能进入终稿（HitL 强制）。

    编排方式¶

    合同 PDF
   │
   ▼  串联 Pipeline
[条款拆解] → [多维审查（四维并行）] → [法条 RAG 增强] → [修订建议] → [律师 HitL 复核] → 终稿
                  │
            fan-out 四维并行 → fan-in 聚合

    主体是**串联 Pipeline**，其中"多维审查"那一站内部是**并行 fan-out/fan-in**。

    与 EduAgent 的映射¶

    多维审查 = 简历六维并行（第 4 章）；法条检索 = QA RAG（第 5 章）；律师复核 = 试卷 HitL（第 6 章）；条款拆解 = get_structured_llm（3.4）。

    简历一句话¶

    构建合同智能审查助手：四维度并行评审（法律/合规/财务/权责）+ 法条 RAG 溯源 + 高风险条款律师 HitL 复核，问题点支持原文定位，单份合同审查耗时从 X 小时降至 Y 分钟。

    10.2.3 场景三：研发协作与代码审查平台¶

    业务背景与痛点¶

    研发团队的痛点：PR 评审耗时且标准不一、新人不熟悉内部规范、单测覆盖不足。一个理想的研发助手要能**自动多维审 PR、基于内部代码库答疑、还能生成并验证测试**——这正好对应并行 + RAG + 沙箱 HitL。

    Agent 拆解（含业务逻辑）¶

    ① PR 审查 Agent（范式：并行评审，对应第 4 章） - 业务逻辑：对一个 PR 的 diff，**多维并行**审查—— - 安全维：SQL 注入、硬编码密钥、越权； - 性能维：N+1 查询、循环内 IO、复杂度； - 风格维：命名、注释、是否符合团队规范； - 测试维：是否有对应单测、覆盖率是否达标。 - 关键业务规则：每维给"阻断/警告/建议"三级；任一维出现"阻断"级问题 → PR 标记为"不可合并"。 - 直接复用第 6 章试卷"代码三轨批改"的多轨思想 + 第 4 章并行结构。

    ② 代码库 RAG Agent（范式：RAG，对应第 5 章） - 业务逻辑：把内部代码规范、架构文档、历史 PR、ADR 灌入知识库，回答"我们项目怎么处理鉴权""这个工具类在哪"。 - 关键业务规则：检索范围限定在企业私有库（权限隔离），引用具体文件路径/行号。

    ③ 测试生成 Agent（范式：沙箱执行 + HitL，对应第 6 章） - 业务逻辑：针对新增函数生成单测 → 在沙箱中试跑 → 跑通的建议合并、跑挂的标注原因 → 人工确认后并入。 - 关键业务规则：自动生成的测试**必须人工确认**才进主干（HitL）；沙箱执行失败不阻断，降级为"建议人工补测"。

    ④ 缺陷定位 Agent（范式：RAG + 推理） - 业务逻辑：结合报错堆栈 + 代码库检索，定位最可能的缺陷文件/函数，给修复建议。

    编排方式¶

            研发请求
           │
    ┌──────▼───────┐
    │ 意图路由       │  审PR / 问答 / 生成测试 / 查缺陷
    └──┬───┬───┬──┬┘
   PR审查 问答 测试 缺陷
   (并行) RAG (沙箱HitL) RAG

    路由分发**为主；PR 审查内部是**并行；测试生成内含 HitL。

    与 EduAgent 的映射¶

    PR 审查 = 简历并行（第 4 章）+ 试卷代码批改三轨（第 6 章）；代码库问答 = QA RAG（第 5 章）；测试生成 = 试卷沙箱 + HitL（第 6 章）。

    简历一句话¶

    研发协作平台多 Agent 系统：PR 安全/性能/风格/测试四维并行审查 + 内部代码库 RAG 答疑 + 单测生成沙箱验证 HitL 合并，PR 平均评审时长下降 X%。

    10.2.4 场景四：医疗导诊与报告解读助手¶

    业务背景与痛点¶

    互联网医院的导诊场景，安全与合规是第一位：不能乱给诊断、危急情况要立即转急诊、任何建议必须有医生背书。这是一个"状态机采集 + 知识增强 + 强制人工兜底"的典型，且 HitL 不是可选项而是**法规红线**。

    Agent 拆解（含业务逻辑）¶

    ① 分诊路由 Agent（范式：路由 + 安全规则，对应 8.4） - 业务逻辑：判断该挂哪个科室 + 紧急度分级。 - 关键业务规则（安全优先）：命中"胸痛、大出血、意识丧失、自杀倾向"等危急词 → 跳过一切后续流程，直接提示拨打急救 / 转人工急诊（硬规则前置，零容错）。

    ② 症状问询 Agent（范式：多轮状态机，对应第 7 章） - 业务逻辑：按医学问诊逻辑分阶段结构化采集——主诉 → 现病史 → 既往史 → 过敏史，每阶段缺失则追问。 - 关键业务规则：阶段流转有固定顺序（状态机），采集到"危急体征"随时可中断转急诊。 - 直接迁移第 7 章模拟面试的阶段状态机（WARMUP→TECH→…），把"面试阶段"换成"问诊阶段"。

    ③ 医学指南 RAG Agent（范式：RAG，对应第 5 章） - 业务逻辑：检索权威诊疗指南、药品说明书、禁忌库，给出**科普性**建议（非诊断）。 - 关键业务规则：只引用权威来源，所有输出加"仅供参考，不代替医生诊断"声明；检索不到则不臆测。

    ④ 报告解读 Agent（范式：并行评审，对应第 4 章） - 业务逻辑：化验单/体检报告的多项指标**并行解读**（血常规、肝功、血脂…各一路），标注异常项 + 通俗解释。 - 关键业务规则：异常指标只做"提示关注"，不做确诊结论。

    ⑤ 医生复核 Agent（范式：HitL 强制兜底，对应第 6 章） - 业务逻辑：所有面向患者的建议，在推送前 interrupt，由值班医生确认/修正后才出。 - 关键业务规则：这是**法规强制**的人工兜底，任何 AI 输出未经医生确认不得作为医疗意见。

    编排方式¶

    患者输入
   │
[分诊路由]──危急词──→ 立即转急诊（安全硬规则，最高优先级）
   │ 非危急
   ▼
[症状问询(状态机)] → [医学指南 RAG] → [报告解读(并行)] → [医生 HitL 复核] → 推送患者

    安全规则前置 + 状态机 + RAG + 并行 + 强制 HitL 的组合。

    与 EduAgent 的映射¶

    症状问询 = 面试状态机（第 7 章）；指南检索 = QA RAG（第 5 章）；报告解读 = 简历并行（第 4 章）；医生复核 = 试卷 HitL（第 6 章）；危急词前置 = 统一入口规则前置拦截（8.4）的安全化变体。

    ⚠️ 这个场景的灵魂是"安全兜底"：HitL 在 EduAgent 里是"提升质量"，在医疗里是"不可逾越的红线"。把它写进简历时，要突出"AI 仅做辅助、人工强制复核"的合规设计——这正是企业最看重的落地能力。

    简历一句话¶

    互联网医院导诊多 Agent 系统：危急症状安全前置 + 结构化问诊状态机 + 诊疗指南 RAG + 检验报告并行解读 + 医生强制 HitL 复核，在保证合规红线下将导诊效率提升 X%。

    10.2.5 场景五：智能投研分析助手¶

    业务背景与痛点¶

    券商/基金的研究员看一家公司，要综合财报、公告、新闻舆情、行业数据，再出研报。痛点是**信息源多、维度多、且投资建议受强监管**（必须合规风控）。这是"多源采集 + 多维并行 + 知识增强 + 风控兜底"的组合。

    Agent 拆解（含业务逻辑）¶

    ① 数据采集 Agent（范式：工具调用 / MCP，对应 5.11） - 业务逻辑：通过联网搜索 MCP + 数据接口，拉取目标公司的财报、公告、新闻、行业数据。 - 关键业务规则：标注每条数据来源与时间，过期数据降权。

    ② 多维分析 Agent（范式：并行评审，对应第 4 章） - 业务逻辑：四维并行——基本面（财务健康度）、技术面（量价趋势）、舆情面（新闻情绪）、行业面（赛道景气度），各出评分 + 关键结论。 - 关键业务规则：四维独立 fan-out，最后聚合成"综合评级"；任一维数据缺失则标"数据不足"而非补零。

    ③ 研报 RAG Agent（范式：RAG，对应第 5 章） - 业务逻辑：检索历史研报、行业数据库、券商内部观点，为分析提供横向对比与历史参照。

    ④ 估值建模 Agent（范式：结构化生成） - 业务逻辑：综合多维分析 + 研报参照，输出估值区间与逻辑（DCF/可比公司法的结构化结果）。

    ⑤ 风控复核 Agent（范式：HitL，对应第 6 章） - 业务逻辑：投资建议在出具前 interrupt，经合规/风控确认（利益冲突、信披合规、风险揭示）后才能发布。 - 关键业务规则：监管要求决定 HitL 强制，任何对外投资观点必须风控签字。

    编排方式¶

    研究标的
   │
   ▼  串联 Pipeline
[数据采集(MCP)] → [多维分析(四维并行)] → [研报 RAG 增强] → [估值建模] → [风控 HitL 复核] → 研报
                       │
                 fan-out 四维并行 → fan-in 聚合

    Pipeline 串联 + 内部并行 + RAG + 强制 HitL，结构与场景二（合同审查）高度同构。

    与 EduAgent 的映射¶

    数据采集 = MCP 联网搜索（5.11）；多维分析 = 简历并行（第 4 章）；研报检索 = QA RAG（第 5 章）；风控复核 = 试卷 HitL（第 6 章）；整体编排 = 求职全链路 Pipeline（8.3）的同构放大。

    简历一句话¶

    智能投研多 Agent 平台：多源数据采集（MCP）+ 基本面/技术面/舆情/行业四维并行分析 + 研报 RAG 横向对比 + 投资建议风控 HitL 复核，研究员单标的研究周期缩短 X%。

    10.2.6 更多可迁移场景一览¶

    除上面五个详解的场景，下面这些同样是"多 Agent 协同"，可按 10.2.0 的方法论自行拆解：

    场景 核心 Agent 组合 主要范式映射
    智能运维 AIOps 告警分诊路由 + 日志 RAG + 根因并行分析 + 处置 HitL 路由 + RAG + 并行 + HitL
    招聘全流程助手 JD 解析 + 简历并行筛选 + 模拟面试状态机 + 评估报告 几乎 = EduAgent resume+interview
    电商智能运营 选品 RAG + 文案多版本并行生成 + 投放策略 + 上架 HitL RAG + 并行 + HitL
    政务办事助手 事项路由 + 政策 RAG + 材料预审并行 + 人工终审 路由 + RAG + 并行 + HitL
    保险智能核保 资料结构化 + 多维风险并行评估 + 条款 RAG + 核保员 HitL 并行 + RAG + HitL
    智能教研备课 大纲生成状态机 + 资料 RAG + 多维度试题并行出题 + 教师审核 状态机 + RAG + 并行 + HitL

    💡 规律：几乎所有"专业服务类"业务，落地多 Agent 时都是这四种范式的排列组合 + 路由/Pipeline 编排 + 人工兜底。你已经把每一块都亲手写过了。

    10.2.7 如何把场景写进简历¶

    把上面任一场景组织成简历项目时，建议这样组织（招聘方最关心的就是这几点）：

    1. 一句话定位：用"多 Agent + 具体业务 + 量化收益"开头（如 10.2.x 的"简历一句话"）。
    2. 架构亮点：点明用了哪些范式（并行/RAG/HitL/状态机）和编排方式（路由/Pipeline），这是技术深度的体现。
    3. 工程能力：强调统一入口、三层兜底、流式响应、记忆持久化——这些是"能落地"而非"demo"的标志，企业极其看重。
    4. 难点与权衡：写 1-2 个真实难点（如"LLM 路由 vs 本地分类的取舍""HitL 强制兜底的合规设计""长对话摘要压缩"），对应 9.3 的面试题。
    5. 量化结果：耗时下降、人工介入率、准确率、Token 成本等，哪怕是估算也要有。

    📎 诚信提示：简历写你**真正理解并能讲清**的部分。EduAgent 的每个范式你都手写过、每个难点都踩过，面试时能讲到节点和文件级别——这种"讲得透"远比堆砌名词有说服力。下一节 9.3 的面试题集，就是帮你把这些"讲得透"的能力盘点成可应答的形式。

    章节总结¶

    • 迁移方法论四步：找角色 → 定范式 → 定编排 → 补地基；业务 = 一组角色，角色 = Agent + 范式，系统 = 编排 + 地基
    • 五个详解场景：客服中台（路由为主）、合同审查（Pipeline+并行）、代码平台（路由+并行+HitL）、医疗导诊（安全前置+状态机+强制HitL）、投研助手（Pipeline+并行+风控HitL）
    • 四种范式全程复用：并行（第4章）/ RAG（第5章）/ HitL（第6章）/ 状态机+SSE（第7章），换的是业务皮、不变的是图结构
    • 企业看重的是"能落地"：统一入口、三层兜底、流式、记忆、人工兜底，是把 demo 变成系统的关键，也是简历的加分项
    • 简历构思起点：任选一个场景，按 10.2.7 的五要素组织，技术深度与工程能力兼具
