    10.1 全景回顾与系统总览¶

    学习目标¶

    • 把第 2-8 章建成的东西拼成一张完整的系统地图
    • 理解三层架构（地基层 / Agent 层 / 集成层）如何协作
    • 掌握四个 Agent 各自演示的 LangGraph 范式，建立"一套技术、四种用法"的认知
    • 跟随一条请求走完全链路，把所有零件串成闭环

    10.1.1 我们从零建成了什么¶

    经过前面七章，你已经亲手写出了一个完整的后端系统 —— EduAgent：一个 IT 教培方向的 AI 原生多 Agent 教学辅助系统。技术栈是 LangChain 1.2.10 + LangGraph 1.0.9 + FastAPI + DeepSeek + Milvus + PostgreSQL。

    它不是一个玩具 demo，而是具备：四个各司其职的专业 Agent、一套统一的对外入口、完整的异常/重试/降级体系、本地模型与 RAG 知识库、多轮对话记忆与持久化、以及把这一切装配起来的应用骨架。

    一句话概括整个系统：用户说一句话，系统自动听懂意图、路由到对的 Agent（或几个 Agent 串联）、执行并以流式返回结果，全程有记忆、能降级、可观测。

    10.1.2 三层架构总览¶

    整个系统可以清晰地分成三层，自下而上：

    ┌─────────────────────────────────────────────────────────────┐
│  集成层（第 8 章）                                              │
│    unified_chat.py  统一入口：前置拦截 + LLM 路由 + SSE 分发     │
│    orchestrator.py  编排器：单 Agent 直达 / 多 Agent 串联       │
│    main.py          应用装配：lifespan + 路由 + MCP + health    │
└───────────────┬─────────────────────────────────────────────┘
                │ 调度
┌───────────────▼─────────────────────────────────────────────┐
│  Agent 层（第 4-7 章）—— 四个 Agent，四种 LangGraph 范式        │
│    简历审查（并行）  QA（RAG）  试卷批改（HitL）  模拟面试（状态机+SSE）│
└───────────────┬─────────────────────────────────────────────┘
                │ 复用
┌───────────────▼─────────────────────────────────────────────┐
│  地基层（第 3 章 + 第 5 章公共件）—— 所有 Agent 共用             │
│    config / logger / exceptions / retry / llm_factory          │
│    memory（MemorySaver+摘要）/ 本地模型 / MCP / 认证            │
└─────────────────────────────────────────────────────────────┘
    • **地基层**不感知任何 Agent 的业务逻辑，只提供底层能力（取模型、记忆、异常、重试、认证）。
    • **Agent 层**每个 Agent 是一张独立的 LangGraph 图，复用地基层，互不依赖。
    • **集成层**站在最上面，把四个 Agent 统一到一个入口背后，对用户屏蔽内部结构。

    这种分层的好处在前面已经反复体现：地基层改一处、所有 Agent 受益；某个 Agent 单独验证、不影响其它；集成层只做"连线"、不碰业务。

    10.1.3 四个 Agent 与四种 LangGraph 范式¶

    这是整门课的教学主线 —— 同一套 LangGraph 技术，用四种典型范式各演示一遍。学会这四种，几乎覆盖了多 Agent 系统里所有常见的控制流：

    Agent 章节 LangGraph 范式 核心机制 解决的问题
    简历审查 第 4 章 并行评审 fan-out 多分支并行 → fan-in 聚合 一份输入要从多个维度同时评估
    智能问答 第 5 章 RAG 检索 → 精排 → 增强生成 让 LLM 基于私有知识库回答
    试卷批改 第 6 章 Human-in-the-Loop interrupt 暂停 → 人工介入 → resume 恢复 关键决策需要人来把关
    模拟面试 第 7 章 状态机 + SSE 阶段流转 + 多轮对话 + 流式输出 有明确阶段的长流程交互

    💡 为什么是这四种：并行解决"一个输入多维评估"、RAG 解决"基于私有知识回答"、HitL 解决"关键决策要人把关"、状态机解决"有阶段的多轮流程"。现实里的多 Agent 系统，基本都是这四种范式的组合与变形（下一节 9.2 会展开迁移场景）。

    10.1.4 公共地基：被所有 Agent 复用的零件¶

    地基层是整个系统能"稳"的原因。回顾它提供的能力，以及在哪一章造的：

    公共件 文件 章节 提供的能力
    配置中心 config.py 第 3 章 所有环境变量的唯一真相源（Settings）
    结构化日志 core/logger.py 3.3 统一日志格式，便于检索定位
    异常体系 core/exceptions.py 3.3 EduAgentBaseError + 子类，按类型决定降级
    重试降级 core/retry.py 3.5 with_retry 三层兜底（重试→Agent降级→系统兜底）
    LLM 工厂 core/llm_factory.py 3.4 get_llm / get_structured_llm，统一取模型 + 缓存
    认证 dependencies.py 3.6 get_current_user，JWT 鉴权
    记忆管理 core/memory.py 5.10 MemorySaver 隔离、thread_id、滑动窗口、摘要压缩
    本地模型 reranker / classifier / embedder 5.8 / 5.9 / 5.4 精排、意图分类、向量嵌入
    知识库 core/knowledge_base.py 5.4 / 5.18 文档向量化入 Milvus + 检索
    MCP 工具 mcp/* 5.11 知识库 MCP + 联网搜索 MCP

    📎 一个贯穿全课的设计原则：调 LLM 一律走 get_llm/get_structured_llm，绝不在节点里手搓模型；存对话一律走 MemorySaver + thread_id；调用失败一律靠 with_retry 兜底。统一入口收敛，是大型系统可维护的前提。

    10.1.5 集成层：从四个孤岛到一个系统¶

    第 8 章把四个独立 Agent 拧成系统，靠两个核心角色：

                用户一句话
                │
                ▼
   ┌─────────────────────────┐
   │ unified_chat.py（接待员） │  听懂意图
   │   ① 规则前置拦截（零Token）│
   │   ② LLM 路由（6 类意图）  │
   │   ③ SSE 四分支分发        │
   └───────────┬─────────────┘
               │ 派活
               ▼
   ┌─────────────────────────┐
   │ orchestrator.py（调度台） │  执行编排
   │   单 Agent 直达           │
   │   多 Agent 串联 Pipeline  │
   │   （前序输出注入后序）     │
   └───────────┬─────────────┘
               │ 调图
               ▼
        四个 Agent 的 LangGraph 图
    • 接待员 unified_chat.py：规则前置拦截处理社交/元场景（零 Token），LLM 路由判 6 类意图，按 label 分四支（qa 流式 / 引导跳转 / pipeline 计划 / 澄清）。
    • 调度台 orchestrator.py：拿到明确的 agent_type 后直调对应图；或按预置 Pipeline 串联多个 Agent，把前序的结构化输出注入后序的上下文。
    • 应用骨架 main.py：lifespan 启动时跑迁移、并行预热三个本地模型、驱动 MCP；再挂路由、配 CORS、暴露 /health。

    10.1.6 一条请求的完整生命周期¶

    把所有零件串起来，跟随第 7 章的「李明」（应聘 AI 大模型开发工程师）在统一助手里说一句技术问题，看请求怎么穿过三层：

    李明："什么是 RAG 的核心原理？"
   │
   ▼  集成层
[unified_chat] 前置拦截未命中 → LLM 路由（get_llm "intent"）判为 qa
   │           推 routing_decision 事件（"已转接到智能问答"）
   ▼  集成层
[orchestrator] 单 Agent 直达 → 懒加载 QA 图 → @with_retry 包裹调用
   │
   ▼  Agent 层（QA 图，RAG 范式）
[load_memory] 读 MemorySaver 历史（thread_id 定位）+ 摘要
[classify]    意图分类器（MiniLM, 5.9）判通用/专项
[retrieve]    BGE-M3 嵌入（5.4）→ Milvus 检索
[rerank]      BGE-Reranker（5.8）精排
[generate]    get_llm("qa") 增强生成 → 流式 token
   │
   ▼  地基层（全程复用）
   config / logger / exceptions / retry / llm_factory / memory
   │
   ▼  集成层
[unified_chat] 透传 progress + token + meta 事件 → SSE 流式返回
   │
   ▼
李明的屏幕：进度条 → 答案逐字浮现 → 引用来源

    这一条链路，同时用到了三层的几乎每一个零件。这就是"系统"二字的含义——不是某个 Agent 厉害，而是所有零件按依赖关系协作起来，对用户呈现为"说句话就有答案"。

    第 10 章 收尾（扩展） 全景回顾 + 能力迁移场景 + 面试题集

    章节总结¶

    • 三层架构：地基层（共用能力）→ Agent 层（四种范式）→ 集成层（统一调度），层层解耦
    • 四种范式：并行评审 / RAG / Human-in-the-Loop / 状态机+SSE，覆盖多 Agent 系统的主流控制流
    • 统一收敛：取模型走 get_llm、存记忆走 MemorySaver+thread_id、容错走 with_retry，是系统可维护的根基
    • 集成 = 接待员 + 调度台：unified_chat 听懂意图、orchestrator 派活执行、main 把一切装配起来
    • 一条请求穿三层：一个简单的技术提问，背后是三层几十个零件的协作

    你现在掌握的，不只是"做出了 EduAgent"，而是**搭建一个多 Agent 系统的完整方法论**：怎么分层、怎么选范式、怎么编排、怎么容错、怎么集成。这套方法论可以迁移到大量其它场景。

    下一节 10.2 多 Agent 能力迁移场景 给出若干个同样需要"多个专业 Agent 协同"的真实场景，每个都拆解成"由哪几个 Agent 构成、各对应你学过的哪种范式、怎么编排"——可以直接作为简历项目的构思起点。
