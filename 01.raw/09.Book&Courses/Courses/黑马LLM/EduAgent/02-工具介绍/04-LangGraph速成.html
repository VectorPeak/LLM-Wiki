    2.4 LangGraph 速成¶

    学习目标¶

    • 回顾并落地「Agent = 图」的心智模型：State、Node、Edge、Checkpointer
    • 掌握用 StateGraph 定义图、add_node 加节点、add_edge + START / END 连边、compile 编译
    • 掌握节点的写法：读 State → 返回「要更新的字段」
    • 掌握用 add_conditional_edges 实现条件分支（路由）
    • 掌握用 MemorySaver + thread_id 实现多轮记忆，理解 add_messages
    • 了解 interrupt / Command（人在环中，第六章详解）
    • 知道本项目的 LangGraph 规范与禁用写法

    ✅ 好消息：本节所有 demo 不需要大模型、不需要 API Key——我们把节点写成简单的 Python 逻辑，就能完整跑通一个 Agent 的骨架。这能让你专注于「图怎么搭、怎么跑」这件事本身。等你把骨架理解透了，第四章往节点里填大模型调用就水到渠成。

    LangGraph 是本项目的**绝对核心**，这一节请务必动手把每个例子敲一遍、跑一遍。

    2.4.1 回顾心智模型，以及本节要造什么¶

    回顾 1.2.4 讲过的心智模型：一个 Agent 就是一张图，由四要素构成——

    • State（状态）：所有节点共享的一份数据；
    • Node（节点）：一个函数，读 State、做事、返回要更新的内容；
    • Edge（边）：决定一个节点之后去哪（固定边 / 条件边）；
    • Checkpointer（检查点）：把 State 存下来，实现记忆与恢复。

    本节我们就用这四要素，从零搭一个「学习助手」Agent：它接收一个问题，先判断问题类型（概念题 / 代码题 / 闲聊），再根据类型走不同分支给出回应，最后还能记住多轮对话。我们会一步步把它搭起来，每一步都能运行。

    2.4.2 第一步：定义 State¶

    State 用一个 TypedDict 来定义——它就是规定「这张图里流动的数据有哪些字段」。我们的学习助手需要三个字段：

    from typing import TypedDict

class HelperState(TypedDict):
    question: str      # 用户的问题（输入）
    category: str      # 分类结果：concept / code / chat（中间结果）
    answer:   str      # 最终回应（输出）

    你可以把 State 理解成一张**贯穿全程的「工单」**：问题进来时填上 question，经过分类节点填上 category，经过回应节点填上 answer。每个节点都在这张工单上读取已有信息、补充新信息。

    2.4.3 第二步：写节点¶

    节点就是普通的 Python 函数，遵循一个**固定约定**：

    接收当前 State 作为参数，返回一个字典，字典里只包含「这个节点要更新的字段」。

    注意这个关键点：节点不直接修改传进来的 State，而是返回一个「增量更新」。LangGraph 会自动把你返回的字典合并进 State。没返回的字段保持原样。

    def classify_node(state: HelperState) -> dict:
    """分类节点：根据关键词判断问题类型"""
    q = state["question"]
    if "代码" in q or "报错" in q or "bug" in q:
        category = "code"
    elif "什么是" in q or "概念" in q or "原理" in q:
        category = "concept"
    else:
        category = "chat"
    return {"category": category}          # 只返回要更新的字段

def answer_concept_node(state: HelperState) -> dict:
    return {"answer": f"【概念解答】关于「{state['question']}」，它的核心思想是……"}

def answer_code_node(state: HelperState) -> dict:
    return {"answer": f"【代码助手】针对「{state['question']}」，我们一步步排查……"}

def answer_chat_node(state: HelperState) -> dict:
    return {"answer": "【闲聊】哈哈，没问题，我们继续聊～"}

    这就是为什么 2.2 学的 Pydantic、2.3 学的大模型调用能无缝融入：在真实项目里，节点函数内部会去调用大模型（await llm.ainvoke(...)）、查知识库，然后把结果 return {"字段": 结果}。本节为了聚焦图结构，节点里只写了简单的 Python 判断。

    2.4.4 第三步：搭图、编译、运行¶

    现在把节点连成一张图。先搭一个最简单的**直线图**（分类 → 概念解答 → 结束），把机制跑通：

    from langgraph.graph import StateGraph, START, END

builder = StateGraph(HelperState)          # ① 用 State 类型创建图构建器

builder.add_node("classify", classify_node)         # ② 注册节点（名字, 函数）
builder.add_node("answer",   answer_concept_node)

builder.add_edge(START, "classify")        # ③ 连边：START 是入口
builder.add_edge("classify", "answer")     #    分类后去回应
builder.add_edge("answer", END)            #    回应后结束（END 是出口）

graph = builder.compile()                  # ④ 编译成可执行的图

# ⑤ 运行：传入初始 State，拿回最终 State
result = graph.invoke({"question": "什么是装饰器", "category": "", "answer": ""})
print(result)

    输出：

    {'question': '什么是装饰器', 'category': 'concept', 'answer': '【概念解答】关于「什么是装饰器」，它的核心思想是……'}

    图的执行流向可以画成：

    START ──► classify ──► answer ──► END

    逐步理解这五步：

    1. StateGraph(HelperState)：创建一个「图构建器」，并告诉它图里流动的数据结构是 HelperState。
    2. add_node("名字", 函数)：把一个函数注册成图上的节点，并给它起个名字（后面连边时用这个名字引用）。
    3. add_edge(起点, 终点)：连一条固定的边。START 和 END 是 LangGraph 内置的特殊起点和终点——入口必须从 START 连出，出口必须连到 END。
    4. compile()：把搭好的图编译成一个真正能执行的对象。
    5. invoke(初始State)：从 START 开始执行，依次跑过各节点，每个节点的返回值被合并进 State，最后返回完整的最终 State。

    规范提醒：设置入口和出口，统一用 START / END 连边。旧教程里的 builder.set_entry_point(...) / builder.set_finish_point(...) 在本项目里**禁止使用**。

    （invoke 是同步版，方便我们在小脚本里直接跑。项目里在 FastAPI 异步环境中用的是异步版 await graph.ainvoke(...)，用法一致。）

    2.4.5 加分支：条件边¶

    上面的图永远走「概念解答」，没用上分类结果。真实 Agent 需要**根据 State 的值动态选择走哪条路**，这就是**条件边**。

    条件边需要两样东西：一个**路由函数**（读 State，返回一个字符串「路标」），和一张**路标 → 目标节点**的映射表。

    from langgraph.graph import StateGraph, START, END

def route_by_category(state: HelperState) -> str:
    """路由函数：返回一个字符串路标，决定下一步去哪个节点"""
    return state["category"]      # 返回 "concept" / "code" / "chat"

builder = StateGraph(HelperState)

builder.add_node("classify", classify_node)
builder.add_node("concept",  answer_concept_node)
builder.add_node("code",     answer_code_node)
builder.add_node("chat",     answer_chat_node)

builder.add_edge(START, "classify")

# 条件边：分类后，根据 route_by_category 的返回值选择目标节点
builder.add_conditional_edges(
    "classify",                  # 从哪个节点出发
    route_by_category,           # 路由函数
    {                            # 路标 → 目标节点 的映射
        "concept": "concept",
        "code":    "code",
        "chat":    "chat",
    },
)

builder.add_edge("concept", END)
builder.add_edge("code",    END)
builder.add_edge("chat",    END)

graph = builder.compile()

# 试三种不同的问题，观察走了不同分支
for q in ["什么是装饰器", "这段代码报错怎么办", "今天天气不错"]:
    result = graph.invoke({"question": q, "category": "", "answer": ""})
    print(f"问题：{q}\n  → 分类：{result['category']}　回应：{result['answer']}\n")

    输出：

    问题：什么是装饰器
  → 分类：concept　回应：【概念解答】关于「什么是装饰器」，它的核心思想是……

问题：这段代码报错怎么办
  → 分类：code　回应：【代码助手】针对「这段代码报错怎么办」，我们一步步排查……

问题：今天天气不错
  → 分类：chat　回应：【闲聊】哈哈，没问题，我们继续聊～

    现在的图长这样：

                        ┌──► concept ──┐
START ──► classify ─┼──► code ─────┼──► END
                    └──► chat ─────┘
              （由 route_by_category 决定走哪条）

    这正是 EduAgent 智能问答 Agent 的核心结构：先用一个分类节点判断问题类型，再用条件边把不同类型的问题分流到不同的处理路径。你现在已经掌握了它的骨架。

    2.4.6 加记忆：MemorySaver 与 thread_id¶

    到目前为止，每次 invoke 都是独立的，图记不住上一次聊了什么。要实现**多轮记忆**，需要两步：

    1. 编译时绑定一个 Checkpointer（本地用 MemorySaver），它负责在每次执行后把 State 存下来；
    2. 调用时传入一个 thread_id，作为「这是哪一段对话」的标识。相同 thread_id 的多次调用，会接续同一份记忆。

    为了演示「累积记忆」，我们让消息字段使用一个特殊机制 add_messages——它能让每次新消息**追加**到历史里，而不是覆盖：

    from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import HumanMessage, AIMessage

class ChatState(TypedDict):
    # Annotated[..., add_messages]：告诉 LangGraph 这个列表字段「追加」而非「覆盖」
    messages: Annotated[list, add_messages]

def reply_node(state: ChatState) -> dict:
    last_user_msg = state["messages"][-1].content        # 取最后一条用户消息
    history_count = len(state["messages"])               # 看看记住了几条
    reply = f"我收到了「{last_user_msg}」（当前历史共 {history_count} 条消息）"
    return {"messages": [AIMessage(content=reply)]}      # 返回的新消息会被「追加」

builder = StateGraph(ChatState)
builder.add_node("reply", reply_node)
builder.add_edge(START, "reply")
builder.add_edge("reply", END)

graph = builder.compile(checkpointer=MemorySaver())      # 绑定记忆

config = {"configurable": {"thread_id": "user-1"}}        # 同一对话的标识

graph.invoke({"messages": [HumanMessage(content="你好")]}, config)
result = graph.invoke({"messages": [HumanMessage(content="还记得我刚说了啥吗")]}, config)

for m in result["messages"]:
    print(f"{type(m).__name__}: {m.content}")

    输出：

    HumanMessage: 你好
AIMessage: 我收到了「你好」（当前历史共 1 条消息）
HumanMessage: 还记得我刚说了啥吗
AIMessage: 我收到了「还记得我刚说了啥吗」（当前历史共 3 条消息）

    看第二次调用：我们只传了一条新消息，但最终的 messages 里**累积了全部 4 条**（前两条来自第一轮）。这证明图确实**记住了上一轮对话**。关键就在两处：编译时的 checkpointer=MemorySaver()，和调用时相同的 thread_id。

    add_messages 在做什么？ 它是一个「合并规则」：默认情况下，节点返回 {"messages": [...]} 会**覆盖**原列表；而加了 Annotated[list, add_messages] 后，新消息会**追加**到历史末尾。这背后的「合并规则（Reducer）」机制，如果你想深入理解，可以看本节配套的拓展阅读《拓展：状态合并与 Reducer》——不看不影响主线。

    EduAgent 里的真实应用：四个 Agent 全部用 add_messages 管理对话消息；记忆通过 MemorySaver 实现，并按 Agent 类型隔离；thread_id 用 student_{学员ID}_session_{会话ID} 的格式拼成，确保每个学员的每段会话各记各的。这些我们会在后续章节实现。

    2.4.7 了解：interrupt 与 Command（人在环中）¶

    LangGraph 还有一个强大能力：让图**在某个节点中途「暂停」，等外部（比如老师）做出决定后再继续**。这就是「人在环中（HitL）」，用 interrupt() 暂停、用 Command(resume=...) 恢复。

    EduAgent 的试卷批改 Agent 正是用它实现「AI 批改完 → 暂停 → 等老师确认/修改 → 继续发布」的流程。这是相对进阶的内容，我们放到**第六章**结合真实业务详细讲解。本节你只需要知道「LangGraph 支持中途暂停等人介入」这件事即可。

    2.4.8 LangGraph 规范小结¶

    把本项目关于 LangGraph 的硬性规范汇总：

    用途 ❌ 禁用写法 ✅ 必用写法
    设置入口 / 出口 set_entry_point() / set_finish_point() add_edge(START, ...) / add_edge(..., END)
    快速创建 Agent create_react_agent（作为主要方式） 自己用 StateGraph 搭图
    节点更新状态 直接修改传入的 state 对象 返回「要更新的字段」字典
    多轮记忆 ConversationBufferMemory compile(checkpointer=...) + thread_id

    核心心法就一句：自己用 StateGraph 显式地把节点和边画出来，让流程清晰可控——这正是本项目选择 LangGraph 而非「一键式 Agent」的原因。

    章节总结¶

    本节我们亲手搭建了第一个能跑的 Agent 骨架，把 LangGraph 的核心机制走了一遍：

    • 四步套路：定义 State（TypedDict）→ 写节点（读 State、返回更新字段）→ 搭图（StateGraph + add_node + add_edge + START/END）→ compile 后 invoke。
    • 条件边：用 add_conditional_edges + 路由函数实现「根据 State 动态分支」——这是问答 Agent 的核心结构。
    • 记忆：compile(checkpointer=MemorySaver()) + 相同 thread_id 实现多轮记忆；add_messages 让消息追加而非覆盖。
    • 进阶预告：interrupt / Command 实现人在环中（第六章）。
    • 规范：统一用 START/END，节点返回增量更新，禁用旧版记忆与入口写法。

    到这里，你已经具备了「看懂、写出一张 LangGraph 图」的能力。这是整个项目最核心的技能——后面四个 Agent，无非是把节点里的简单逻辑换成「调用大模型 + 查知识库 + 打分」的真实业务。
