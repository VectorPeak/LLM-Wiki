    2.9 后台任务与异步上下文管理器（选读）¶

    这是一篇选读的拓展材料，对应主线 2.1.5 和 2.1.6 两节。如果你看完主线觉得「模板会用了，但不太懂为什么」，这篇会从最底层的概念帮你彻底搞明白。不读它完全不影响你继续学习项目主线——所以别有压力，学有余力再看。

    本文同样每段代码都可独立运行。

    学习目标¶

    • 搞懂「引用」和「垃圾回收」，从而理解后台任务「为什么会消失」
    • 搞懂「生成器」和 yield，从而理解 @asynccontextmanager 的工作原理

    第一部分：为什么后台任务会「消失」¶

    1.1 先搞懂「引用」：变量名是贴在对象上的标签¶

    在 Python 里，有一个非常重要、但初学者常常忽略的事实：变量名不是对象本身，而是贴在对象上的一张「标签」。

    a = [1, 2, 3]      # 创建了一个列表对象，并把标签 a 贴在它身上
b = a              # 又把标签 b 也贴在同一个列表上（不是复制）

    现在这个列表对象身上贴着两张标签：a 和 b。我们说这个对象有 2 个引用。

    a = None           # 撕掉标签 a（让 a 指向别的东西）
                   # 列表对象身上还剩 1 张标签 b，所以它还活着

    只要一个对象身上**还贴着至少一张标签（还有人引用它）**，它就安全。

    1.2 再搞懂「垃圾回收」：没人要的对象会被清理¶

    Python 会自动管理内存。它的规则简单到一句话：

    当一个对象身上一张标签都不剩了（没有任何变量引用它），Python 就认为它是「垃圾」，会在某个时刻把它从内存里清理掉。

    这个自动清理机制就叫**垃圾回收（Garbage Collection，简称 GC）。它平时是好事——你不用手动释放内存。但它有一个前提：**你得保证「还需要的东西」身上一直贴着标签。一旦你不小心让某个还在用的对象「没人引用」了，它就可能在你不注意时被清理掉。

    下面这段代码能让你直观看到「标签撕光后对象被回收」：

    class Cake:
    def __init__(self, name):
        self.name = name
    def __del__(self):                       # 对象被回收时，Python 会调用这个方法
        print(f"🗑️ 蛋糕「{self.name}」被回收了")

cake = Cake("草莓")          # 创建蛋糕，贴上标签 cake
print("蛋糕还在")
cake = None                  # 撕掉唯一的标签 → 没人引用了 → 触发回收
print("撕掉标签之后")

    输出：

    蛋糕还在
🗑️ 蛋糕「草莓」被回收了
撕掉标签之后

    看到了吗？一旦 cake = None 撕掉了唯一的标签，蛋糕对象立刻被回收。

    1.3 关键来了：事件循环不会替你「抓住」后台任务¶

    现在回到 asyncio.create_task。当你写：

    asyncio.create_task(grade_exam("EX-001"))

    这行代码创建了一个**后台任务对象**，并交给事件循环去调度执行。你可能以为「既然交给事件循环了，它肯定会帮我抓着这个任务直到跑完吧？」——并不会。

    Python 官方明确说明：事件循环对任务只持有「弱引用」。所谓弱引用，你可以理解成「它只是拿便利贴记了一下有这么个任务，但这张便利贴不算数、不能阻止任务被回收」。

    这意味着：如果你自己没有用一个普通变量（强标签）抓住这个任务对象，那么这个任务身上就只剩事件循环那张「不算数的便利贴」。在 GC 眼里，它约等于「没人要」，于是可能在它还没跑完的时候，就把它当垃圾清理掉了。

    结果就是主线 2.1.5 描述的那个隐蔽 bug：后台任务无声无息地消失，既不报错也不完成。 更可怕的是，这个 bug 时有时无（取决于 GC 什么时候触发），极难排查。

    1.4 解决方案：用一个集合「抓住」所有后台任务¶

    解法因此非常直白：自己用一个普通变量牢牢抓住任务，给它一张「算数的标签」。 项目里用的是一个模块级集合 set：

    import asyncio

_background_tasks = set()      # 这个集合就是「抓手」，给任务提供强引用

async def job():
    await asyncio.sleep(1)
    print("后台任务完成")

async def main():
    task = asyncio.create_task(job())
    _background_tasks.add(task)                        # ① 集合抓住任务 → 不会被回收
    task.add_done_callback(_background_tasks.discard)  # ② 任务跑完，把它从集合移除
    await asyncio.sleep(2)

asyncio.run(main())

    逐行理解这两个关键操作：

    • ① _background_tasks.add(task)：把任务放进集合，等于给它贴了一张「算数的标签」。只要它还在集合里，GC 就不会回收它，任务能安全跑到结束。
    • ② task.add_done_callback(_background_tasks.discard)：add_done_callback 的意思是「这个任务一旦跑完，就自动调用我给的这个函数」。这里给的是 集合.discard，作用是任务结束后**把自己从集合里删掉**。

    为什么还要第②步删掉它？因为如果只加不删，集合会随着任务越来越多而无限膨胀，内存泄漏。加了第②步，任务跑完就「功成身退」自动移除，集合始终只保留「正在运行中」的任务。

    一句话总结第一部分：后台任务不会自己活着，你必须用一个集合「抓住」它防止被垃圾回收（强引用），并在它跑完后让它自动「松手」（避免内存泄漏）。这就是主线那个三步模板的全部道理。

    第二部分：@asynccontextmanager 到底是什么魔法¶

    主线告诉你「yield 上面是启动、下面是关闭」。这一部分我们搞清楚**为什么**。

    2.1 起点：你早就用过的 with¶

    你很可能已经写过这样的代码：

    with open("data.txt", "w") as f:
    f.write("hello")
# 不用你手动调用 f.close()，离开 with 缩进块时文件会自动关闭

    with 的本质就是：进入时自动做一件「准备」的事，离开时自动做一件「收尾」的事。 这里准备 = 打开文件，收尾 = 关闭文件。这种「有头有尾、自动收尾」的东西，就叫**上下文管理器**。

    我们能不能自己写一个这样的上下文管理器？能，而且最简单的方式要先认识「生成器」。

    2.2 关键概念：生成器与 yield —— 一个能「暂停」的函数¶

    普通函数一旦 return 就彻底结束了。但有一种特殊函数，用 yield 代替 return，它能**执行到一半「暂停」，把值交出去，之后还能从暂停的地方「继续」往下跑**。这种函数叫**生成器**。

    def my_gen():
    print("A：第一段")
    yield                # 执行到这里「暂停」，把控制权交出去
    print("B：第二段")    # 等被要求「继续」时，才会执行这里

g = my_gen()             # 注意：此时函数体一行都还没执行！只是创建了生成器
print("=== 第一次 next ===")
next(g)                  # 让它跑到第一个 yield 处暂停 → 打印 A
print("=== 第二次 next ===")
next(g)                  # 让它从 yield 之后「继续」 → 打印 B

    输出：

    === 第一次 next ===
A：第一段
=== 第二次 next ===
B：第二段

    请仔细体会这个执行顺序：函数在 yield 处**停住**了，等到第二次 next(g) 才从 yield 之后**继续**。yield 就像一个「存档点」——程序跑到这里暂停存档，之后能从存档点恢复。

    有没有觉得眼熟？ 这正是上下文管理器需要的能力：「先做上半段（准备）→ 暂停 → ……（中间用户干活）→ 继续做下半段（收尾）」。

    2.3 把生成器变成上下文管理器：@contextmanager（同步版）¶

    Python 提供了一个装饰器 @contextmanager，能把「一个带 yield 的生成器」直接变成「一个能用于 with 的上下文管理器」。它的约定是：

    • **yield 之前**的代码 = 进入 with 时执行（准备）；
    • **yield 之后**的代码 = 离开 with 时执行（收尾）。
    from contextlib import contextmanager

@contextmanager
def managed_resource():
    print("【准备】打开资源")     # 进入 with 时执行
    yield "资源对象"              # 把 yield 的值交给 as 后面的变量
    print("【收尾】关闭资源")     # 离开 with 时执行

with managed_resource() as res:
    print(f"正在使用：{res}")

    输出：

    【准备】打开资源
正在使用：资源对象
【收尾】关闭资源

    到这里，「yield 上面是准备、下面是收尾」这句话的原理就完全清楚了：with 进入时把生成器跑到 yield 暂停（执行了上半段准备），缩进块里的代码是「中间用户干活」，缩进块结束时再让生成器从 yield 继续（执行下半段收尾）。

    2.4 异步版：@asynccontextmanager¶

    现在只剩最后一步。当「准备」和「收尾」里包含**异步操作**（比如异步连接数据库、异步预热模型）时，我们就需要异步版本：

    • 装饰器换成 @asynccontextmanager；
    • 函数前面加 async；
    • 使用时从 with 换成 async with。

    其余的「yield 上面是准备、下面是收尾」规则**一模一样**。

    import asyncio
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan():
    print("【启动】异步加载模型 / 连接数据库")    # yield 之前 = 启动
    await asyncio.sleep(0.5)                       # 这里可以写异步操作
    yield
    print("【关闭】异步释放资源")                  # yield 之后 = 关闭

async def main():
    async with lifespan():
        print("应用运行中……")

asyncio.run(main())

    输出：

    【启动】异步加载模型 / 连接数据库
应用运行中……
【关闭】异步释放资源

    这和主线 2.1.6 的例子是同一个东西，只是现在你知道它背后是「生成器在 yield 处暂停 / 恢复」的机制了。

    一句话总结第二部分：@asynccontextmanager 借助生成器「能暂停能恢复」的能力，把「启动逻辑」和「关闭逻辑」用一个 yield 一分为二——上半段在进入时跑，下半段在退出时跑。EduAgent 的 main.py 正是用它来管理「应用启动预热」和「应用关闭清理」。

    总结¶

    这篇拓展材料补齐了主线里两个「先会用、后理解」的知识点：

    • 后台任务为什么会消失：因为事件循环只对任务持「弱引用」，不能阻止垃圾回收。你必须用一个集合给任务提供「强引用」抓住它，并在跑完后移除以防内存泄漏——这就是三步模板的原理。
    • @asynccontextmanager 是什么魔法：它建立在「生成器能在 yield 处暂停 / 恢复」之上，把启动与关闭逻辑用 yield 一分为二。我们从同步 with → 生成器 → @contextmanager → @asynccontextmanager 一路推了过来。

    理解了这两点，你对异步编程的认识就比「只会套模板」深了一层。现在可以放心回到主线，继续学习 2.2 Pydantic 速成。
