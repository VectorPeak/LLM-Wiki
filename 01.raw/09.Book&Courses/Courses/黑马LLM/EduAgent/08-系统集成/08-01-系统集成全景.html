    8.1 系统集成全景¶

    学习目标¶

    • 理解为什么需要 Orchestrator：把四个独立 Agent 拧成一个系统
    • 掌握统一入口的请求生命周期：前置拦截 → LLM 路由 → 分发执行
    • 区分两种执行模式：单 Agent 直达 与 多 Agent 串联 Pipeline
    • 厘清本章每个零件「在前面哪一章已经造好」，本章只做装配

    8.1.1 前四章造了什么，这一章做什么¶

    到第 7 章为止，我们已经把四个 Agent 各自从零实现了一遍，每个 Agent 演示一种 LangGraph 范式：

    Agent 范式 章节 入口接口
    简历审查 并行评审（六维度 fan-out/fan-in） 第 4 章 POST /resume/...
    智能问答 RAG（检索增强 + 记忆） 第 5 章 POST /qa/...
    试卷批改 Human-in-the-Loop（interrupt/resume） 第 6 章 POST /exam/...
    模拟面试 状态机 + SSE（多轮对话） 第 7 章 POST /interview/...

    但它们现在是**四个互不相干的接口**。学员要用，得自己知道"问技术问题去 /qa、批改去 /exam、面试去 /interview"——这把"判断该用哪个功能"的负担丢给了用户。

    第 8 章做的事只有一句话：在四个 Agent 前面架一个统一入口，用户只管说一句话，系统自动判断该路由到哪个 Agent（或哪几个 Agent 串联），再把结果以统一格式返回。

    💡 关键认知：本章几乎不"造新轮子"。Orchestrator 调用的四个 Agent 图（build_*_graph）、异常体系、重试降级、LLM 工厂、MCP 工具、本地模型——全部在前面章节已经实现。本章的工作是**装配**：把这些零件接到一个统一入口和一个 main.py 上。下面 8.1.6 会逐件标注来源。

    8.1.2 两个核心角色¶

    系统集成由两个核心文件承担，职责分明：

    文件 角色 一句话职责
    backend/api/v1/unified_chat.py 统一入口 面向用户：收一句话 → 判断意图 → 用 SSE 流式返回（路由卡片 / 引导 / 答案）
    backend/core/orchestrator.py 编排器 面向 Agent：拿到明确的 agent_type → 直调对应 Agent 图，或按序串联多个 Agent

    简单说：统一入口负责"听懂用户要什么"，编排器负责"把活派给对的 Agent"。前者是"接待员"，后者是"调度台"。

    8.1.3 统一请求生命周期¶

    用户在统一助手里发一句话，会经历下面这条流水线（全程 SSE 流式，前端边收边渲染）：

                              用户一句话
                              │
                  ┌───────────▼────────────┐
                  │ POST /api/v1/chat/stream │   unified_chat.py
                  └───────────┬────────────┘
                              │
   ① 规则前置拦截 _pre_filter ── 命中五类社交/元场景 ──→ 零 Token 模板回复 → done
      （你好 / 谢谢 / 再见 / 你是谁 / 你能做什么）            （完全不调 LLM）
                              │ 未命中
                              ▼
   ② LLM 路由 _llm_route（DeepSeek 判 6 类意图，无本地分类模型）
                              │
                              ▼
   ③ 推送 routing_decision 事件（前端显示"已路由到 XXX"卡片）
                              │
        ┌──────────────┬──────┴───────────┬──────────────┐
        ▼              ▼                  ▼              ▼
       qa          exam / resume       multi_agent     clarify
   单 Agent 流式      / interview       求职全链路计划      意图不明
   执行 QA 图       引导跳转对应页面     （resume→interview） 追问澄清
        │              │                  │              │
        ▼              ▼                  ▼              ▼
   token 流 + meta   guidance 事件      pipeline_plan    guidance 事件
                              │
                              ▼
                          done 事件

    每一步对应一种 SSE 事件类型，前端据此渲染不同 UI：

    事件类型 何时推送 前端表现
    routing_decision LLM 路由判完 顶部"已为你转接到【智能问答】"卡片
    progress QA 各节点开始（检索/精排…） "检索知识库中..."进度条
    token QA 生成时逐字 答案气泡逐字打出
    meta QA 答完 答案模式 / 引用来源
    guidance exam/resume/interview/clarify 引导卡片（含"前往 XX"按钮）
    pipeline_plan multi_agent 多步骤计划卡片（按序点击）
    done 流结束 结束信号
    error 异常 错误提示

    8.1.4 两种执行模式：单 Agent vs 多 Agent 串联¶

    编排器（Orchestrator）对外只有一个入口 handle(request)，内部分两种模式：

      Orchestrator.handle(AgentRequest)
              │
        pipeline_mode?
         ┌────┴─────┐
         否          是
         ▼           ▼
   _run_single   _run_pipeline
     _agent       按序跑多个 Agent
         │        前序 structured_output
         │        自动注入后序 context
   @with_retry         │
   调对应 Agent 图       ▼
         │        _aggregate_pipeline
         ▼        聚合各步结果
              │
              ▼
       AgentResponse（统一出参）

    单 Agent 直达：最常见。_run_single_agent 直接调目标 Agent 的 LangGraph 图，用 @with_retry 包一层自动重试降级（来自 3.5），从最终 State 提取响应，封成统一的 AgentResponse。

    多 Agent 串联 Pipeline：把几个 Agent 按固定顺序跑，前一个的结构化输出喂给后一个。源码里预置了两条 Pipeline：

    Pipeline key 顺序 场景
    job_preparation 简历审查 → 模拟面试 求职全链路：先审简历，把简历结果作为面试的背景
    code_deep_review 试卷批改 → 智能问答 代码深度复盘：批改后针对薄弱点深入讲解

    📎 一个容易混淆的点（8.5 会细讲）：统一入口的 multi_agent 分支**不会**真的把 Pipeline 一口气跑完，它只推一个 pipeline_plan（步骤计划）让前端引导用户**按步点击**。而编排器的 _run_pipeline 才是**程序化**地一次跑完多个 Agent（由"强制 Pipeline"的请求触发）。两条路径并存，服务不同的交互需求——一个是"给你规划好让你自己走"，一个是"我一次帮你跑完"。

    8.1.5 为什么意图路由用 LLM 而不是本地分类模型¶

    判断"用户这句话该路由到哪个 Agent"是一个文本分类问题。一种常见做法是训练/部署一个本地小模型（如 MiniLM）做多分类。本项目**没有这么做**，而是直接让 DeepSeek 判断（get_llm("intent")，温度 0，返回 JSON 标签）。

    原因很实在：

    • 调用频率低：只有统一入口这一个地方触发路由，不是每个 Agent 内部的高频操作，一次 LLM 调用的开销完全可接受。
    • 省一个本地模型：不必额外加载、维护一个分类模型，部署更轻。
    • 更灵活：要新增一类意图，改 Prompt 即可，不用重训模型。

    异常兜底也简单：LLM 路由失败（超时 / JSON 解析失败）就**降级回 qa**，不阻断 SSE 流——大不了当成普通技术问答处理，用户体验不断线。

    8.1.6 本章零件来源对照（重点）¶

    本章装配用到的零件，绝大多数在前面章节已经造好。理解这张表，就理解了"集成"二字的含义——集成不是重写，是连线：

    零件 在哪一章造的 本章怎么用
    四个 Agent 图 build_*_graph 第 4 / 5 / 6 / 7 章 Orchestrator 懒加载后直调
    异常体系 exceptions.py 3.3 Orchestrator 捕获 AgentExecutionError/PipelineError 等
    重试降级 retry.py（with_retry / 三层兜底） 3.5 _run_single_agent 用 @with_retry 包裹
    LLM 工厂 get_llm（含 "intent" 配置） 3.4 路由判断、QA 流式都靠它
    MCP 工具（知识库 / 联网搜索 Server） 5.11 main.py 把它们 mount 进 FastAPI
    本地模型（reranker / 意图分类器 / BGE-M3 嵌入） 5.8 / 5.9 / 5.4 main.py 启动时并行预热
    DB 迁移 run_migrations 第 3 章（数据库） main.py lifespan 启动时执行
    认证 / 依赖注入 get_current_user 3.6 统一入口、各端点鉴权

    章节总结¶

    • 集成的本质：四个 Agent 已各自实现，本章在它们前面架统一入口 + 编排器，用户只说一句话，系统自动路由
    • 两个角色：unified_chat.py（接待员，听懂意图）+ orchestrator.py（调度台，派活给 Agent）
    • 请求生命周期：规则前置拦截（零 Token）→ LLM 路由（6 类意图）→ 按分支分发（qa 流式 / 引导跳转 / pipeline 计划 / 澄清）
    • 两种执行模式：单 Agent 直达（最常见）vs 多 Agent 串联 Pipeline（前序输出注入后序）
    • 集成 = 连线：异常、重试、LLM 工厂、MCP、本地模型全是前面章节造好的零件，本章只做装配
