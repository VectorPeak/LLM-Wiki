    5.6 Hybrid 召回与 WeightedRanker¶

    学习目标¶

    • 理解为什么要同时做稠密检索（Dense）和稀疏检索（Sparse），各自解决什么问题
    • 理解 WeightedRanker 与 RRFRanker 的区别，知道本项目为什么选前者
    • 用 AnnSearchRequest 构造双路检索请求，理解每个参数的含义
    • 实现 KnowledgeBaseClient._hybrid_search()，返回召回候选列表

    💡 本节实现图中的 retrieve 节点的底层召回能力。 召回解决"从几百万个 chunk 里找出最相关的几十个"。找出来之后，下一节（5.7）的 Reranker 再对这几十个做精细打分，最终选出最好的 3 条。

    5.6.1 为什么要混合检索¶

    单独用稠密向量（Dense）或稀疏向量（Sparse）各有短板：

    只用 Dense（语义检索）的问题

    语义检索靠向量相似度，能理解同义词和语义关联，但遇到精确术语时可能失效。例如：

    查询："NullPointerException 怎么处理"
稠密检索召回："Java 空指针异常解决方案"   ← 语义相似，能召回 ✓
稠密检索遗漏："NPE 排查步骤"              ← 因为向量距离稍远，可能漏掉 ✗

    只用 Sparse（关键词检索）的问题

    稀疏检索靠词频权重，精确匹配 token，但无法理解语义变体：

    查询："怎么防止内存溢出"
稀疏检索遗漏："JVM 堆内存管理"            ← 没有相同 token，召回不到 ✗

    混合检索：两路并行，取长补短

    Dense 路负责语义理解，Sparse 路负责精确词匹配，两路结果用 WeightedRanker 加权融合，兼顾两者的优势。BGE-M3 天然支持同一个 Query 同时输出 dense 向量和 sparse 向量，不需要额外调用。

    5.6.2 WeightedRanker vs RRFRanker：选哪个¶

    MilvusClient.hybrid_search() 提供两种融合策略：

    RRFRanker（倒数排名融合）

    score = Σ  1 / (k + rank_i)      k 默认 60，rank_i 是该文档在第 i 路检索中的排名
    • 只看**排名**，不看原始分数；Dense 第 1 名和 Sparse 第 1 名权重完全相同
    • 两路之间没有轻重之分
    • 优点：鲁棒，不受原始分数量纲影响
    • 缺点：无法表达"语义相似度比关键词匹配更重要"的业务意图

    WeightedRanker（加权平均分）

    score = w_dense × score_dense_norm + w_sparse × score_sparse_norm
        各路分数先 min-max 归一化，再按权重加权
    • 可以指定 Dense 和 Sparse 各自的**权重比例**
    • WeightedRanker(0.7, 0.3) = Dense 占 70%、Sparse 占 30%

    本项目选 WeightedRanker(0.7, 0.3) 的原因：

    课程问答以语义性问题为主（"为什么要用 IOC？"、"AOP 和代理模式有什么关系？"），语义检索应该主导。但技术问答里偶尔出现精确的 API 名称、报错信息，稀疏检索不能完全忽视。7:3 在实践中效果较好，可按实际场景调整。

    WeightedRanker 的权重影响的是两路结果的**合并排序**，不影响各自的召回集合。两路 AnnSearchRequest 分别独立执行，Milvus 拿到两路结果后才做加权融合。

    5.6.3 实现 _hybrid_search()¶

    # backend/core/knowledge_base.py（追加到 KnowledgeBaseClient，接 5.5 写入方法之后）

from typing import Optional
from pymilvus import MilvusClient, DataType, AnnSearchRequest, WeightedRanker

    # ── 检索配置 ─────────────────────────────────────────────
    VECTOR_TOP_K = 10    # Hybrid 召回的候选数量，传给 Reranker 精排
    ANN_EF       = 64    # HNSW 搜索时候选集大小（精度/速度平衡点）

    def _hybrid_search(
        self,
        query_embedding: list[float],
        query_sparse: dict,
        top_k: int,
        filters: Optional[str] = None,
    ) -> list[dict]:
        """
        对 knowledge_domain 做 Hybrid 检索（Dense + Sparse → WeightedRanker 融合）。

        两个 AnnSearchRequest 分别构造 Dense 和 Sparse 检索请求，
        由 Milvus 在服务端并行执行后，用 WeightedRanker 加权融合排序。

        Args:
            query_embedding: Dense Query 向量（1024 维，来自 encode_query）
            query_sparse:    Sparse Query 向量（{token_id: weight}，来自 encode_query）
            top_k:           每路召回数量（融合后同样取 top_k）
            filters:         Milvus bool 表达式，如 'tenant_id == "xxx"'

        Returns:
            候选文档列表，每项含 "content" / "score" / "metadata"。
            score 是 WeightedRanker 的加权排序信号，不是概率，
            直接交给 5.7 节的 Reranker 做精细打分。
        """
        try:
            # ── Dense ANN 检索请求 ─────────────────────────────────────
            # COSINE 度量匹配 BGE-M3 dense 向量（L2 归一化后等价于余弦相似度）
            # ef=64：HNSW 搜索时的候选集大小，越大精度越高，64 是精度/速度平衡点
            dense_req = AnnSearchRequest(
                data=[query_embedding],
                anns_field="embedding",
                param={
                    "metric_type": "COSINE",
                    "params": {"ef": self.ANN_EF},
                },
                limit=top_k,
                expr=filters,
            )

            # ── Sparse 关键词检索请求 ──────────────────────────────────
            # IP（内积）是 BGE-M3 lexical_weights 的标准度量
            sparse_req = AnnSearchRequest(
                data=[query_sparse],
                anns_field="sparse_embedding",
                param={"metric_type": "IP"},
                limit=top_k,
                expr=filters,
            )

            output_fields = [
                "content", "source_name", "chunk_type",
                "course_id", "document_id", "chunk_index",
            ]

            # ── WeightedRanker(0.7, 0.3) ──────────────────────────────
            # 第一个权重对应第一个请求（Dense），第二个对应第二个请求（Sparse）
            # 两路结果在 Milvus 服务端并行检索，融合后返回
            results = self._client.hybrid_search(
                collection_name=COLLECTION_NAME,
                reqs=[dense_req, sparse_req],
                ranker=WeightedRanker(0.7, 0.3),
                limit=top_k,
                output_fields=output_fields,
            )

            # ── 解析结果 ───────────────────────────────────────────────
            # MilvusClient 的 hybrid_search 结果用 distance 字段存融合后的分数
            # 这个分数是排序信号，不是概率，不做任何额外处理，直接传给 Reranker
            candidates = []
            for hit in results[0]:
                candidates.append({
                    "content": hit.get("content") or "",
                    "score":   hit.get("distance") or 0.0,
                    "metadata": {
                        "source_name": hit.get("source_name") or "",
                        "chunk_type":  hit.get("chunk_type")  or "text",
                        "course_id":   hit.get("course_id")   or "",
                        "document_id": hit.get("document_id") or "",
                        "chunk_index": hit.get("chunk_index") or 0,
                    },
                })

            logger.info(
                "knowledge_base.hybrid_search_done",
                candidates=len(candidates),
            )
            return candidates

        except Exception as e:
            logger.error("knowledge_base.hybrid_search_failed", error=str(e))
            return []

    @staticmethod
    def _build_filter(tenant_id: str, course_id: Optional[str] = None) -> str:
        """
        构建 Milvus bool 过滤表达式。
        对 tenant_id / course_id 做转义，防止 filter 表达式注入。
        """
        safe_tenant = tenant_id.replace('"', '\\"')
        expr = f'tenant_id == "{safe_tenant}"'
        if course_id:
            safe_course = course_id.replace('"', '\\"')
            expr += f' and course_id == "{safe_course}"'
        return expr

    distance 字段说明：MilvusClient 的 hybrid_search 结果沿用向量搜索的命名惯例，用 distance 存融合后的分数（不是"距离"的本义）。

    5.6.4 数据流：_hybrid_search() 的输入与输出¶

    encode_query(query)                      ← 5.4 节 BGEMEmbedder
    ├── dense   = [0.12, -0.34, ..., 0.45]   （1024 维浮点向量）
    └── sparse  = {2003: 0.15, 8471: 0.09, ...}  （稀疏字典）
         │
         ▼  _hybrid_search(dense, sparse, top_k=10, filters=...)
    ┌──────────────────────────────────────────────────────┐
    │  Milvus knowledge_domain                             │
    │    AnnSearchRequest(dense, COSINE, ef=64) ──┐        │
    │    AnnSearchRequest(sparse, IP)             ├─► WeightedRanker(0.7, 0.3)
    │                                             │   Top-10 候选            │
    └──────────────────────────────────────────────────────┘
         │
         ▼  返回 list[dict]（10 条候选，含 content / score / metadata）
         │  score = WeightedRanker 加权排序信号（不是概率）
         │
         ▼  → 传给 5.7 节 BGEReranker 精排，得到 Top-3 + 置信度

    章节总结¶

    • 混合检索的价值：Dense 负责语义理解，Sparse 负责精确词匹配，两路并行互补
    • WeightedRanker(0.7, 0.3)：课程问答语义为主，Dense 权重更高；两路在 Milvus 服务端并行执行，融合只影响排序
    • _hybrid_search()：用两个 AnnSearchRequest 构造双路请求，distance 字段是 WeightedRanker 的排序信号，不是概率
    • 输出是原始候选：Hybrid 召回的 10 条候选列表直接传给下一节的 Reranker，不做任何质量判断

    下一节 5.7 重排序（Reranker） 实现 reranker.py：BGEReranker CrossEncoder 直接输出 [0,1] 置信度，并在同一文件实现 retrieve() Pipeline 函数，将 _hybrid_search() 和精排串成一步，retrieve_node 直接调用。
