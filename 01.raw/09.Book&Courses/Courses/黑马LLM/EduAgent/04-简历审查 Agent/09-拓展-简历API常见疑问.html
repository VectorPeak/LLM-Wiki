    04-8 拓展：简历 API 常见疑问答疑（resume.py）¶

    这份文档收集了 backend/api/v1/resume.py 一带最容易卡住的问题——既有同学实际问过的，也有从初学角度预判的。遇到困惑时按目录找对应条目即可。涉及的代码都在 04-8。

    目录¶

    • 一、先搞清楚：这个文件是干嘛的
    • 二、HTTP 接口基础（装饰器 / 状态码 / 鉴权 / 文件上传 / 异常）
    • 三、异步与后台任务（重点）
    • 四、数据库相关
    • 五、State 与字段

    一、先搞清楚：这个文件是干嘛的¶

    Q：resume.py 到底是什么？它和我写的那个简历 Agent 是什么关系？

    resume.py 是**后端的 HTTP 接口层**——它把你写好的简历 Agent"包装成"几个网址（接口），让外界能通过 HTTP 来调用。

    前端（或 curl / Postman）永远不直接碰那个 Agent，它们之间只通过 HTTP 请求/响应交流：

    前端                      后端(resume.py)              简历Agent(graph)
 │  POST /resume/upload    │                              │
 ├────────────────────────>│  存文件、写库、后台启动 ────>│ (后台跑30-60s)
 │  <── 202 {review_id} ───┤                              │
 │  GET /reviews/{id}(轮询) │                              │
 ├────────────────────────>│  查库 → 返回状态/结果         │

    后端做四件事，对应四个接口：上传、查询、删除、列表。

    二、HTTP 接口基础¶

    Q：@router.post("/upload", status_code=202) 这一行是什么？

    @router.post(...) 是个**装饰器**，意思是"下面这个函数负责处理 POST /resume/upload 这个请求"。status_code=202 指定**默认返回的 HTTP 状态码**是 202。

    状态码是后端告诉前端"这次请求结果如何"的标准数字。常见的： - 200 OK：成功并有结果 - 202 Accepted：已接受、正在处理（还没结果）—— 上传接口用它，因为审查在后台 - 204 No Content：成功但无返回内容 —— 删除用它 - 400 Bad Request：你传的东西不对（如非 PDF） - 401 Unauthorized：没登录 / token 无效 - 404 Not Found：找不到（如不存在的 review_id） - 413 Payload Too Large：文件太大

    Q：current_user: dict = Depends(get_current_user) 是什么？前端怎么"登录"？

    这是 FastAPI 的**依赖注入 + 鉴权**机制。它声明"调这个接口必须先登录"。

    流程是这样：前端先调登录接口（/login，3.6）拿到一个 JWT token（一串加密字符串，代表"我是谁"）；之后每次调接口，都在请求头里带上 Authorization: Bearer <token>。get_current_user 负责验证这个 token、解出"是哪个用户"，塞进 current_user（含 user_id、tenant_id）。token 无效或没带 → 直接抛 401，函数体根本进不去。

    简单说：token 就像门禁卡，登录时领卡，之后每次进门刷一下。Depends(get_current_user) 就是门口的刷卡机。

    Q：file: UploadFile = File(...) 是什么？前端怎么把文件传过来的？

    声明"我要接收一个上传文件"。前端用 multipart/form-data 格式把文件传过来（curl 里就是 -F "file=@简历.pdf"），FastAPI 自动把它解析成一个 UploadFile 对象。File(...) 里的 ... 表示**必填**（不传就报错）。

    Q：raise HTTPException(status_code=400, detail="仅支持 PDF 格式") 是什么？

    HTTPException 是 FastAPI 的标准报错方式。raise 它，FastAPI 会自动把它变成一个 {"detail": "仅支持 PDF 格式"} 的 400 响应返回给前端，函数后面的代码不再执行。比手动 return 一个错误更规范。

    Q：客户端 client.post(...) 的参数，怎么对应到服务端函数的参数？（重要）

    先破除一个误区：客户端的 client.post(...) 不是在"直接调用"服务端那个 Python 函数——它俩是两个程序，中间隔着 HTTP。客户端只是"拼一个 HTTP 请求"发出去，服务端 FastAPI 收到后，自己把函数参数一个个填好。所以不是"对齐参数名"，而是"请求的不同部位被分配到不同参数上"。

    以上传为例，服务端 upload_resume(file, current_user) 的两个参数来自请求的两个不同部位：

    客户端 client.post(...)                       服务端 upload_resume(...)
─────────────────────────────────────────────────────────────────────
"/resume/upload"           ──路由──►  决定调用哪个函数

files={"file": (...)}      ─────────►  file: UploadFile = File(...)
        ↑ 键叫 "file"                   ↑ 参数也叫 file —— 靠这个名字对上

headers={"Authorization":  ─────────►  current_user = Depends(get_current_user)
         "Bearer <token>"}             ↑ 依赖函数从这个 header 读 token、解出用户

    两个要点： - file 是对齐的，靠 files 字典的"键"：files={"file": ...} 的键 "file" 必须和参数名 file 一致；写成 files={"resume": ...} 服务端就找不到、报 422。 - current_user 客户端没传，是服务端算的：客户端只给了 headers 里的 token，Depends(get_current_user) 让服务端现场从 header 读 token、解出用户。所以它不该出现在客户端调用里。

    那个 files 的值 (文件名, f, "application/pdf") 是三元组：文件名（file_path.split("/")[-1] 取路径最后一段）、文件内容、MIME 类型。

    通用规律——客户端哪部分 → 服务端哪种参数：

    服务端参数声明 来自请求的 客户端怎么传（httpx）
    路由 {review_id} + review_id: str URL 路径 拼进 URL：/reviews/abc-123
    q: str（普通类型） 查询串 ?q= params={"q": "..."}
    Pydantic 模型 / body 请求体 JSON json={...}
    x: str = Form(...) 表单字段 data={"x": "..."}
    file: UploadFile = File(...) 上传文件 files={"file": (...)}（键要对上）
    x: str = Header(...) 请求头 headers={"x": "..."}
    x = Depends(某函数) 服务端自己算 不直接传，只给依赖要的东西（如 token）

    记住：带 Depends(...) 的参数，客户端永远不直接传——它是服务端现场算出来的。

    三、异步与后台任务（重点）¶

    Q：这个文件为什么全是 async def 和 await？

    因为后端要**同时处理很多请求**。async/await 让一个请求在"等数据库""等读文件"这种 I/O 时，让出 CPU 去处理别的请求，而不是干等。回顾 2.1——这就是异步的意义：不阻塞、高并发。凡是会"等"的操作（查库、读文件）前面都加 await。

    Q：asyncio.Task 是什么？什么时候用？

    Task 是**一个"正在后台跑的协程"的句柄（把手）**。

    打个比方——你在餐厅点菜： - 写一个 async def 协程 = "一道菜的做法" - 直接 await 它 = "站在窗口等菜做好才走" - asyncio.create_task(协程) = "把单子递进后厨，后厨立刻开做，给你一张**取餐号**，你拿号就去找座位了"

    这张取餐号就是 Task。当你想让某件事和当前代码并行跑、而不是卡着等它的时候，就用它。

    Q：task = asyncio.create_task(graph.ainvoke(...)) 为什么不直接 await？

    这是整个异步设计的核心。对比：

    # ❌ 如果直接 await：函数会卡住 30-60 秒，等审查全跑完才返回
await graph.ainvoke(initial_state)
return {"review_id": ...}        # 前端要干等一分钟

# ✅ 实际用 create_task：审查丢后台跑，函数立刻返回
task = asyncio.create_task(graph.ainvoke(initial_state))
return {"review_id": ..., "status": "processing"}   # 前端秒收到回应

    await = 等它做完再继续；create_task = 让它后台跑，我马上继续。 上传接口要立刻返回 review_id（202 + 轮询模式），所以**不能等**，必须用 create_task。

    注意：graph.ainvoke(...) 写出来只是"一道菜的做法"（一个协程对象），它本身**不会自己开跑**——await 它或 create_task 它才会真正执行。

    Q：下面这三行是固定套路吗？看不懂后两行。

    task = asyncio.create_task(graph.ainvoke(initial_state))   # ①启动
_background_tasks.add(task)                                 # ②攥住引用
task.add_done_callback(_on_task_done)                       # ③挂收尾回调

    是的，这是 asyncio"丢一个后台任务"的标准三件套，可当固定模板记。

    • ① create_task：启动后台任务、拿到句柄（取餐号）。
    • ② _background_tasks.add(task) —— GC 保护：create_task 之后，asyncio 内部只用**弱引用**记着这个任务。如果代码里不拿变量"攥住"它，垃圾回收可能在它跑完前就把它清掉（后厨的活儿凭空消失）。所以塞进一个模块级集合 _background_tasks 攥牢。这是 Python 官方文档建议的写法。
    • ③ task.add_done_callback(_on_task_done) —— 注册完成回调：意思是"这个任务一结束（成功/出错/被取消），自动调用 _on_task_done 函数"。你不用盯着，它自己触发。回调里做收尾：从集合移除任务（松手）、删临时文件、任务崩了就把记录标 failed。

    比方：add_done_callback 就是"这桌菜出餐后，后厨自动做的收尾——把订单从待办板擦掉、清理灶台"。你点完菜走人，善后它自己干。

    Q：为什么上传响应里看不到审查结果，只有 review_id？

    因为上传是 202 + 后台异步：审查任务被丢到后台就**立刻返回**了（不等 30-60 秒），所以响应里只有 review_id。真正的报告是后台任务跑完后**写进数据库**的。你要拿 review_id 去**轮询查询接口** GET /resume/reviews/{review_id}，等它从 processing 变 done，才能看到报告。

    Q：那我上传拿到 review_id，过 60 秒再单独查一次，行不行？

    行，但有个关键前提：那 30-60 秒里，跑后台任务的进程必须一直活着。

    • 跑**真实服务器**（uvicorn backend.main:app，常驻进程）→ ✅ 成立。服务器一直活着、任务跑完，60 秒后你单独查就能看到 done。
    • 跑**测试脚本**（asyncio.run(...) 上传完就退出）→ ❌ 不行。进程一退出，后台任务就被取消，记录永远卡 processing。

    所以要么在脚本里轮询（让脚本别退出），要么干脆起一个真实服务器，再上传 + 等 + 单独查。

    四、数据库相关¶

    Q：async with AsyncSessionLocal() as session 是什么？

    开一个**异步数据库会话**（回顾 2.7 / 3.6）。async with 保证用完自动关闭、归还连接。所有查库都在这个 session 里做，最后 await session.commit() 提交。

    Q：SQL 里的 :review_id 是什么？为什么不直接把值拼进字符串？

    :review_id 是**参数占位符**，真正的值通过后面的字典 {"review_id": review_id} 传入。这叫**参数化查询**，作用是**防 SQL 注入**——绝不能用 f"... WHERE id='{review_id}'" 这种字符串拼接，否则别人传个恶意字符串就能攻击你的数据库。

    Q：为什么查询/删除都要 WHERE ... AND student_id = :student_id？

    越权防护。加上 AND student_id，就保证"只能查/删自己的记录"。否则别人知道你的 review_id 就能看你的简历报告、删你的记录。

    Q：写 JSONB 要 json.dumps，读出来却不用 json.loads，为什么不一致？

    • 写：State 里是 Python dict，往 JSONB 列写要先 json.dumps 转成 JSON 字符串（4.7）。
    • 读：从 JSONB 列读出来时，asyncpg 驱动已经自动把它反序列化成 Python dict/list 了，所以不用再 json.loads。

    读和写方向相反，所以一个要手动序列化、一个自动反序列化。get_review 里那个 _to_dict 就是个容错：万一拿到的还是字符串才 json.loads，否则直接用。

    五、State 与字段¶

    Q：initial_state 里 "messages": [] —— 真实运行就是空的吗？还是测试占位？

    是**真实的空**，不是测试占位。messages 是 LangGraph 里"对话消息"通道，多轮聊天类 Agent 才用。但**简历审查是一次性流水线、没有对话**，8 个节点没有任何一个读写 messages，所以它从头到尾都是空的。

    保留它只是因为 ResumeState 声明了这个字段（通用模板习惯）。到第五章的问答 Agent，messages 才真正用来存多轮对话历史。

    Q：为什么数据库写 pdf_minio_path，State 里却用 pdf_local_path、minio 留空？

    这俩都是"文件存哪儿"的路径，但对应两种存储： - pdf_minio_path = 文件在 MinIO 对象存储里的路径 - pdf_local_path = 文件在本地磁盘的路径

    原项目用 MinIO，所以数据库有 pdf_minio_path 列，写库时填个占位路径记账。但**本课程本地模式不用 MinIO**，文件存在本地，所以 State 里给 pdf_local_path（真正用的）、minio 留空。Agent 的 extract_text 读的是 pdf_local_path，那两个 MinIO 节点本地模式空跑。pdf_minio_path 是 MinIO 设计的遗留字段，记账用，本地模式不靠它。

    Q：为什么先往数据库插一条 processing 记录，再启动后台任务？

    为了**让 review_id 一上传就查得到**。先插记录，库里立刻就有这条（status=processing）。所以你拿 review_id 随时能查到（只是结果还没出来）。如果不先插，后台任务还没建记录前，前端查会 404。

    Q：graph.ainvoke 和 graph.invoke 有什么区别？

    ainvoke 是**异步版**（a = async），要配 await 或 create_task 用；invoke 是同步版。后端全程异步，所以用 ainvoke。

    六、怎么测试（正常 + 错误情况）¶

    Q：怎么端到端测一遍？

    Agent 建好 + 本地有真实 PDF + 起好服务器（uvicorn）+ 配好 DeepSeek Key，就能测。流程：上传拿 review_id → 轮询 GET /reviews/{id} 直到 done → 看报告。（可用配套脚本 verify_resume_e2e.py。）

    Q：各种错误情况怎么造？分别返回什么？

    想测的错误 怎么造 预期
    非 PDF 文件 传 .txt 400 "仅支持 PDF 格式"
    空文件 传 0 字节文件 400 "上传文件为空"
    文件过大 传 >20MB 413 "文件过大"
    没登录 不带 token 401
    token 失效 乱填 token 401
    查不存在的 id 编个 uuid 去查 404
    查别人的 id 用别的账号的 review_id 404（越权被挡）
    没配 Key 不配 DeepSeek Key 能 done，但全是兜底 50 分

    curl 示例：

    # 非 PDF → 400
curl -X POST http://localhost:8000/resume/upload \
  -H "Authorization: Bearer <token>" -F "file=@test.txt"

# 没登录 → 401
curl -X POST http://localhost:8000/resume/upload -F "file=@简历.pdf"
