    4.3 提示词（prompts.py）¶

    学习目标¶

    • 理解提示词在 Agent 里的角色，以及为什么单独成文件
    • 掌握「评分标准（rubric）」式提示词的设计
    • 理解占位符 {...} + .format() 的填充机制，以及每个提示被哪个节点使用
    • 理解 Think 提示词（结构化输出前的"先想后答"）
    • 写完即测：填充提示词，验证占位符正确替换

    文件路径 作用 进度

    4.3.1 提示词的角色¶

    如果说节点是"动作"、数据模型是"表格"，那提示词就是**指挥大模型做事的"剧本"**。简历 Agent 每次调 LLM，都要给它一段提示词，告诉它"现在做什么、按什么标准、注意什么"。

    我们把所有提示词集中放在 prompts.py，而不是散在各个节点里。好处是：提示词是最需要反复调优的部分，集中管理后，调提示词不用动业务代码，一眼能看全、好对比。

    提示词里有形如 {resume_text} 的**占位符**，运行时用 .format(resume_text=实际文本) 填入真实数据（回顾 Python 的字符串格式化）。本节定义的提示词分五类：系统提示、结构化提取、六维度评分、问题诊断、整体评价（外加一个 Think 提示）。

    4.3.2 系统提示与提取提示¶

    系统提示（SYSTEM_PROMPT） 定义大模型的"人设"——它会作为 SystemMessage 放在每次对话最前面，给 LLM 定基调：

    SYSTEM_PROMPT = """你是一位经验丰富的 IT 行业职业顾问，专门为应届毕业生和初/中级工程师审查简历。
你的评审严格、客观、可操作，不给出模糊的夸奖，只给出具体的问题定位和修改建议。"""

    提取提示（EXTRACT_STRUCTURED_PROMPT） 用于 extract_structured 节点，把简历原文交给 LLM、要求按规则提取。它有一个占位符 {resume_text}：

    EXTRACT_STRUCTURED_PROMPT = """请从以下简历文本中提取结构化信息。

【简历原文】
{resume_text}

提取要求：
- 完整保留项目描述的原始文字，不要改写或压缩
- 技术栈列表每项单独一个（如 Spring Boot、MySQL，不合并）
- 时间格式统一为 YYYY.MM - YYYY.MM（如写"至今"则保留"至今"）
- 无法提取的字段填空字符串，不要填"未知"或"无"
- 量化亮点：只提取含数字的句子（如"提升30%"、"10万DAU"）"""

    注意它**只规定"怎么提取"，不规定"输出什么字段"**——因为输出结构由 4.2 的 ResumeStructured Schema 通过 with_structured_output 保证了。提示词管"内容要求"，Schema 管"格式约束"，两者分工。

    4.3.3 六维度评分提示（rubric 设计）¶

    这是本节的重点。六个维度各有一段独立的评分提示，统一放在一个**字典** DIMENSION_REVIEW_PROMPTS 里（键是维度标识，如 project_depth）。这样 4.5 的并行评审节点可以按维度键取出对应提示。

    每段提示的精髓是**评分标准（rubric）——把 0–100 分**分档写清楚每一档长什么样，让 LLM 有明确的尺子可依，而不是凭感觉打分。以"项目深度"为例：

    DIMENSION_REVIEW_PROMPTS = {
    "project_depth": """请评审以下简历在【项目深度】维度的表现。

【评审重点】{focus}

【结构化摘要】
{structured_summary}

【简历原文（前3000字）】
{resume_text}

评分标准（0-100分）：
- 90-100：每个项目都有量化指标、明确的技术选型理由、清晰的个人贡献和难点解决
- 70-89： 大部分项目有量化数据，个人贡献基本清晰
- 50-69： 项目描述偏泛，缺少量化数据，个人贡献不明确
- 30-49： 项目描述流水账，看不出技术深度
- 0-29：  项目描述极度简陋或与岗位完全不相关""",

    # 其余 5 个维度（tech_match / expression / structure / quantification / authenticity）
    # 结构完全相同，只是【维度名】和【评分标准】不同 —— 完整内容见下方 4.3.5
}

    每段提示有三个占位符：

    • {focus}：评审侧重点（来自 4.5 的 SIX_DIMENSIONS 表，每个维度一句），告诉 LLM 这个维度重点看什么；
    • {structured_summary}：4.2 提取出的简历摘要（精简版，不传全文以省 token）；
    • {resume_text}：简历原文前 3000 字。

    为什么把评分标准写这么细？ 因为大模型打分如果没有标尺，结果会飘忽不定、难以复现。把每一档的特征写明，相当于给 LLM 一把"刻度尺"，让不同简历的评分有一致的依据——这是用 LLM 做"评估打分"类任务的关键技巧。

    4.3.4 诊断、评价与 Think 提示¶

    剩下三段提示：

    • DIAGNOSE_ISSUES_PROMPT（问题诊断）：用于 diagnose_issues 节点。占位符 {structured_summary}、{resume_text}、{raw_issues}（各维度已发现的问题汇总）。它要求 LLM 定位到具体位置、判优先级、给可操作建议、去重、控制在 5–15 条。
    • GENERATE_SUMMARY_PROMPT（整体评价）：用于 generate_summary 节点。占位符更多——结构化摘要、各维度评分、综合分、高优先级问题、目标岗位。
    • DIAGNOSE_THINK_PROMPT（Think 提示）：这是个特别的设计。在生成"结构化的问题清单"之前，先让 LLM 用**自由文本**做一轮宏观分析（最核心短板是什么、问题间有无共同根因、技能与经历是否有落差）。

    Think 提示是什么思路？ 直接让 LLM 输出结构化结果，它容易"只见树木不见森林"。所以先用一段自由推理（Think）让它"想一想全局"，再把这段思考**作为上下文**喂给后面的结构化诊断——相当于"先打草稿、再正式作答"，能显著提升诊断质量。这是一种轻量的"推理增强"技巧，你会在后面几个 Agent 里反复见到。

    章节总结¶

    本节我们写好了简历 Agent 的全部提示词：

    • 集中管理：提示词单独成文件，便于反复调优，与业务代码分离。
    • 提取提示：只管"内容要求"，输出格式交给 4.2 的 Schema——提示词与 Schema 分工。
    • 六维度 rubric：把 0–100 分分档写清，给 LLM 一把"刻度尺"，让评分有一致依据（LLM 评估类任务的关键技巧）。
    • Think 提示：结构化输出前先用自由文本做一轮宏观分析，"先打草稿再作答"提升质量。
    • 占位符机制：{...} + .format() 在运行时填入真实数据；每段提示标注了占位符和消费它的节点。
