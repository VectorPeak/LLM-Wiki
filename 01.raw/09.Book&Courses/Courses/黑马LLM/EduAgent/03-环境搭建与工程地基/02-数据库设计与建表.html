    3.2 数据库设计与建表¶

    学习目标¶

    • 掌握项目数据库的三大贯穿性设计：UUID 主键、多租户 tenant_id、时间戳与自动更新
    • 逐张理解 11 张业务表的设计意图，以及它们与四个 Agent 的对应关系
    • 理解 status 状态流转、JSONB 字段、外键约束、UNIQUE 约束等设计手法
    • 落地数据库会话依赖 get_db（承接 2.5、2.6）

    3.2.1 三大贯穿性设计¶

    在看具体的表之前，先理解三个**贯穿所有表**的设计约定。理解了它们，看每张表就轻松了。

    设计一：UUID 主键¶

    每张表的主键 id 都是 UUID（一长串全局唯一的字符串，如 3e76aeed-5e01-...），而不是常见的自增整数：

    id UUID PRIMARY KEY DEFAULT uuid_generate_v4()

    为什么用 UUID 而非自增 ID？因为 UUID 全局唯一、无法被猜测、天然适合多租户和分布式场景——不同租户、不同服务生成的 ID 永不冲突，也不会暴露「你是第几个用户」这类信息。使用前需要先启用 PostgreSQL 的 UUID 扩展：

    CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

    设计二：多租户 tenant_id¶

    每张业务表都有一个 tenant_id 字段（本节 3.2.9 会专门讲透）：

    tenant_id VARCHAR(64) NOT NULL DEFAULT 'tenant_default'

    它是「多租户隔离」的核心——同一套系统可以服务多个机构（租户），各租户的数据通过 tenant_id 严格隔离。本地开发默认都用 tenant_default。

    设计三：时间戳 + 自动更新¶

    每张表都有 created_at（创建时间）和大多有 updated_at（更新时间），类型是带时区的 TIMESTAMPTZ：

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

    为了让 updated_at 在每次更新时自动刷新，我们建一个**触发器函数**，并挂到需要的表上（完整代码放在本节末尾的 init_db.sql 里）：

    CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

    3.2.2 用户与权限：users¶

    CREATE TABLE IF NOT EXISTS users (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id       VARCHAR(64) NOT NULL DEFAULT 'tenant_default',
    username        VARCHAR(64) NOT NULL,
    email           VARCHAR(128) NOT NULL,
    password_hash   VARCHAR(256) NOT NULL,      -- bcrypt 哈希，绝不存明文密码
    role            VARCHAR(16) NOT NULL CHECK (role IN ('student', 'teacher', 'admin')),
    class_id        UUID,                        -- 班级（预留字段）
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (tenant_id, email)                    -- 同租户内邮箱唯一
);

CREATE INDEX idx_users_tenant_id ON users (tenant_id);
CREATE INDEX idx_users_role ON users (role);
CREATE INDEX idx_users_class_id ON users (class_id);

    几个设计要点：

    • password_hash：只存 bcrypt 加密后的哈希，绝不存明文密码（回顾 2.6，登录时用 passlib 校验）。这是安全底线。
    • role + CHECK 约束：角色只能是 student / teacher / admin 三者之一，数据库层面强制校验，写错值直接报错。
    • UNIQUE (tenant_id, email)：邮箱在「同一租户内」唯一——不同租户可以有相同邮箱，体现了多租户隔离。
    • 索引：在经常用于查询/过滤的字段（tenant_id、role）上建索引，加快查询。

    3.2.3 知识库待补充队列：knowledge_pending_queue¶

    CREATE TABLE IF NOT EXISTS knowledge_pending_queue (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id       VARCHAR(64) NOT NULL DEFAULT 'tenant_default',
    question        TEXT NOT NULL,                -- 学员的原始问题
    student_id      UUID REFERENCES users(id),
    confidence      FLOAT NOT NULL,               -- RAG 检索置信度，越低说明知识库越缺这块内容
    status          VARCHAR(16) NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending', 'resolved', 'dismissed')),
    resolved_by     UUID REFERENCES users(id),
    resolved_at     TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_knowledge_pending_queue_tenant_id ON knowledge_pending_queue (tenant_id);
CREATE INDEX idx_knowledge_pending_queue_status ON knowledge_pending_queue (status);

    这张表很巧妙：当学员提问，但知识库里检索置信度太低（说明知识库缺这块内容）时，系统会把问题**记到这个队列**，供教师后续补充知识库。这对应问答 Agent 的 enqueue_pending 节点（第五章实现）——让系统在「答不好」时主动暴露知识盲区。

    3.2.4 试卷批改（五张表）¶

    试卷批改涉及五张表，它们的关系是：一张**试卷**（exams）有多道**题目**（questions），简答题有多个**得分点**（scoring_points）；学员**提交**（exam_submissions）后，每道题产生一条**批改结果**（exam_reviews）。

    exams ──1:N──► questions ──1:N──► scoring_points
  │
  └──► exam_submissions ──1:N──► exam_reviews

    exams / questions / scoring_points¶

    CREATE TABLE IF NOT EXISTS exams (
    id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id   VARCHAR(64) NOT NULL DEFAULT 'tenant_default',
    title       VARCHAR(256) NOT NULL,
    description TEXT,
    due_date    TIMESTAMPTZ,
    created_by  UUID REFERENCES users(id),
    is_active   BOOLEAN NOT NULL DEFAULT TRUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_exams_tenant_id ON exams (tenant_id);

CREATE TABLE IF NOT EXISTS questions (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id       VARCHAR(64) NOT NULL DEFAULT 'tenant_default',
    exam_id         UUID REFERENCES exams(id) ON DELETE CASCADE,
    question_no     INT NOT NULL,
    question_type   VARCHAR(16) NOT NULL
                    CHECK (question_type IN ('single_choice', 'multi_choice', 'judge', 'short_answer', 'code')),
    content         TEXT NOT NULL,
    correct_answer  TEXT,                         -- 客观题存标准答案；代码题存测试用例 JSON
    score           INT NOT NULL DEFAULT 10,
    knowledge_tag   VARCHAR(128),                 -- 知识点标签，用于薄弱点聚合
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_questions_exam_id ON questions (exam_id);
CREATE INDEX idx_questions_knowledge_tag ON questions (knowledge_tag);

CREATE TABLE IF NOT EXISTS scoring_points (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    question_id     UUID REFERENCES questions(id) ON DELETE CASCADE,
    point_desc      TEXT NOT NULL,                -- 得分点描述
    point_score     INT NOT NULL,                 -- 该得分点的分值
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    confirmed_by    UUID REFERENCES users(id),    -- 教师审核确认
    confirmed_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_scoring_points_question_id ON scoring_points (question_id);
    • question_type 五种题型：单选 / 多选 / 判断 / 简答 / 代码。这直接对应批改 Agent 的「三轨并行」——客观题、简答题、代码题走不同批改逻辑（第六章详解）。
    • ON DELETE CASCADE：删除一张试卷时，它下面的题目会**级联自动删除**，不会留下「孤儿数据」。
    • scoring_points（得分点）：简答题不是「对/错」二元判断，而是拆成多个「得分点」分别评分。教师可以审核确认这些得分点（confirmed_by）。

    exam_submissions（提交记录）—— HitL 状态流转的核心¶

    CREATE TABLE IF NOT EXISTS exam_submissions (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id       VARCHAR(64) NOT NULL DEFAULT 'tenant_default',
    exam_id         UUID REFERENCES exams(id),
    student_id      UUID REFERENCES users(id),
    source          VARCHAR(16) NOT NULL DEFAULT 'word'
                    CHECK (source IN ('word', 'online', 'miniapp')),
    word_minio_path VARCHAR(512),                 -- 上传的 Word 文件路径（本地路径，遗留命名）
    -- 状态流转：提交 → AI批改中 → 待教师复核 → 已复核 → 已发布
    status          VARCHAR(16) NOT NULL DEFAULT 'submitted'
                    CHECK (status IN ('submitted', 'ai_processing', 'pending_review', 'reviewed', 'published')),
    submitted_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    published_at    TIMESTAMPTZ,
    weak_points          JSONB,                   -- AI 分析的知识薄弱点（JSON 数组）
    weak_points_summary  TEXT,                    -- 薄弱点文字摘要
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (exam_id, student_id)                  -- 每人每卷只能提交一次
);

CREATE INDEX idx_exam_submissions_tenant_id ON exam_submissions (tenant_id);
CREATE INDEX idx_exam_submissions_exam_id ON exam_submissions (exam_id);
CREATE INDEX idx_exam_submissions_student_id ON exam_submissions (student_id);
CREATE INDEX idx_exam_submissions_status ON exam_submissions (status);
    • status 五段流转：submitted（已提交）→ ai_processing（AI 批改中）→ pending_review（待教师复核）→ reviewed（已复核）→ published（已发布）。这条流转链正是「人在环中（HitL）」的体现——AI 批改完不是直接给学生看，而是先进入 pending_review 等教师确认（第六章会用 LangGraph 的 interrupt 实现这个暂停点）。
    • weak_points JSONB：用 PostgreSQL 的 JSONB 类型直接存一段结构化 JSON（如 [{"tag": "Spring IOC", "wrong_count": 2, ...}]）。JSONB 让我们能灵活存储「结构不固定的复杂数据」，无需为它单独建表。
    • UNIQUE (exam_id, student_id)：保证每个学员每张试卷只能提交一次。

    exam_reviews（逐题批改结果）¶

    CREATE TABLE IF NOT EXISTS exam_reviews (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    submission_id   UUID REFERENCES exam_submissions(id) ON DELETE CASCADE,
    question_id     UUID REFERENCES questions(id),
    question_type   VARCHAR(16) NOT NULL,         -- 冗余存储，省去 JOIN
    knowledge_tag   VARCHAR(128),                 -- 冗余存储，便于薄弱点聚合
    student_answer  TEXT,
    ai_score        INT,                          -- AI 给的分
    ai_feedback     TEXT,                         -- AI 的文字反馈
    ai_raw_result   JSONB,                        -- AI 批改的完整原始输出
    teacher_score   INT,                          -- 教师修改后的分（NULL=同意 AI）
    teacher_comment TEXT,
    final_score     INT,                          -- 最终分：优先 teacher_score，否则 ai_score
    needs_review    BOOLEAN NOT NULL DEFAULT FALSE, -- AI 置信度低时自动标记
    reviewed_by     UUID REFERENCES users(id),
    reviewed_at     TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_exam_reviews_submission_id ON exam_reviews (submission_id);
CREATE INDEX idx_exam_reviews_needs_review ON exam_reviews (needs_review);
CREATE INDEX idx_exam_reviews_knowledge_tag ON exam_reviews (knowledge_tag);
    • ai_score / teacher_score / final_score 三个分：这是 HitL 的精髓——AI 先给一个分（ai_score），教师可以修改（teacher_score），最终分（final_score）优先采用教师的。needs_review 在 AI 不确定时自动置 true，提醒教师重点复核这道题。
    • 「冗余存储」：question_type、knowledge_tag 本来在 questions 表里有，这里又存了一份。这是**有意为之的性能优化**——查询批改结果时不用再去 JOIN questions 表，直接读这张表就够了。

    3.2.5 简历审查：resume_reviews¶

    CREATE TABLE IF NOT EXISTS resume_reviews (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id       VARCHAR(64) NOT NULL DEFAULT 'tenant_default',
    student_id      UUID REFERENCES users(id),
    pdf_minio_path  VARCHAR(512) NOT NULL,        -- PDF 路径（本地路径，遗留命名）
    structured_data JSONB,                        -- LLM 结构化提取结果
    scores          JSONB,                        -- 六维度评分
    issues          JSONB,                        -- 逐条问题清单
    summary         JSONB,                        -- 整体评价
    status          VARCHAR(16) NOT NULL DEFAULT 'pending'

    3.2.8 多租户 tenant_id 设计¶

    现在专门把多租户讲透。为什么每张业务表都要带 tenant_id？

    设想 EduAgent 同时服务「A 培训机构」和「B 培训机构」。它们共用同一套系统、同一个数据库，但 A 的学员绝对不能看到 B 的数据。实现隔离最常见、最简单的方式，就是给每张表加一个 tenant_id 字段标明「这条数据属于哪个租户」，然后**所有查询都自动带上 WHERE tenant_id = 当前租户**：

    -- 查用户时，永远带上 tenant_id 过滤，确保只看到本租户的数据
SELECT * FROM users WHERE tenant_id = :tenant_id AND role = 'student';
    • 本地开发：只有一个租户，所有数据的 tenant_id 都是默认的 tenant_default。
    • 当前用户的 tenant_id 从哪来：回顾 2.5 的 get_current_user 依赖——它从 JWT Token 里解析出 tenant_id，接口拿到后用于过滤查询。
    • 向量库也隔离：不只是 PostgreSQL，Milvus 里的向量也会按 tenant_id 做命名空间隔离（第五章详解）。

    这种「一个字段 + 查询过滤」的多租户方案，是中小型 SaaS 系统最常用的做法，简单且足够用。

    3.2.9 数据库会话依赖：dependencies.py¶

    表建好了，应用怎么连接和操作它？这就要落地 2.5 和 2.6 学过的内容了。在 backend/dependencies.py 里：

    # backend/dependencies.py（数据库部分）
from typing import AsyncGenerator
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine, async_sessionmaker

from backend.config import get_settings

settings = get_settings()

# ── 创建异步引擎（连接池）──
engine = create_async_engine(
    settings.database_url,        # 来自 config.py，最终来自 .env.local
    pool_size=10,                 # 连接池基础大小
    max_overflow=20,              # 高峰时最多再额外开 20 个连接
    echo=False,                   # True 会打印所有 SQL，调试时可临时打开
)

# ── 会话工厂 ──
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)


async def get_db() -> AsyncGenerator[AsyncSession, None]:
    """FastAPI 依赖：获取异步数据库会话，自动提交 / 回滚 / 关闭"""
    async with AsyncSessionLocal() as session:
        try:
            yield session            # 把会话交给接口使用（回顾 2.1.6 / 2.5）
            await session.commit()   # 接口正常结束 → 自动提交
        except Exception:
            await session.rollback() # 出错 → 自动回滚
            raise

    这段代码把前面几节完美地串了起来：

    • settings.database_url —— 来自 config.py 的 BaseSettings（2.2），最终来自 .env.local（3.1），值是 postgresql+asyncpg://...（2.6）；
    • create_async_engine + async_sessionmaker —— 2.6 学的异步连接三步走；
    • get_db 用 yield 写成依赖 —— 2.5 学的依赖注入 + 2.1.6 的「yield 上面准备、下面收尾」。

    之后所有需要数据库的接口，只要写 db: AsyncSession = Depends(get_db)，就能拿到一个**用完自动提交/回滚/关闭**的会话。AsyncSessionLocal 这个会话工厂也会被 Agent 节点和迁移脚本复用。

    3.2.10 自动迁移：migrations.py¶

    最后一个问题：init_db.sql 只在 PostgreSQL 容器首次启动（数据目录为空）时自动执行一次。如果数据库**已经建好了**，后来我们又想给某张表**新增一个字段**，怎么办？总不能让所有人删库重建吧。

    解决方案是一套**幂等的自动迁移补丁**。在 backend/db/migrations.py 里维护一个补丁列表，应用每次启动时自动执行：

    # backend/db/migrations.py
from sqlalchemy import text
from backend.dependencies import AsyncSessionLocal
from backend.core.logger import get_logger

logger = get_logger(__name__)

# 所有补丁，按时间顺序追加。SQL 必须幂等（带 IF NOT EXISTS）
_MIGRATIONS: list[tuple[str, str]] = [
    (
        "exam_submissions.weak_points",
        "ALTER TABLE exam_submissions ADD COLUMN IF NOT EXISTS weak_points JSONB",
    ),
    (
        "exam_reviews.knowledge_tag",
        "ALTER TABLE exam_reviews ADD COLUMN IF NOT EXISTS knowledge_tag VARCHAR(128)",
    ),
    (
        "idx_exam_submissions_student_created",
        "CREATE INDEX IF NOT EXISTS idx_exam_submissions_student_created "
        "ON exam_submissions (student_id, created_at DESC)",
    ),
    # …… 每次给 init_db.sql 加字段，就在这里同步追加一条
]


async def run_migrations() -> None:
    """应用启动时执行所有 Schema 补丁；单条失败只警告，不阻断启动。"""
    async with AsyncSessionLocal() as session:
        for desc, sql in _MIGRATIONS:
            try:
                await session.execute(text(sql))
                await session.commit()
            except Exception as e:
                await session.rollback()
                if "already exists" not in str(e):
                    logger.warning("db.migration_failed", column=desc, error=str(e))
    logger.info("db.migrations_done", count=len(_MIGRATIONS))

    理解这套机制的三个要点：

    1. 幂等（idempotent）：每条 SQL 都用 ADD COLUMN IF NOT EXISTS / CREATE INDEX IF NOT EXISTS，意味着**重复执行也安全**——字段已存在就跳过。所以应用每次启动都跑一遍，毫无副作用。
    2. 只增不毁：补丁里**只允许 ADD / CREATE 这类增量操作，严禁 DROP / TRUNCATE** 等破坏性变更，从根上杜绝「迁移脚本误删数据」的事故。
    3. 双写规则：每次你在 init_db.sql 新增一个字段，必须同步在 _MIGRATIONS 里追加一条对应的 ADD COLUMN IF NOT EXISTS。这样——全新的数据库由 init_db.sql 一次建全；已存在的数据库由 migrations.py 补齐新字段。两边保持一致，谁都不落下。

    run_migrations() 会在应用启动时由 lifespan 自动调用（回顾 2.1.6 的 @asynccontextmanager），这部分我们在第八章装配 main.py 时实现。

-- 自动更新 updated_at 触发器
-- ============================================================
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DO $$
DECLARE
    t TEXT;
BEGIN
    FOREACH t IN ARRAY ARRAY[
        'users',
        'exams', 'exam_submissions', 'exam_reviews',
        'resume_reviews', 'interview_sessions',
        'interview_questions', 'qa_sessions'
    ]
    LOOP
        EXECUTE format('
            CREATE TRIGGER trg_%s_updated_at
            BEFORE UPDATE ON %s
            FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
        ', t, t);
    END LOOP;
END;
$$;

    """FastAPI 依赖：获取异步数据库会话，自动提交 / 回滚 / 关闭"""
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

    ⚠️ 这个文件依赖 backend/config.py（提供 get_settings() 和 database_url），而 config.py 我们下一节（3.3）才创建。所以**如果你现在就想运行，请先跳到 3.3 把 config.py 建好**，再回来；或者按章节顺序往下走即可，到 3.3 自然就齐了。

    文件 3：backend/db/migrations.py¶

    # backend/db/migrations.py
#
# 启动时自动执行的 Schema 补丁（全部幂等，可重复运行）。
# 规则：
#   - 只写 ADD COLUMN IF NOT EXISTS / CREATE INDEX IF NOT EXISTS 等幂等 DDL
#   - 禁止写 DROP / TRUNCATE 等破坏性变更
#   - 每次 init_db.sql 新增字段，同步在 _MIGRATIONS 里追加一条

from sqlalchemy import text
from backend.dependencies import AsyncSessionLocal
from backend.core.logger import get_logger

logger = get_logger(__name__)

# ── 所有需要补丁的 DDL，按时间顺序追加。SQL 必须幂等（IF NOT EXISTS）──
_MIGRATIONS: list[tuple[str, str]] = [
    (
        "exam_submissions.weak_points",
        "ALTER TABLE exam_submissions ADD COLUMN IF NOT EXISTS weak_points JSONB",
    ),
    (
        "exam_reviews.knowledge_tag",
        "ALTER TABLE exam_reviews ADD COLUMN IF NOT EXISTS knowledge_tag VARCHAR(128)",
    ),
    (
        "exam_submissions.weak_points_summary",
        "ALTER TABLE exam_submissions ADD COLUMN IF NOT EXISTS weak_points_summary TEXT",
    ),
    (
        "idx_exam_submissions_student_created",
        "CREATE INDEX IF NOT EXISTS idx_exam_submissions_student_created "
        "ON exam_submissions (student_id, created_at DESC)",
    ),
    (
        "idx_resume_reviews_student_created",
        "CREATE INDEX IF NOT EXISTS idx_resume_reviews_student_created "
        "ON resume_reviews (student_id, created_at DESC)",
    ),
    (
        "idx_interview_sessions_student_created",
        "CREATE INDEX IF NOT EXISTS idx_interview_sessions_student_created "
        "ON interview_sessions (student_id, created_at DESC)",
    ),
]


async def run_migrations() -> None:
    """
    在应用启动时执行所有 Schema 补丁。
    单条失败只记录警告，不阻断启动流程。
    """
    async with AsyncSessionLocal() as session:
        for desc, sql in _MIGRATIONS:
            try:
                await session.execute(text(sql))
                await session.commit()
                logger.debug("db.migration_applied", column=desc)
            except Exception as e:
                await session.rollback()
                err = str(e)
                if "already exists" not in err:
                    logger.warning("db.migration_failed", column=desc, error=err)

    logger.info("db.migrations_done", count=len(_MIGRATIONS))

    migrations.py 依赖 backend/core/logger.py（下一节创建）和 backend/dependencies.py（本节已建）。所以它能否独立运行同样取决于 3.3 的 logger.py——按章节顺序走即可。

    3.2.12 需要重建表时：清空重来（PyCharm）¶

    如果你的库是**早期建的、和最新建表语句对不上**（比如某张表少了字段），最干净的办法不是逐个 ALTER，而是**清空所有表、重新执行一遍完整的 init_db.sql**。下面用 PyCharm 操作（回顾 2.6.5 学过的 DROP SCHEMA 清空法）。

    ⚠️ 这会删除库里所有数据，仅限本地开发环境使用！ 生产环境绝不能这么干。

    第一步：清空整个 public schema。 在 PyCharm 的 Query Console（顶部下拉确认是 eduagent.public）里执行：

    DROP SCHEMA public CASCADE;          -- 删除 public 下所有表、函数、扩展
CREATE SCHEMA public;                -- 重建一个空的 public
GRANT ALL ON SCHEMA public TO eduagent_user;
GRANT ALL ON SCHEMA public TO public;

    执行后会提示"drop cascades to ... 13 个对象"（11 张表 + 触发器函数 + uuid-ossp 扩展），库就回到了干净无表的状态。

    第二步：重新执行 init_db.sql。 两种方式任选：

    • 方式①（推荐）：在左侧 Database 工具窗里**右键 eduagent 数据源 → "Run SQL Script…" → 选择 scripts/init_db.sql → Run**。PyCharm 会把整个文件按顺序执行（包括开头的 CREATE EXTENSION "uuid-ossp"，正好把第一步删掉的扩展补回来）。
    • 方式②：在编辑器里打开 init_db.sql，确认右上角的数据源选的是 eduagent，Ctrl+A 全选 → 点绿色 ▶（或 Ctrl+Enter）执行整段。

    第三步：验证。 右键数据源 → Refresh，展开 schemas → public → tables，应看到 11 张表。或直接跑：

    SELECT count(*) FROM information_schema.tables WHERE table_schema = 'public';   -- 应为 11

    第四步：重新灌测试账号。 清空把 student01 等账号也删了，所以重跑一次 seed 脚本（见 3.6）把账号补回来：

    python scripts/seed_data.py

    💡 可能遇到的坑：第二步重跑时若 CREATE EXTENSION "uuid-ossp" 报权限不足，说明你的 eduagent_user 没有建扩展的权限。用超级用户 postgres 对该库单独执行一次 CREATE EXTENSION IF NOT EXISTS "uuid-ossp";，再重跑 init_db.sql 即可。

    章节总结¶

    本节我们设计并建好了 EduAgent 的整个数据库：

    • 三大贯穿性设计：UUID 主键（全局唯一、安全、多租户友好）、tenant_id 多租户隔离、TIMESTAMPTZ 时间戳 + 自动更新触发器。
    • 11 张表：覆盖用户、低置信度队列、试卷批改、简历审查、模拟面试、问答会话，每张表都和具体 Agent 对应。
    • 关键设计手法：status 状态流转（尤其是批改的五段流转 = HitL）、JSONB 存结构化结果（承接 Pydantic）、外键 + ON DELETE CASCADE、UNIQUE 约束（thread_id / 提交唯一性）、冗余存储优化查询。
    • 会话依赖：dependencies.py 落地 create_async_engine + get_db，把配置、异步、依赖注入串成一体。
    • 自动迁移：migrations.py 用幂等补丁解决「已有库加字段」问题，牢记「幂等、只增不毁、init_db 与 migrations 双写同步」。
