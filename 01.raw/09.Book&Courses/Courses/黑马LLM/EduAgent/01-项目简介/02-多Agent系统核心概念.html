    1.2 多 Agent 系统核心概念¶

    学习目标¶

    • 理解什么是 Agent，以及它与「一次大模型调用」的本质区别
    • 了解 Agent 从简单到复杂的几种典型形态
    • 理解为什么 EduAgent 要拆成四个独立的 Agent
    • 理解为什么用 LangGraph 的「图」来实现 Agent，掌握 State / Node / Edge / Checkpointer 四要素
    • 了解编排者 Orchestrator 的作用，以及项目关键约束的由来

    在动手之前，我们必须先把几个最核心的概念讲清楚：到底什么是 Agent？为什么要用 LangGraph？ 这一节不写项目代码，但它决定了你后面能不能「想明白」而不是「抄明白」。

    1.2.1 什么是 Agent¶

    先看一个最朴素的对比。

    当你直接调用一次大模型时，流程是这样的：

    用户问题  ──►  大模型  ──►  回答

    这只是一次「问答」，它没有记忆、不会使用工具、不会根据情况做不同处理。我们不把它叫做 Agent。

    而一个 Agent（智能体），是一个**以大模型为「大脑」、能够感知输入、自主决策、并采取行动来完成目标的系统**。它通常具备这样几种能力：

    • 感知（Perceive）：接收用户输入和上下文；
    • 记忆（Memory）：记住之前的对话或中间结果；
    • 决策（Decide）：根据当前情况判断下一步该做什么（要不要查知识库？要不要联网？该走哪条分支？）；
    • 行动（Act）：调用工具、检索知识、生成内容；
    • 可循环 / 可中断：可以反复执行直到完成，也可以在中途停下来等人介入。

    用一句话概括：普通大模型调用是「一问一答」，Agent 是「一套会思考、会用工具、有状态的工作流程」。

    EduAgent 里的每个 Agent 都满足这个定义。比如「智能问答 QA」会先判断问题类型，决定走通用直答还是查知识库，检索后还会判断置信度够不够、要不要联网兜底，最后还会把对话压缩成摘要记下来——这是一连串的感知、决策和行动，而不是简单的一次问答。

    1.2.2 Agent 的几种形态¶

    Agent 不是只有一种长相。从简单到复杂，业界常见的形态可以这样理解：

    形态一：单次调用            用户 ──► LLM ──► 回答
（不算 Agent）

形态二：固定工作流          用户 ──► 步骤A ──► 步骤B(含LLM) ──► 步骤C ──► 结果
（流程写死，LLM 嵌在某些步骤里）

形态三：单 Agent            用户 ──► ┌─► LLM 决策 ─► 调用工具 ─┐
（LLM 自主决定调哪些工具，          │                       │
  循环到任务完成）                 └──────── 循环 ◄─────────┘

形态四：多 Agent 协作        用户 ──► 编排者 ──┬─► Agent1
（多个专精 Agent，                          ├─► Agent2
  由编排者统一调度）                         └─► Agent3
    • 形态一：就是普通一次大模型调用，没有 Agent 的特征。
    • 形态二（工作流）：流程是人为编排好的固定步骤，LLM 只在某些环节出力。它可控、可预测，但不够灵活。
    • 形态三（单 Agent）：把决策权交给 LLM，让它自己决定调用哪些工具、循环多少次。灵活但有时不可控。
    • 形态四（多 Agent）：把复杂问题拆给多个专精 Agent，再由一个编排者统一调度。

    EduAgent 主要是形态二和形态四的结合：每个 Agent 内部是一套用 LangGraph 显式画出来的、带分支和条件判断的「受控工作流」；四个 Agent 之上再由 Orchestrator 做多 Agent 编排。我们刻意选择「受控」而非「完全自主」，因为在教育这种对准确性要求高的业务里，**流程可控、行为可预测**比「让模型自由发挥」更重要。

    1.2.3 为什么 EduAgent 要拆成四个 Agent¶

    你可能会问：为什么不做成一个「全能 Agent」，而要拆成四个？原因是这四类业务的**流程形状根本不同**：

    • 问答是「检索 → 判断 → 生成」的 RAG 流程；
    • 批改是「并行分轨打分 → 等老师确认 → 发布」的 HitL 流程；
    • 简历审查是「抽取 → 多维度并行评分 → 汇总建议」的扇出流程；
    • 模拟面试是「分阶段推进、记住上下文」的状态机流程。

    把它们硬塞进一个 Agent，会让流程逻辑变成一团乱麻，难以维护、难以测试、难以单独替换。**按业务边界拆分（高内聚、低耦合）**是软件工程的基本原则，在 Agent 系统里同样成立。拆分后每个 Agent 都可以独立开发、独立测试、独立升级，这也是为什么本课程能带你「一个 Agent 一个 Agent」地循序渐进实现。

    1.2.4 实现 Agent 的框架：LangGraph¶

    理解了「要做带分支、有状态的受控工作流」，我们就能理解**为什么要用 LangGraph，而不是用 LangChain 的「链（Chain）」**。

    「链」是一条直线：

    A ──► B ──► C ──► D

    链非常适合「固定顺序的几步处理」，但它有个致命限制：只能直线走，没法表达分支、循环、并行、中途暂停。而真实 Agent 恰恰处处需要这些：

    • 问答需要根据问题类型走不同分支（条件分支）；
    • 批改需要同时跑三个题型轨道（并行）；
    • 批改还需要停下来等老师确认（中途暂停 / 人在环中）；
    • 多轮对话需要记住上下文（状态持久化）。

    LangGraph 用「图（Graph）」来解决这些问题。一张图由三个核心要素构成：

                      ┌──────────── State（状态）────────────┐
                  │   所有节点共享的一份数据，节点读它、改它    │
                  └──────────────────────────────────────┘
                              ▲          ▲
                              │ 读/写     │ 读/写
        ┌─────────┐  边   ┌───┴────┐  条件边  ┌─────────┐
   START ─► 节点A ─────► 节点B ─────┬──► 节点C ──► END
        └─────────┘        └────────┘   │
                                        └──► 节点D ──► END
    • State（状态）：一份所有节点共享的数据结构（在代码里通常是一个 TypedDict）。每个节点都能读取它、并返回要更新的字段。它是节点之间传递信息的「传送带」。
    • Node（节点）：图上的一个处理单元，本质就是一个函数——读取 State、做一件事（调模型、查知识库、算分数……）、返回要更新到 State 的内容。
    • Edge（边）：决定一个节点执行完后该去哪个节点。普通边是固定的「A 之后一定去 B」；**条件边**则根据 State 的当前值动态选择去向（这就是「分支」）。
    • Checkpointer（检查点）：负责把 State 持久化保存，从而实现「多轮记忆」和「中途暂停后恢复」。

    把这几样组合起来，你就能画出任意复杂的业务流程图，再用一行 compile() 把它编译成一个可执行的 Agent。这正是本课程后面每个 Agent 的实现套路：定义 State → 写若干节点 → 用边把它们连起来（含条件边）→ 绑定 Checkpointer → 编译运行。

    你现在不需要会写 LangGraph 代码，只要建立起「Agent = 一张由 State 串起来、节点处理、边控制走向的图」这个心智模型即可。第二章会用一个最小的可运行例子带你把这套语法真正写一遍。

    1.2.5 编排者 Orchestrator¶

    四个 Agent 各自是一张图，那么用户的一句话进来，谁来决定交给哪个 Agent？答案是 Orchestrator（编排者）。

    它的职责有两个层次：

    1. 意图识别 + 单 Agent 路由：理解用户想干什么（问答？批改？面试？），把请求直接交给对应的那一个 Agent。这是最常见的情况。
    2. 多 Agent 串联（Pipeline）：在复杂场景下，把多个 Agent 串成一条流水线，前一个的输出作为后一个的输入，协作完成更复杂的任务。

    你可以把 Orchestrator 理解为整个系统的「前台 + 调度员」：它不亲自干活，但它知道每件事该找谁。这部分我们会在第八章实现。

    章节总结¶

    本节我们抛开具体项目，建立了多 Agent 系统的核心心智模型：

    • Agent 的本质：以大模型为大脑、能感知、决策、行动、且有状态的系统，区别于「一问一答」的单次调用。
    • Agent 的形态：从单次调用，到固定工作流，到单 Agent 自主决策，再到多 Agent 协作；EduAgent 采用「受控工作流 + 多 Agent 编排」的组合，强调可控可预测。
    • 为何用 LangGraph：链只能直线走，而真实 Agent 需要分支、并行、中断、持久化，这些都要靠「图」来表达；图的四要素是 State、Node、Edge、Checkpointer。
    • Orchestrator 负责意图识别与路由；项目的各种强制约束，本质都是帮你提前规避的坑。

    到这里，第一章的认知准备就完成了。下一章「工具介绍」，我们将用一组**脱离 EduAgent 的最小可运行例子**，带你快速上手 Python 异步编程、Pydantic、LangChain、LangGraph、FastAPI 和 PostgreSQL 这几样贯穿全项目的基础工具。打好这个基础，我们就正式进入动手实战。
