# 【Agent实战-第1天】规划模块

## 1. 总体

在大多数当前的 Agent 系统中，行业 "know-how" 的 plan 规划，确实是由 prompt 人为写进去的。也就是说：

> 目前大部分的规划（Planning）逻辑，是通过提示词（prompt）或程序结构，手动告诉 LLM 它该怎么思考、怎么分步执行的。

比如：

```text
You are an AI assistant. To complete tasks, always think step by step,
consider tools you have, and reason before acting. Use this format:
Think
Decide
Act
Observe
```

或者更复杂一点，像 AutoGPT / BabyAGI 中，框架本身就把「任务拆解、执行、回顾」这类流程写死了，LLM 只是在填空而已。

---

### 🤖 那 LLM 能不能自己做规划呢？

能，但目前还不是特别可靠或完全自动化。比如：

- 你可以 prompt LLM 说：“给我制定一个完成 X 的行动计划”，它确实能生成一套 steps。
- 你也可以训练一个 planner 模块，让它生成 sub-tasks，再交给 executor 模块去执行。

这属于「让 LLM 来规划」，但也需要你在框架上先告诉它“你负责规划”，等于是半自动。

所以结论：

| 问题 | 回答 |
|---|---|
| 规划是 LLM 自己想的吗？ | 一部分是，但通常是在框架或 prompt 引导下实现的。 |
| 是否完全自动？ | 还没完全达到，当前系统大多还是人为设计规划流程，LLM 负责填空。 |
| 未来可能吗？ | 是的，未来可能让 LLM 具备更多自主规划能力，比如通过 Memory + Planning + RL 等方式进化出更强的 autonomy。 |

---

## 2. 如何选择

在实际落地（即把大语言模型应用到真实业务场景）时，究竟哪些地方应该“写在 Prompt 里”，哪些地方应该由“人工或程序来固定定义”，往往取决于**可控性、灵活性和复杂度**等因素。下面从常见的应用视角来分析。

---

### 2.1 什么时候用 Prompt 让 LLM 来决定或规划

#### 1. 需要模型自行推理或发挥创造力时

- **问题不确定、场景复杂**：例如，你需要一个解决方案，但并不清楚最佳方案是什么，需要模型自己做大量推断。
- **希望模型能灵活应对多变场景**：场景可能临时发生变化，或者问题本身没有“标准化”的解决流程，这时借助 LLM 自主推理和生成方案更高效。
- **需要模型产生更多可能性**：尤其在创意、撰写文案、构思初稿等需要发散思维的任务中，你希望模型做不同尝试、给出多种备选方案。

#### 2. 人力成本/维护成本高

- **不要人为写死过多逻辑**：有时业务频繁变化，如果完全硬编码，会导致需要经常改程序。通过 Prompt 动态让模型来生成、优化策略或流程，可减少手动维护的成本。

#### 3. 辅助决策或自动化

- 你只需要告诉模型“目标”或“限制条件”，让模型自己“分解”并“规划”下一步操作，而非固定给出所有步骤。

---

### 2.2 什么时候要用人为定义/硬编码

#### 1. 流程固定，可控性要求高

- **强流程化/标准化**：如果某些业务流程、法务流程、风控流程等，规定必须走固定的若干步骤、检查点。例如 KYC（实名认证）等合规步骤，这种就适合在业务代码里“写死”或严格定义。
- **合规或安全要求高**：不能容忍模型输出违反规定的内容；需要可解释、可审计。人工定义好的流程更可控，审计上也更简单。

#### 2. 不需要太多“模型推理”

- **简单稳定的逻辑**：比如根据用户选择，进入下一个固定页面或固定问答，不需要模型判断或发挥创造力。手动硬编码更加直接、高效。
- **高准确度要求 + 可预期**：有些核心业务关键性很高（例如金融交易的步骤），一旦出错会造成损失，这时往往宁可牺牲灵活度，也要保证流程的绝对稳定和可验证。

#### 3. 需要结合大量外部系统或特定算法

- **与数据库、API 或传统程序强绑定**：如果中间步骤牵涉到很多传统逻辑（比如数据库查询、多层调用），而这些逻辑又必须严格按某个顺序走，这种更适合在编程逻辑里“定死”流程，而不是让模型自由调度。

---

### 2.3 综合或混合的做法

在真实生产环境中，往往会出现混合的模式：

1. **大框架“定死”，关键节点用 Prompt**：先用人工代码或流程图固定好业务主流程，在需要创造力或不确定性强的地方，让模型根据 Prompt 来规划或填充内容。
2. **在 Prompt 中嵌入关键信息和限制条件**：比如你可以在 Prompt 里告诉模型“这里要先检查一下输入是否合法，否则直接返回失败”，再让模型自己决定在什么条件下执行具体动作。
3. **LLM 生成“初步规划”，再由人工/代码做校验或修订**：例如让模型生成一个方案，然后可以通过代码或人工来审核它，如果不符合要求，再让模型重新迭代或直接由人来修正最终执行流程。

---

### 2.4 如何进行选择：关键考量点

#### 1. 是否允许模型发挥主观创造力或灵活应对

- 如果需要，倾向于多用 Prompt，让 LLM 自行规划。
- 如果不行（必须“100% 按照规定”），就多在程序里硬编码。

#### 2. 可控性 / 风险承受度

- 重要环节、合规要求极高场景 -> 人工 + 程序严格定义。
- 容错度高或创新、探索场景 -> 让模型自由生成。

#### 3. 维护成本

- 需求变化频繁，需要经常改 -> 用 Prompt 可能更灵活。
- 需求相对稳定 -> 硬编码也没问题。

#### 4. 可解释性 / 审计要求

- 模型生成的内容难以完全审计或解释 -> 重要核心部分需人工定义。
- 非关键部分，可以让 LLM 去生成。

---

### 小结

- **Prompt 更像“指导”或“原则”**，让模型在这些原则内自由思考、制定和执行流程，适合需要灵活应变、创造性或自动化程度高的场景。
- **人工/程序硬编码的流程**，适合高度可控、可预测、合规、安全的任务；这些场景往往我们不希望模型自由发挥。

实际系统里常常“先在人为代码中固定主干流程”，再在需要模型能力的节点中，通过 Prompt 来让模型做局部规划或执行，从而在灵活和可控之间找到平衡。

## 3. CASE

下面给出一些更具体的场景案例，分别说明在实际项目中，哪些部分通常用“人工或程序硬编码”，哪些部分可以通过 Prompt 让 LLM 自主生成或规划，以帮助理解在真实落地时如何选择：

---

### Case 1：电商客服问答系统

- **场景概述**：用户在电商平台咨询商品信息、物流进度、售后政策等问题。
- **硬编码部分（程序/人工定义）**：
  - **身份验证流程**：当用户进行订单查询或退款操作时，需要先验证用户的账号、订单号等，必须是固定规则（如 API 查询、数据库对比），这部分流程和验证逻辑可以直接写在后端代码里，避免出错或绕过。
  - **业务限制**：对于售后政策，例如七天无理由退货，平台规定了具体条件和程序，每个步骤是固定的，不能依赖模型“自由发挥”。
- **Prompt/LLM 部分**：
  - **客服对话内容**：对用户提出的一般性问题，期望得到自然语言回答（如“这件衣服尺码如何选择？”、“优惠活动有哪些？”）。这里可以给模型一个 Prompt，告诉它使用友好的客服风格，结合商品特性给出建议。
  - **常见问题总结**：当用户问相似问题时，可以让模型从已有 FAQ 数据库中抓取信息，并基于 Prompt（“请用简洁易懂的语言回答”）来生成更贴切的回答。

在这个案例中，**用户身份验证、售后规则**等必须可控，因此需要硬编码；而**对话、问答**等需要灵活性、自然语言表达的地方，可以让 LLM 来自由生成答案。

---

### Case 2：企业内部知识库问答机器人

- **场景概述**：在大型企业内部，为员工提供一个问答机器人，查询公司制度、办公流程或技术文档等信息。
- **硬编码部分**：
  - **权限管理**：不同部门、不同级别员工所能查询的文档不同，这些权限逻辑通常严格写在系统后端，不能让 LLM 决定是否开放访问。
  - **查询语句生成和检索流程**：可能需要将用户的问题转换成检索查询去搜索文档；若企业有自己的语义搜索引擎或 Elasticsearch，这部分可以由后端或中间层固定实现。
- **Prompt/LLM 部分**：
  - **解释和总结**：找到相关文档后，需要一个自然语言总结或解释，甚至需要模型对比多份文档，生成一段概括性的答复。
  - **模糊查询或多跳推理**：当员工的问题比较复杂，需要跨多部门文档信息，需要 LLM 来合理串联信息。你可以让模型在 Prompt 中“自己规划如何将搜索结果整合起来”。

这里，“权限管理和检索流程”是可预测并需要高可控性的，所以硬编码；但如何根据检索内容进行**总结、解释**就可以让 LLM 灵活处理。

---

### Case 3：舆情监测与分析

- **场景概述**：某公司想要监测社交媒体或新闻中的负面评价，并进行一些自动化分析和分类，比如识别主题、情感、风险等级等。
- **硬编码部分**：
  - **数据收集管线**：比如爬虫或 API 获取社交媒体文本，清洗、脱敏等，这些是标准化数据流程，通常用程序来完成。
  - **分类标签定义**：如“正面、中性、负面”，或“政策风险、市场风险、形象风险”等标签，需要公司内部先定义好，这些分类名称和规则一般是固定的。
- **Prompt/LLM 部分**：
  - **文本自动打标签**：让模型对每条新数据做情感判断、主题提取。Prompt 中可以写：“根据以下定义的标签，判断文本属于哪一类”。
  - **舆情概述和总结**：对每天/每周的主要话题进行归纳总结、提炼关键词，生成可读的报告，要求模型在 Prompt 中按照固定格式输出。

在该场景中，**数据收集与标签体系**是“有固定框架”的，所以会先写死规则；但对话题做进一步**总结、归纳**这类具有创造性或概括性工作就可以交给模型完成，通过 Prompt 来指导模型输出报告内容。

---

### Case 4：法律合规审核（合同审核场景）

- **场景概述**：公司内部有大量合同，需要自动化审阅合规性，检测其中是否存在风险条款。
- **硬编码部分**：
  - **合规审核准则**：比如国家法律法规、公司条款库，这些是公司法务部门明确规定的点，需要确保准确执行，不能让模型随意“推断”。
  - **风险等级定义和处理流程**：如果检测到高风险条款，需要人工复核或上报部门领导，流程是固定的，不可跳过。
- **Prompt/LLM 部分**：
  - **条款文字分析**：让模型针对具体文本回答“此条款是否包含以下风险要点？如果是，请指出理由”。
  - **文字改写或提示修改建议**：在发现有不合规或模糊表述时，让模型尝试改写成更合规、风险更低的版本。

法律合规尤其看重**可控性和准确性**，所以很多关键点都要先定义清楚，但是对于模型能做的部分，比如从自然语言文本中找出可疑表述并给出修改建议，还是可以通过 Prompt 交给 LLM 来生成。

---

### Case 5：用户画像和营销推荐

- **场景概述**：电商或金融类产品需要根据用户行为数据，做用户画像，然后做推荐或个性化营销方案。
- **硬编码部分**：
  - **数据聚合和建模**：大部分企业已经有自己的数据仓库，用户画像可能用传统机器学习/模型来生成标签，比如“青年用户”、“喜欢电子产品”、“近期高活跃度”等。
  - **营销策略规则**：公司有既定的预算、优先级规则，哪些类型的用户触发什么优惠券/活动，这些逻辑是业务固化的，需要在后台写死。
- **Prompt/LLM 部分**：
  - **个性化文案**：对不同用户群体，可以让模型根据用户特征来自动撰写更吸引人的营销文案，而不是一个模板发全场。
  - **活动创意建议**：在阶段性营销活动时，让模型根据用户画像产生一些创意点子，比如“可以尝试抽奖、拼团、秒杀形式”，并说明可能的优缺点。

在此场景中，“画像、用户分层、营销预算”这些要由程序和业务线来制定并控制；而让模型来写“多样化、个性化文案”或给出营销创意就极大地发挥了 LLM 的生成能力。

---

### Case 6：复杂项目管理或任务分解（内部协作工具）

- **场景概述**：公司在做一个新产品，需要对目标、需求进行拆分，形成任务清单，然后分配到不同的团队成员。
- **硬编码部分**：
  - **项目管理规则与权限**：谁有权限指派任务？谁能修改优先级？项目甘特图或任务管理表在系统里的逻辑固定不可随意篡改。
  - **任务追踪和提醒机制**：定期提醒负责人里程碑检查，这类流程化功能一般由项目管理工具代码实现。
- **Prompt/LLM 部分**：
  - **需求拆解和建议**：让模型基于产品需求，自动生成一个初步的任务列表或里程碑设定，提示“哪些部分可并行，哪些需要先做市场调研”，帮助项目经理节省脑力劳动。
  - **跨部门协作沟通建议**：在项目推进过程中，如果遇到问题，让模型建议如何与其他部门沟通、哪些信息需要同步、注意哪些风险等，发挥模型的“文本组织”和“知识总结”能力。

这里，“项目管理的核心逻辑”还是要在代码/平台上固化，以确保可控和记录；但对于内容性的建议（需求拆解、沟通提示）可以让 LLM 自主思考，并在 Prompt 中告知“需要输出详细但简洁的列表，并包括优先级说明”等。

---

### 小结

#### 1. 固定 & 硬编码

- 常见于需要**高可控性、固定逻辑或合规要求**的部分，或对**数据处理、权限管理、业务规则**等有严格要求的场景。
- 其优势是：结果可预期、容易审计、维护简单。
- 劣势是：缺乏灵活性，不易处理未知变化或新需求。

#### 2. Prompt & LLM

- 适合对**自然语言处理、创造性或不确定性**较高的任务，或需要做**推理/归纳/总结**时。
- 优势是：可以减少人工或传统编程的复杂度，快速给出多种方案或文案，能适应变化的场景。
- 劣势是：输出可能有不确定性，需要一定的验证或控制策略。

在现实落地中，这两者往往会配合使用：**把不可或缺的核心业务流程用人工/代码严格定义和实现，然后让模型在 Prompt 里处理那些需要人力创意或复杂推理的部分**，从而实现对“灵活度与可控性”的平衡。

## 4. 目前主流框架的 plan 模块实现

下面我来拆解一些主流 LLM-Agent 框架（或方法）在“规划（Planning）”上的核心思路，主要分为以下几类：

1. ReAct
2. MRKL
3. BabyAGI
4. AutoGPT

### 4.1 ReAct

> **ReAct: Synergizing Reasoning and Acting in Language Models**  
> 出处：论文 ReAct（2022年提出，作者包括许多学界/业界大拿）

#### 1.1 核心思路

- **动机**：  
  传统的 “Chain-of-Thought（CoT）推理”只写 reasoning 不执行行动；ReAct 提出在 reasoning 的过程中，LLM 也可以执行行动（Action）并观察环境，从而在多步交互中完成复杂任务。

- **格式**：  
  在提示中，要求 LLM 同时输出：

  1. **Thought**（思考过程，类似 Chain-of-Thought）
  2. **Action**（决定要执行的动作/调用的工具）
  3. **Observation**（得到的环境或工具返回的信息）

- 这三步互相迭代，比如：

```text
Thought 1: 我想先查一下数据库的内容
Action 1: query_db("xxx")
Observation 1: 数据库返回xxxx
Thought 2: 看起来结果是...
Action 2: ...
Observation 2: ...
...
```

#### 1.2 规划机制

- **为什么说它是“即时规划”？**  
  ReAct 的“规划”是通过在 prompt 模板中写明“先思考(Thought)，再行动(Action)，再观察(Observation)，然后再思考”这样一个**循环框架**。这个框架其实是人为指定好的。

- **LLM 自己的贡献**：  
  ReAct 让 LLM 在每一步 “Thought” 中去推断下一步要怎么做，也就是“分步决策”，属于小规模的、在线的 planning。

- **人对 LLM 的限制**：
  - 需要在 prompt 里写死格式，告诉它必须先写 `Thought`，再写 `Action`，然后等环境给你 `Observation` 后再继续。
  - LLM 不会自行生成完全不符合格式的回复（通过上下文约束）。
  - 每次要执行 action 时，需要外部程序（agent 主体）去解析 LLM 生成的 action，然后调用相应的工具。

在 ReAct 里，“规划”是嵌在每一轮推理-行动循环里，类似于让 LLM 自己在小范围内“边想边做”。它不需要一次性规划一大串，只需要一步步来。

---

### 4.2 MRKL

> **MRKL: Modular Reasoning, Knowledge and Language**  
> 出处：OpenAI 的示例框架 MRKL System

#### 2.1 核心思路

- **动机**：  
  把 LLM 当做“控制中枢”，然后配置好一组专门的“专家模块”或者“工具”（如“天气 API”、“计算器”、“数据库检索”等），让 LLM 通过一个“路由器（Router）”的思维过程，决定该调用哪个工具。

- **LLM 如何工作**：  
  MRKL 提供一个 **Prompt 模板**，其中包括：

  1. **工具列表**：每个工具的功能描述。
  2. **主要指令**：告诉 LLM“你可以思考后调用工具，拿到结果后继续思考”。
  3. **对话或任务上下文**：让 LLM 结合上下文做决策。

- **整体结构**：
  1. 用户请求 ->
  2. LLM 做推理（“我要用哪个工具处理这个问题”）->
  3. 调用对应的 “Tool” ->
  4. Tool 返回结果 ->
  5. LLM 再次推理 + 得出最终答案。

#### 2.2 规划机制

- **高度依赖 Prompt 配置**  
  MRKL 最终还是通过 prompt（加一些外部程序逻辑）来告诉 LLM “可以做哪些动作、如何调用工具”。

- **“规划”是选择哪个工具**  
  在 MRKL 里，所谓的 “Planning” 更多是：“思考这一步我该用哪一个（或哪几个）工具？”  
  LLM 每一步都基于上一步结果（从工具返回的消息）再思考是否需要再次调用另一个工具，直到得出最终结果。

- **对 LLM 的限制**
  - 同样需要严格的提示词控制，让 LLM 输出形如 “I should use tool X with input Y”。
  - 由外部 Python 程序来解析这个指令并执行对应函数（或 API 调用），然后再把结果回注到 LLM 进行下一步推理。

### 4.3 BabyAGI

> **BabyAGI**：GitHub 上曾一度爆火的“自动化 Agent”原型，基于 LangChain + OpenAI 组合实现，核心是能根据一个主目标，不断地产生和管理子任务。

#### 3.1 核心思路

- **高层“任务管理”循环**  
  BabyAGI 使用一个所谓的 “Task List” 来管理所有待办任务。它有三个主要组件：

  1. **Task Creation Agent**：根据当前任务、执行结果，不断新建子任务。
  2. **Task Prioritization Agent**：对现有任务重新排序，决定执行顺序。
  3. **Execution Agent**：真正去执行当前的任务（通常是调用 LLM/工具等）。

- **每一轮循环做什么**
  1. 从 “Task List” 中取出最高优先级的任务。
  2. 调用 **Execution Agent** 去执行。
  3. 把执行结果（Result）交给 **Task Creation Agent**，是否需要生成新的子任务？
  4. 把更新后的任务列表交给 **Task Prioritization Agent**，排序并循环。

#### 3.2 规划机制

- **“规划”体现在哪？**
  - 其实 BabyAGI 的 “Task Creation Agent” 就是一个“任务规划器”，它通过 GPT 来不断提出新的子任务。
  - “Task Prioritization Agent” 再根据大目标来对这些子任务排序，基本等于在做简单的调度和优先级规划。

- **流程依赖**
  - 依赖外部 Python 代码来把这三个 Agent 串联起来。
  - 每个 Agent 本身只是一个在 Prompt 里说明职责（我是谁、我该干啥、输入是什么、输出格式是什么）然后让 GPT 生成文本。
  - 这些文本再被外部程序解析成“任务列表”等结构。

BabyAGI 的优点是它提供了一个比较清晰的**宏观任务管理循环**，让 LLM 有了一个持续迭代的容器，能把“创建任务—执行—再创建任务”这件事一直循环下去，看上去像是自动化地 self-learning/self-improvement，但实际上大部分逻辑还是写在外部。

---

### 4.4 AutoGPT

> **AutoGPT**：最近 GitHub 的一个实验性项目，它想做一个“完全自动化的 GPT”——给它一个目标，它就能不断自我迭代执行、联网搜索、读写文件等等。

#### 4.1 核心思路

- **类似 BabyAGI，但是更复杂**  
  AutoGPT 也有一个任务/目标管理系统，也能生成子任务并执行。它侧重更丰富的“工具”支持，如联网、读取/写入文件、执行代码等。

- **核心模块**
  1. **AI Config**：存放 AI 的角色、名称、目标等基础信息。
  2. **Memory**：把过去的重要信息存下来，供下一步参考。
  3. **Planner（或类似角色）**：生成下一步要干啥。
  4. **Command Executor**：解析 LLM 返回的命令，然后在外部执行相应操作。

#### 4.2 规划机制

- **还是离不开人写的控制循环**  
  AutoGPT 的 Python 代码中有个主循环：

  1. 让 LLM 生成对下一个 “Action/Command” 的描述（比如 `"search: 'How to fix bug X'"`）。
  2. 程序解析这段描述，确定要执行什么命令、参数是什么。
  3. 调用命令后拿到结果写回 Memory，并再次喂给 LLM，问它下一步怎么做。
  4. 不断重复，直到达到目标或设置的退出条件。

- **LLM 在这中间做什么？**
  - LLM 做的就是“在给定上下文里，输出下一步最合适的 Action 和 Reasoning”。
  - 它实际上在 “Planning + Reasoning” + “工具调用命令”。
  - 但这个 “Planning” 并不是 LLM 本身的自主行为，而是**外部提示 + 循环结构**强行让它做出一系列“工具调用决策”。

---

### 4.5 总结对比

| 框架/方法 | 规划在哪体现 | 规划谁来决定 | 是否完全自动 |
|---|---|---|---|
| ReAct | 每一步的 Thought -> Action -> Observation | LLM 自发思考下一步，但在 prompt 模板中被约束 | 需要外部解析 Action |
| MRKL | 选择适配的 Tool 并多次调用 | LLM 决定调用哪个工具 | 需要外部程序维护工具 |
| BabyAGI | 任务拆分、创建子任务、排序 | LLM 作为任务生成器 + 排序器 | 需要外部 Python 循环 |
| AutoGPT | 自主给出下一个 Command / Action | LLM 通过 Reasoning 产生命令 | 需要外部主循环解析命令 |

> 可以看到，这些系统里的“规划逻辑”大部分都是由 **“Prompt + 外部程序结构”** 来确保 LLM 产生一个个分步骤的决策，并不像一个真正的通用 AI 在大脑里自行做完一切。

---

## 最后几点总结

### 1. LLM 目前的规划能力

- 在没有任何外部结构的情况下，纯靠让 LLM 自发生成“完整的多步计划”，往往会出错或者停得太早。
- 因此大家都想了各种办法，把 LLM 的推理过程分步骤、交互式地“想一点、做一点”，让它看着环境反馈再继续想，从而更加稳健。

### 2. 为什么需要 Prompt 里写死规划流程？

- 因为 LLM 本质上是一个“语言生成”模型，需要你告诉它**预期输出格式**和**使用工具的方法**。不然它不懂该如何有条理地拆分任务、调用工具。
- **这些框架（ReAct / MRKL / BabyAGI / AutoGPT）都是人为设计一种提示模板 & 代码循环，把 LLM 的推理一步步“卡”住，然后反复调用并记录。**

### 3. 未来

- 随着更多的研究，一些项目开始尝试让 LLM 自己去生成 Prompt / 工具描述，甚至能主动改写 Prompt。但是依然需要一个“元框架”或“元代理”告诉它“你现在可以改写 Prompt”。
- 真正的“自我规划 + 自我执行 + 自我纠错 + 自我扩张”也许还需要更深层的 RL（强化学习）或 Agents in Agents 的复杂体系。

简单来说：

“规划机制”在当前最火的 Agent 框架里，几乎都是通过 **Prompt + 一些手写逻辑** 实现的，LLM 在这些框架里扮演“执行规划”或“辅助生成规划”的角色，但很少有框架能让 LLM 完全靠自己从 0 到 1 做所有大规模规划。
