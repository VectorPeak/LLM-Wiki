# 【RAG实战-13】系统评估测试集构建指南

## 1. 构建测试数据集的整体流程和方法

构建高质量的 RAG 评估数据集需要精心的规划和多步骤的流程。建议按照以下步骤进行：

1. **确定评估范围和领域：**首先明确需要覆盖的领域和知识库，例如医疗、法律、教育、企业知识库等。收集这些领域具有代表性的文档或知识源，并确保内容经过授权可用于评估。整个知识库将作为 RAG 系统检索模块的语料库。针对每个领域，可以分别建立子数据集，以便评估系统在不同领域下的表现。

2. **设计评估问题集：**为知识库中的内容设计一系列问题。问题可以来源于多种途径：

   - **人工编写问题：**由领域专家或熟悉文档的人员基于文档内容提出问题。这能保证问题真实、有挑战性，并贴近实际用户关心的问题。人工构建的问题质量通常更高，但成本也较高。
   - **自动生成问题：**利用大型语言模型（LLM）从文档中自动生成问答对。例如，让 LLM 阅读一段文本并生成相关的问题及答案。这种方法可以快速产生大量问题，但需注意验证这些自动生成问题的质量与相关性。自动生成的问题往往比较直白（类似阅读理解题），应尽量调整提示词或人工筛选，以提高问题的多样性和真实感。

> 😎 实践中，可以结合两种方法：先由 LLM 生成初始问题集，然后由人审阅、筛选和修改，去除不相关或重复的问题，确保问题覆盖知识点全面且表述自然。

3. **选择和标注文档片段：**针对每个问题，确定其**参考答案**以及支持该答案的证据文档片段。也就是说，要为每个问题找到 **ground truth 答案和 ground truth 证据**：

   - **参考答案：**通常由人工撰写或确认，即根据知识库内容给出的准确答案文本。对于开放问答任务，可提供简明的准确答案；如果是解释型问题，也可给出较详细的答案要点。必要时可允许多个参考答案或答案要点，以涵盖同一问题的不同正确表达。
   - **支持证据：**标注出能够支持参考答案的文档位置（如**文档 ID 和 chunk 段落或页码**）。这相当于记录“**正确答案来自哪些文档/段落**”。这样不仅用于检索阶段评估（判断检索器是否找到了这些内容），也用于生成阶段的事实一致性评估。对于较长文档，通常需先将文档拆分成合理的**内容块**（chunk）便于检索。标注时可以直接引用包含答案信息的句子或段落作为证据片段。如果问题需要跨多个文档或多个段落才能回答（如多跳问题），则需要标注多个相关片段作为参考证据。

4. **覆盖多样性和难度：**确保问题集具有多样性，包括不同类型和难度：

   - **不同难度：**既包含简单事实提取类问题，也包含需要综合多条证据的复杂问题（例如 HotpotQA 风格的多跳问题）。
   - **不同问句类型：**包括是非题、事实型问题、原因解释型问题、流程步骤型问题等。这可以避免评测集中于单一类型的问题，考察系统在各种问答形式下的表现。
   - **避免问题重复和答案泄漏：**问题之间应互不重复，且不要直接用文档原句提问（LLM 可能记忆原句并直接回答）。对于自动生成的问题，要移除明显雷同或只改写表述但答案点相同的问题，以降低数据集冗余度。

5. **质量审查：**在数据集完成初稿后，进行质量检查：

   - **人工校验：**抽样检查一定比例的问题，确认其参考答案确实可由标注的证据推出且正确无误。如果发现错误或模棱两可的地方，需要修改问题或答案。
   - **覆盖率检查：**确保每个重要知识点或内容都有相应的问题，避免数据集偏斜。例如，可对照知识库目录或主题清单，检查是否每个主题都有问题覆盖。
   - **平衡性：**对于多领域数据集，检查各领域的问题数量和难度是否均衡，不让某一领域的问题主导评测结果。

经过上述流程，即可构建出涵盖检索与生成环节、高质量且多样化的评估测试数据集。

6. **标注方式与评价标准**

为了全面评估 RAG 系统的性能，需要分别针对**检索阶段**和**生成阶段**定义标注策略和评价指标，同时关注结果的可解释性（支持证据）。下面分别介绍这两部分的评价标准：

## 2. 检索阶段的标注与评估

在检索阶段，系统根据用户 query 从知识库提取相关文档片段。评估检索质量需要比较系统检索结果与人工标注的**参考证据**，主要考察以下方面：

- **相关性（Relevance）：**检索结果与用户 query 的相关程度。评价方法是检查系统返回的前 K 个文档/段落中有多少是与问题直接相关的。例如，人工标注哪些文档是相关，则可以计算 **Precision@K**（前 K 个结果中相关项比例）。相关性高意味着检索器将真正相关的内容排在了靠前位置。也可通过 LLM 对每个检索结果判定相关/不相关，然后计算相关比例。通常我们希望 **Precision@5 或 @10** 较高，表明结果集中在相关文档上。

- **覆盖率（Coverage）：**检索结果覆盖答案所需信息的程度，即检索是否找齐了回答问题所需要的所有证据。这可用 **Recall@K** 来度量：在人工标注的所有相关文档中，前 K 个检索结果找到了多少（比例）。如果一个问题的答案需要多条证据，理想情况下检索器应当将这些证据都包含在结果中。**Context Sufficiency（上下文充分性）**也是类似概念：衡量检索到的内容是否已经“足够”回答问题。高覆盖率表示检索没有遗漏关键证据，但如果覆盖率低，哪怕生成模型再强也可能因缺少信息而无法正确回答。

- **冗余率（Redundancy）：**指检索结果中信息冗余或重复的程度。冗余率高表现为检索的多个段落其实包含相似或相同的信息，没有提供新的知识点，这会浪费提示窗口空间并可能影响生成质量。可以通过检查去重后独特信息的条数或者计算结果集合的内容多样性来衡量。例如，使用文本相似度检测结果中重复的片段占比。理想的检索结果应避免过多重复，而是提供互补的证据片段。

- **排序质量：**虽然不在用户问题中明确提及，但对于检索系统常用排序指标也可考虑，如 **MRR（平均倒数排名）** 和 **MAP（平均准确率）**。MRR 关注第一个相关文档出现的位置，MAP 综合考虑多个相关文档的排序。高 MRR/MAP 表示检索器不仅找到了相关文档，而且排序合理，将最有用的证据排在了前面。

**标注方法：**为实现上述评估，需要在构建数据集时对每个问题**标注相关文档列表**。这通常通过人工阅读文档确定答案出处完成。评估时，将系统返回的文档集合与标注的相关文档集合进行对比，计算 Precision、Recall 等指标。对于冗余，可在人工标注阶段记录每条证据所含关键信息点，以便检查系统是否检索了过多包含相同信息的片段。

## 3. 生成阶段的标注与评估

在生成阶段，LLM 根据检索到的上下文生成最终答案。评估生成结果需要参考**人工标准答案**并考虑答案与证据的一致性。主要评价维度包括：

- **回答准确性/正确性（Correctness/Accuracy）：**模型生成的答案内容在事实和语义上是否正确地回答了问题。这通常通过将生成答案与人工参考答案对比来评估。如果参考答案是简短的精确答案，可以使用**准确率（Accuracy）或精确匹配（EM、F1 等指标）**（例如在问答基准 SQuAD、NQ 中常用）。然而，对于语言生成的开放式回答，模型的措辞可能与参考答案不同但意思相同，此时简单的词匹配指标可能不足。因此，可以结合人工或 LLM 判定答案是否涵盖了参考答案中的关键信息点。在实践中：

> 😎
> - **人工评价：**由评估人员根据参考答案和证据判定模型回答是否正确、完整。
> - **自动评价：**如利用词嵌入相似度或 BERTScore，或让另一 LLM 作为裁判比较模型答案和参考答案并打分。

- 如果答案存在遗漏关键点或包含错误信息，则准确性评分应降低。准确性评价重点是回答是否**对问题**：既要回答对问题本身（不偏题），又要内容事实正确。

- **事实一致性（Factual Consistency / Faithfulness）：**生成的回答与检索到的来源证据是否一致，有无不符合证据的“幻觉”内容。即回答中的每一项事实陈述是否能在检索文档中找到依据。这一点对于 RAG 系统尤为重要，因为引入检索模块的目的正是降低语言模型胡编乱造的概率。评价方法包括：

  - **证据支撑验证：**将答案划分为若干事实陈述，检查每一条是否能在检索的支持证据中找到依据。人工可以逐句比对，也可以借助 LLM 或 NLI 模型进行判定。
  - **幻觉率：**衡量答案中有多少内容是检索证据中不存在的。如果答案包含了检索资料里没有的事实，那就是“幻觉”。幻觉率可以量化为未对齐内容占比。理想情况下，**答案应完全以检索到的资料为依据**，不添加编造的细节。

- 为了评估一致性，数据集标注时可记录答案对应的证据出处（哪几段支撑了答案每部分）。评测时，看模型答案中的句子是否能在这些出处找到匹配。在没有人工标注支持的情况下，也可使用 **RAGAS** 等自动方法，让 LLM 给答案的“忠实度”打分。

- **语言流畅性和风格（Fluency & Coherence）：**模型回答在语言表达上是否通顺、自然、易于理解。包括句法是否正确、措辞是否得体、逻辑是否连贯等。这通常需要人工主观评分（例如给出 1-5 分）或者使用一定的自动指标（如 GPT-4 等模型对回答流畅性的打分）。一般来说，一个高质量的回答不仅内容正确，还应当**表述清晰流畅**、符合提问语气。如果评估重点在内容而非文风，此项可作为次要指标，但在对比不同模型时流畅性仍是重要参考。

- **回答相关性（Answer Relevance）：**这与准确性相近但侧重于回答是否针对了用户提问，避免答非所问。模型可能给出部分正确的事实但未真正回答问题。评价时需要判定回答是否**真正解决了用户的问题**。这个维度有时与“准确性”合并考虑，但也可以单独打分。例如，一个回答内容虽然事实正确但偏离了提问重点，也应视为相关性差。

**标注方法：**在生成阶段，为每个问题准备**参考答案**（可以是精确答案或详细解释，视任务而定）。参考答案作为标准用来比对模型输出，从而评估准确性和相关性。同时，结合之前标注的证据，可以评估模型回答是否基于证据、无事实错误。标注人员在构建数据集时尽量提供高质量参考答案并尽可能罗列关键要点，以方便日后比较。对于开放性较强的问题（例如主观问答），也可允许多个参考答案或给答案评分而非简单对错判断。

## 4. 支持证据质量与可解释性评估

RAG 系统的一大优势在于能为回答提供出处依据，增强可解释性。因此评估还应考察**支持证据的质量**以及系统提供解释的能力：

- **证据关联性：**生成的答案是否正确引用了检索到的证据，或者说引用的**证据是否真的支持该答案**。如果系统会在回答中附上引文或出处链接（常见于带引用的 RAG 应用），需要检查引用的准确性。例如，评估系统给出的引用文献是否包含了回答所述的事实。如果出现引用不相关文档或张冠李戴，说明证据质量重要评分下降。这个可以通过人工核对答案句子和所引文档是否吻合进行评价。

- **证据充分性：**和检索覆盖率相关，但从生成角度看，即**答案是否利用了足够的证据来支持自己的结论**。例如一个复杂问题需要两段证据拼合才能回答，如果模型仅依据一段证据就给出片面的回答，那么在支持证据充分性上是不理想的。理想的答案应综合了检索到的所有相关信息点。评价时，可检查模型是否遗漏引用某些关键证据（可对比人工标注的参考证据清单）。这一点也可以量化为**支持率**（标注证据中的信息点有多少被体现在答案中）。

- **可解释性：**指系统是否提供了让用户信赖答案的依据。例如有的 RAG 系统会先列出相关段落或给出推理过程，再给答案。这方面的评估较为质性，可通过人工打分：看系统回答是否清晰地引用/提及了来源，逻辑链条是否易于人类理解。如果有显式的中间推理步骤输出，也需要验证这些步骤的正确性。对于需要严格解释的应用（如法律、医疗场景下要求给出依据），这一指标尤为重要。

需要注意的是，支持证据的评估很多已经反映在前述检索和生成评价中（如“事实一致性/忠实度”就是衡量证据支撑）。但是这里强调的是**从用户信任度角度**对系统解释能力的评价。例如 **HotpotQA** 等数据集要求系统给出**支持事实**，评测标准之一就是准确找出了支撑答案的句子。同样，如果评估要求系统输出引用文献列表，也可以计算**证据命中率**（输出的文献中有多少和人工标注证据吻合）。

> 😎 综上，评估时既要看**模型答案本身**（准确、流畅），也要看**答案与证据的关系**（一致、有依据），从多个维度定义清晰的标准打分或计算指标。例如，一些常用的综合指标框架将 RAG 评估归纳为五个方面：**检索上下文的相关性和充分性，答案的相关性和正确性，以及答案是否有幻觉**。这样的维度划分确保我们全面考察 RAG 系统的质量。

## 5. 现有可复用的数据集或基准资源

在构建评估数据集时，充分利用现有公开数据集和基准能够事半功倍。这些资源提供了大量经过验证的问题、答案以及证据，对评估 RAG 系统很有帮助。以下是一些值得参考的公开数据集/基准：

- **KILT 基准：**KILT（Knowledge Intensive Language Tasks）是由 Facebook AI 提出的一个综合基准，涵盖了 **11 个数据集、5 种任务**的知识密集型 NLP 任务。所有任务都基于同一个维基百科快照作为知识库。KILT 统一了输入、输出以及证据格式，每个问题都附有需要检索的**出处文本片段**。KILT 包含的任务中，与 RAG 评估密切相关的有：

  - **Natural Questions（NQ）：**谷歌提出的开放域问答数据集，问题源自真实用户搜索，答案是维基百科短文段。适合评估单跳开放问答的检索和回答准确率。
  - **HotpotQA：**包含复杂问答，需要**跨段落甚至跨文档**才能回答的问题，并提供了**支持事实标注**。适合评估多跳检索能力和答案推理正确性。
  - **TriviaQA：**收集自 Trivia 问答比赛的问题对，问题往往是冷门知识，需从维基等找到答案。可以测试系统对长尾知识的检索与回答能力。
  - **FEVER：**事实验证数据集。给定一个陈述句，系统需检索维基证据并判断该陈述真/假。虽然不是传统问答，但评估点在于检索到正确证据并基于证据做出正确判断，能够测试 RAG 系统的证据检索和事实校验能力。
  - 此外 KILT 还包含 **ELI5**（解释型开放问答，需要长篇综合回答）、**Wizard of Wikipedia**（知识对话）等。KILT 为这些数据集提供了统一格式，可以方便地用于 RAG 评估模型的训练和测试。

- **Natural Questions（NQ）：**如果不使用 KILT 统一版本，也可直接使用 NQ 原始数据集。NQ 提供了真实用户问句以及对应的维基百科答案和出处。特别地，NQ 有明确短文的**长答案**（段落）和**短答案**（名称实体）形式，可分别评估生成段落级回答和精确答案提取的能力。NQ 是开放域问答评测的经典数据集，许多检索式 QA 模型都在此 benchmark 上报告性能。

- **HotpotQA：**HotpotQA 原始数据提供了**支持文段列表**作为 ground truth，这非常适合评估检索阶段的**召回率**（系统是否找全了这两个文段）和生成阶段的**多文档综合能力**。HotpotQA 还有**判别式问题（比较类）和桥接式问题（需要跨越中间实体）**两类，能测试系统在不同类型复杂问题上的表现。由于 HotpotQA 需要同时给出答案和支持证据，它也是评估**可解释性**的良好基准。

- **TriviaQA：**问题多为冷门 trivia 知识，通常需要利用维基百科等开放知识库查找答案。该数据集可以补充 NQ，因为 TriviaQA 的问题往往更长、答案也更多样。TriviaQA 提供了 Wikipedia 和 Web 两种检索环境下的标注答案，可根据需要选用。它可用于测试系统在长文档中定位答案的能力，以及回答复杂问法（有些问题本身很长）的表现。

- **BioASQ（生物医学问答）：**这是一个面向医学/生物领域的问答基准。BioASQ 任务 B 提供了大量生物医学问题，以及**人工撰写的标准答案和相关文献片段**（通常来自 PubMed）。如果评估医疗领域的 RAG 系统，BioASQ 是很宝贵的数据资源。它包含事实型问答和列表型问答等，要求系统检索医学论文并给出准确答案，非常贴近医疗问答场景。

- **法律问答数据集：**法律领域的 QA 有其特殊性，也有一些公开数据可借鉴。例如 COLIEE 系列竞赛提供了法律案例检索和问答数据，要求从法律判例库中检索相关案例并回答问题。有研究对 **14 个法律 QA 数据集**进行了综述，涵盖了法规问答、判例问答等多种类型。如果评估法律领域 RAG，可参考这些公开数据集（如表示法律条文问答的 “BillQA”、司法判决问答的数据等），或者使用这些竞赛的测试题来验证系统性能。

- **企业文档问答：**企业内部知识库通常没有公开数据集，但可以仿照公开数据集的构造方式来自行创建。例如，将公司内部常见问题 FAQ 或产品文档拿来，人为设计问答。提到一个案例：用人力资源政策手册作为知识源，生成关于其中政策的问答作为评估数据。在没有公开数据可用时，这种方法可以定制贴合企业场景的评估集。不过在报告中通常无法提供这些私有数据，更多是用于内部模型测试。

**基准推荐：**如果希望有统一的 Benchmark 评价，可以直接使用像 KILT 这样的基准来测试模型性能。KILT 已经定义了**评估指标（如 Precision、Recall 和一个综合支持证据的指标）**并有公开排行榜。使用现有基准的好处是**可对比**：可以将自家 RAG 系统与文献中的模型在相同数据上的表现做比较。而对于企业内部知识库，可能需要构造自定义的数据集，但也可以借鉴例如 NQ 等的问答风格，使评测具有代表性。总之，灵活运用公开数据集能加快评估数据集的构建，并保证测试覆盖多种典型知识检索与问答挑战。

## 6. 推荐的评估工具、开源框架或平台

评估 RAG 系统性能不仅需要好的数据集和指标，也可以借助一些**自动化工具和框架**高效地执行评估。以下是几种常用的开源工具和平台，可用于 RAG 评估：

- **RAGAS（Retrieval Augmented Generation Assessment）：**这是一个专门为 RAG 系统开发的开源评估库。RAGAS 提供了一套自动化指标来评估检索和生成的不同维度质量，而**不需要人工提供 ground truth 答案**。它包括了诸如**上下文相关性**（Context Relevance）、**回答相关性**（Answer Relevance）、**忠实度/幻觉**（Faithfulness/Hallucination）等指标的实现，通过调用 LLM 对系统的输入、检索结果、输出进行分析打分。RAGAS 可以方便地集成到现有流水线中，并兼容常用的 RAG 框架（LangChain、LlamaIndex、Haystack 等）。使用 RAGAS，开发者能够快速对自己的 RAG 管道做出诊断，比如看看检索相关性分数多少、答案是否偏离证据等，而不必每次都人工标注检查。它甚至支持**生成合成测试数据**，帮助发现模型弱点。需要注意的是，RAGAS 本质上还是基于 LLM 判断，因此在非常长上下文时偶尔也可能出错。总体而言，RAGAS 是目前评价 RAG 系统的强大工具，其论文和社区也在不断完善指标体系。

- **LangChain Evaluation（LangSmith）：**LangChain 框架内置了评估模块，可用于评测 QA 链或 RAG 链的输出质量。LangChain 的 **QA 评估器**（QAEvaluator）能比较模型输出和参考答案，判断回答是否正确。典型做法是使用 **LLM-as-a-judge**（让一个 LLM 充当评审）来给模型答案打分或做对错判断。LangChain 的评估工具支持**有参考答案和无参考答案**两种模式。例如，有参考答案时，可以提示 GPT-4 根据参考答案和提问来打分模型回答的正确性、完整性；无参考时也可根据上下文一致性来评价。LangChain 团队的 LangSmith 平台提供了 UI 和 SDK，可以方便地运行批量评估、分析错误案例。使用 LangChain 评估的好处是与构建链路无缝集成：开发者可以一边开发 RAG 链一边用 LangChain 的 Evaluator 监控回答质量。当想快速迭代提示词或检索参数时，这种内置评估能及时反馈改进是否有效。

- **OpenAI Evals：**OpenAI 开源了一个评测框架 “Evals”，方便用户设计自定义的评测逻辑并对接 GPT 模型执行。虽然不是专门为 RAG 设计，但可以借助 Evals 来评估 RAG 系统：例如编写一个 Eval，令其对于每个问题将 RAG 系统的回答与参考答案比较，或者让 GPT 判断是否有错误。OpenAI Evals 适合批量自动化地跑通过写好的测试用例，并生成汇总结果，且支持一些模板。例如，可以写一个分类 Eval，让 GPT 判断回答是否正确/部分正确/错误。由于其高度可定制，如果熟悉 Python，也可以用 Evals 来包裹 RAG 系统调用，从而对接自己的测试数据集进行系统化评测。这个工具的优点在于**可重复**：同一套 Eval 可以跑在不同模型上对比结果。不过 Evals 需要一定的脚本开发，对不习惯编程的人门槛稍高。

- **TruLens：**TruLens 是一个开源工具包，用于 LLM 应用的质量评估和追踪。它提供了所谓**反馈函数**（Feedback Functions）的机制，可以针对 RAG 应用定制评价函数。例如，可以设定一个反馈函数检查回答中是否包含提供的证据来源，或计算回答和源文本 embedding 的相似度等等。TruLens 可以嵌入到应用代码中，在每次模型调用后收集这些反馈指标。它还提供 Dashboard 用于可视化分析模型性能。对于需要持续监控 RAG 系统在真实用户请求上的表现，TruLens 非常有用，因为它不仅评估静态测试集，也能评估上线后的交互数据。此外，TruLens 支持集成 LangChain 等框架，在实际应用中插入评估钩子而不干扰应用逻辑。

- **DeepEval：**DeepEval 是另一个新的开源 LLM 评测框架，被称为“像 Pytest 一样评测 LLM”。它可以编写测试用例来验证模型输出满足某些断言条件。对于 RAG，可以用 DeepEval 编写测试，例如“当问到某知识点时，模型回答应包含某关键词”或者“模型引用的来源应包含特定短语”。DeepEval 还提供一些内置的评价方法（比如 GPT-4 打分等）。LlamaIndex 等也支持用 DeepEval 来做 RAG/LLM 评测。如果团队已有单元测试习惯，可以把评估数据集的问题转化为一系列测试函数，用 DeepEval 自动验证模型输出是否通过测试，从而实现类似单元测试的评估流程。

- **其他工具和平台：**业界还有一些提供 RAG 评估的商用平台，例如 Patronus AI（提供托管的评估服务，内置上述各种指标和 LLM 评估器）、Galileo AI、LlamaIndex Evaluation 模块等。在选择工具时，可以根据需求决定：

  - 如果希望**完全自动化无参考评估**，RAGAS 是专门方案。
  - 如果已有**参考答案**，倾向于 **LLM 比对**，LangChain Eval / DeepEval / OpenAI Evals 都可行。
  - 如果需要**长期监控和分析**，TruLens 或 LangSmith 这类带仪表板的工具更方便。

> 😎 **小结：**利用这些评估工具，研发者可以快速对 RAG 系统的检索和生成效果进行定量分析和比较。例如，使用 RAGAS 计算上下文 **precision/recall**、答案正确率和幻觉率，或者用 LangChain 让 GPT-4 逐题打分正确性，从而得到每个模型版本的综合得分。这些框架降低了评估的门槛，使得在没有大规模人工标注的情况下也能获取有意义的度量。当然，最终仍建议结合**人工评价**来校准自动指标，确保评估结果可靠。通过数据集、指标和工具三管齐下，可以全面评估 RAG 系统在各领域的性能，为后续改进提供指导。
