## 0x01.简历简介
### **规程宝 - 矿山规程智能RAG问答平台｜核心开发**

`Hybrid-RAG` `Milvus` `MySQL` `FastAPI` `LangChain` `Langfuse` `Langfuse` `BGE-M3` `BGE-reranker-Large` `Qwen/Qwen2.5-14B-Instruct`

**背景：** 某能源企业在安全生产、井下作业、设备运维、隐患排查和培训考试中积累了大量规程制度、SOP、应急预案、事故案例和培训题库。资料多分散在 PDF、Excel、扫描件和历史台账中，现场查询依赖人工翻阅，存在检索效率低、版本不一致、条款定位不准和复训闭环弱等问题。

**过程：**
- **资料入库链路：** 搭建 PDF / Word / Markdown / Excel / CSV 等多格式入库流程，支持规程条款、巡检表、隐患台账、培训题库和事故案例的清洗、Metadata 标注、分块、Embedding、版本标记与向量写入；对扫描件和图文资料预留 OCR / Vision LLM 处理能力，提升井下图纸、流程图、设备截图等资料的可检索性
- **RAG检索链路：** 基于 Milvus 构建 Dense Vector + BM25 Hybrid Search，结合 BGE-M3 进行语义召回，并使用 BGE-reranker-Large 进行二次精排；完整 RAG Pipeline 覆盖意图识别、查询改写、检索计划、FAQ / 文档双通道召回、上下文构建、Prompt Profile 选择和 LLM 流式生成

- **问答增强链路：** 将常见培训问答、岗位操作要点、标准处置流程和固定制度解释沉淀为 FAQ 知识，高置信问题直接返回标准答案；结合历史消息进行 Query Rewrite，补全追问类问题上下文，并通过 Query Variants 扩展等价表达，提升规程条款、隐患关键词和处置流程的命中率；增加 citation 校验与证据阈值控制，答案关联原文页码，证据不足时触发拒答，降低无依据生成风险。
- **测评与回归：** 支持知识库多版本管理(集成入库质量门禁)、多租户与数据隔离，搭建入库质量、检索效果与性能基线三层回归框架；集成 RAGAS 与 Golden Test Set，覆盖规程问答、隐患排查、设备巡检、应急处置、培训解析等场景，统计 Recall@K、MRR、关键词覆盖率、命中来源、答案忠实度和响应耗时等指标。
- **可观测闭环：** 本地部署 Langfuse 记录 Trace metadata、检索诊断与阶段耗时，将线上 Bad Case 沉淀为 Dataset，并通过 Experiment 对比修复前后效果，形成问题发现、标注、回归与验证的持续优化机制。

**成果：** 完成矿山规程 RAG 平台核心链路，覆盖资料入库、混合检索、重排序、问答生成和引用溯源。接入安全规程、作业规程、SOP、应急预案、事故案例、培训题库等 30+ 份文档 / 3000+ 页资料。检索测试集 Recall@5 达到 91.2%，MRR 达到 86.7%答案引用页码准确率达到 89.6%，支持回查原始规程与处置依据，平台上线后，现场人员查询规程和处置流程的平均耗时下降约 45%

#### 2.1 向量数据库选型问题---为什么不用pgvector而使用milvus?
- 向量数据库选型, 在一般情况下都是 **pgvector/milvus** 二选一
- 针对本项目而言, 使用milvus的原因是因为milvus 2.5以上原生支持BM25 稀疏向量检索...如果使用pgvector来进行稠密向量检索, 则需要搭配ES或者PostgreSQL的tsvector全文检索 进行稀疏向量检索, 会带来多维护一套技术栈的开销, 当然milvus本身就是支持千万级的向量数据库, 可扩展性也比较好, Dify默认也使用milvus....

- 虽然选了 pgvector，但调研阶段其他方案也认真看过。简单说说各自的特点和为什么没选。

**Milvus：** 分布式架构最成熟，亿级向量毫无压力，支持 GPU 加速。但运维复杂度高，依赖 etcd、MinIO、Pulsar 一堆组件。我们集群已经够复杂了，不想再加这一坨。如果你是亿级向量的场景，Milvus 是唯一选择。

当时看过一个分享，某互联网公司在 Milvus 上跑了 10 亿级向量，效果很好。但他们的运维团队有三个人专门维护 Milvus 集群。我们这种小团队根本养不起这个人力。

Milvus 还有一个优势是支持 **GPU 加速索引构建**。数据量特别大的时候，用 GPU 建 HNSW 索引比 CPU 快一个数量级。我们数据量小用不上这个能力。

**Qdrant：** Rust 写的，查询速度确实快。单机性能很强，内存效率高。但分布式能力还在完善中。如果你追求**单机极致性能**，Qdrant 值得试。不过说实话，大多数场景这个速度差异感知不明显。

Qdrant 的**过滤查询做得不错**。如果你需要在向量检索的同时加很多过滤条件（比如按时间、按分类、按标签筛选），Qdrant 的方案比 pgvector 优雅很多。pgvector 虽然也能通过 WHERE 句子做过滤，但**索引利用率不如 Qdrant 高**。

**Weaviate：** 混合搜索做得最好，内置了向量化和重排模块。开箱即用体验很丝滑。但它是 Go 写的，部署需要额外服务。如果混合搜索是你的核心需求，Weaviate 比 pgvector 的方案更优雅。

**Chroma：** 上手最快，pip install 就能跑。适合做原型和实验。但生产环境不建议用，功能太少，社区活跃度也不如前面几个。我们早期做 POC 的时候用过一阵，后来很快就切了。

**Pinecone：** 全托管，零运维。国内用不了，数据合规过不去。不在考虑范围内。如果你的数据能上云并且预算充足，Pinecone 确实省心。

##### 3.1.2 RAGAS的测评是如何做的?
1.先说评估维度:三大核心维度 忠实度,答案相关性,上下文相关性
(要了解三大指标的公式 + RAGAS的三个指标不需要参考答案)

2.方法论:分层测+诊断矩阵 Retriever -> Generater -> 端到端
在评测系统的时候也有个顺序,要确定到底是检索的效果不好,还是生成的效果不好,所以要分层测.准备个黄金数据集(20-50条) 先测Retriever(Precision+Recall+MRR+NDCG), 再测Generater(给完美上下文/召回文本,测Faithfullness+Answer Relevance), 最后再端到端地测一遍(诊断矩阵) + 黄金数据集:20-50条

3.LLM-as-Judge 局限 + 缓解
局限:我读过一篇论文,大模型自己在评分的时候呢,实际上是有点局限的. 比如说位置偏差,冗长偏差,自我/家族偏好
缓解:怎么缓解呢,换模型家族/多裁判, 微调小模型, 人机混合(大部分自动,高风险的交给人工)

4.评测的工具选择
行业默认是RAGAS. 当然也可以用DeepEval,这个支持CI/CD集成,而且指标比较多(可能有上百种?)

5.三层叠加方案
大部分情况下/想做个快速原型验证 直接用RAGAS打分就行了. 如果是追求真正靠谱的方案呢,可以用三层叠加的方案. 第一层用RAGAS/DeepEval做初筛. 第二层积累领域的定制测试集,把真实的失败case不断加进去,这才是团队最宝贵的资产. 第三层就是人工抽检,高风险的系统不可省略

##### 3.1.3 为什么不把RAGAS作为主测评?
本项目的主评测不是 RAGAS，而是面向企业 RAG 主链路的工程回归门禁。原因是企业项目不能只判断答案文本是否“看起来合理”，还必须验证：

- 是否召回到预期来源：`Recall@K`
- 预期来源排名是否靠前：`MRR`
- 答案是否覆盖关键事实：`keyword_coverage`
- FAQ 直出、RAG 生成、边界提示等路径是否正确：`hit_type_accuracy`
- source 自动推断是否正确：`source_inference_accuracy`
- Prompt Profile 路由是否正确：`prompt_profile_accuracy`
- 多场景隔离是否正确：`scenario_isolation_accuracy`
- 是否出现错误和明显超时

RAGAS 是很好的 RAG 语义质量评估工具，但它默认关注的是“问题、答案、上下文、参考答案”之间的语义关系。KnowForge 的主评测目标更偏企业工程回归，很多关键指标不是 RAGAS 默认能直接判断的。

|企业级验收问题|RAGAS 默认是否能直接判断|本项目主评测如何判断|
|---|---|---|
|是否召回到预期业务来源|部分能，需要额外改造样本和上下文标注|`expected_source_contains` + `Recall@K` + `MRR`|
|FAQ 是否应该高置信直出|不能直接判断|`expected_hit_type=faq_direct` + `faq_direct_accuracy`|
|问题是否应该进入 RAG 生成|不能直接判断|`hit_type_accuracy`|
|是否识别到 source 选错边界|不能直接判断|`source_boundary` / `source_inference_accuracy`|
|是否命中正确 Prompt Profile|不能直接判断|`expected_prompt_profile` + `prompt_profile_accuracy`|
|是否遵守多场景隔离|不能直接判断|`scenario_isolation_accuracy`|
|是否只查当前 active `kb_version`|不能直接判断|工程评测报告记录 `kb_version` 和检索诊断|
|是否遵守 DataScope 权限过滤|不能直接判断|评测样本传入 `tenant_id` / `dataset_id` / `visibility` / `user_role`|
|是否出现接口错误或依赖异常|不能作为主指标|`errors` / `error_rate`|
|响应耗时是否可接受|不能作为主指标|`avg_elapsed_ms` / 性能基线门禁|

因此，如果把 RAGAS 直接作为主评测，会出现三个问题：

1. **会漏掉企业级链路指标**：FAQ 直出、source 边界、Prompt Profile、多场景隔离、DataScope、active 版本等都不是 RAGAS 的默认评价对象。
2. **会把工程问题误看成语义问题**：例如召回 source 错了、版本过滤错了、权限过滤错了，RAGAS 可能只看到“答案和上下文是否一致”，但无法指出是哪条工程链路退化。
3. **不适合做唯一 CI 门禁**：RAGAS 依赖 LLM-as-judge，成本更高、速度更慢、结果有一定波动；本项目需要一个稳定、可解释、可失败的工程回归门禁。

所以本项目的定位是：

|   |
|---|
|`主评测：自研工程回归门禁   负责判断主链路有没有退化：   Recall@K / MRR / hit_type / source 推断 / Prompt Profile / 场景隔离 / DataScope / 错误率 / 耗时 补充评测：RAGAS   负责分析答案语义质量：   faithfulness / answer_relevancy / context_relevance / groundedness`|

一句话总结：**RAGAS 适合回答“答案语义质量怎么样”，本项目自研门禁负责回答“企业 RAG 主链路是否稳定正确”。两者互补，不是替代关系。**

RAGAS 适合补充回答语义质量，例如：

- `faithfulness`：答案是否忠实于召回上下文
- `answer_relevancy`：答案是否回应了用户问题
- `context_relevance`：召回上下文是否和问题相关
- `response_groundedness`：答案是否能被上下文支撑

所以本项目采用两层评测：

|层级|工具|作用|是否主门禁|
|---|---|---|---|
|工程回归门禁|`evaluate_core_chain.py` + `check_evaluation_gate.py`|验证召回、路由、场景隔离、Prompt、错误率和耗时|是|
|追问专项门禁|`evaluate_followup_chain.py` + `check_followup_gate.py`|验证多轮追问、改写和历史上下文|是|
|RAGAS 补充分析|`evaluate_ragas_quality.py`|评估忠实度、答案相关性等语义质量|否|

##### 3.2.1 项目的数据隔离与多租户设计是怎么做的?
>在本项目中, 分了 **四个维度** 来实现数据隔离与多租户设计

|维度|问题|例子|
|---|---|---|
|**租户隔离**|A 公司能看到 B 公司的资料吗？|`tenant_id="company_a"` 不应查到 `tenant_id="company_b"` 的数据|
|**数据集隔离**|生产环境和测试环境的数据混查？|`dataset_id="production"` 不应查到 `dataset_id="test"` 的数据|
|**可见性**|实习生能看到高管会议纪要吗？|`visibility="restricted"` 的内容不应被普通员工检索到|
|**角色隔离**|HR 能看到财务数据吗？|HR 角色不应查到 `allowed_roles=["finance_admin"]` 的数据|

##### 3.2.2 数据隔离一般情况下分为几层?
> 一般数据隔离分成了 物理隔离+逻辑隔离+数据错隔离

一、**物理隔离**（强隔离，最高安全等级）原理：硬件层面完全拆分，不同租户 / 业务使用独立服务器、存储、交换机、机房，网络物理不通，无任何共享硬件资源。
特点：1、隔离强度最高，不存在数据越权泄露、跨租户渗透风险；2、成本极高，硬件、运维、机房资源翻倍；3、扩容、资源复用差，适合金融、政务、涉密等高合规场景。

二、**逻辑隔离**（资源共享，中间隔离方案，云平台最常用）原理：共用底层物理硬件（服务器、存储、网络），依靠软件、虚拟化、网络策略做权限、资源、数据边界分割，硬件互通但逻辑上无法互相访问。
细分两类典型实现：1、网络逻辑隔离：VLAN、子网、防火墙 ACL、安全组，阻断跨租户网络访问；2、虚拟化隔离：虚拟机、容器、K8s Namespace，内核层做资源调度隔离。
特点：1、硬件复用，成本适中，弹性扩缩容；2、依赖软件策略，存在配置漏洞、逃逸风险；3、适合公有云、多租户 SaaS、企业多业务中台。

三、**数据层隔离**（应用 / 数据库层面隔离，最轻量）：原理共享数据库实例、中间件服务，仅在数据存储结构上做隔离，分为三种细分手段：1、独立库：每个租户单独数据库；2、独立 Schema：同一库下不同租户分开 Schema；3、租户 ID 行隔离（单表多租户）：一张表加tenant_id字段，查询强制过滤租户数据。
特点：1、改造成本最低，资源利用率最高，运维简单；2、隔离最弱，极易出现 SQL 漏洞、越权查询、数据混读；3、适合中小 SaaS、低敏感业务，搭配权限校验使用。
