## 0x01. 如何理解Nvidia英伟达的Multi-GPU多卡通信框架NCCL？

> 赞同数：7
> 原文链接：[如何理解Nvidia英伟达的Multi-GPU多卡通信框架NCCL？](https://www.zhihu.com/question/63219175/answer/2043582180488640450)

说实话，这个问题下大部分回答在讲NCCL的学术原理，Ring和Tree算法怎么回事。我不讲那个。我们花了一个多月真金白银在4090上NCCL多卡通信踩出来的结论就一句话：**4090单机多卡通信基本线性增长，跨节点就是深渊。** 万兆试过，十万兆也试过，全部推翻回到单机。请原谅我们的贫穷，10万兆卡和线缆一套也要大几千呢好吧。

先把概念掰清楚。NCCL和NVLink是两码事，NVLink是硬件，GPU之间物理连接的高速通道，走电信号，A100的NVLink 3.0双向带宽600GB/s[1]；NCCL是软件，NVIDIA做的一套通信库，负责管理GPU之间怎么传数据，可以用NVLink传，也可以用PCIe传，也可以用网线传（InfiniBand或TCP/IP）[2]。

4090没有NVLink，NVIDIA在30系以后砍掉了消费级GPU的NVLink支持[3]，所以NCCL在4090上走的是PCIe 4.0 x16，单向理论带宽32GB/s[4]。能用，但别指望快，差了将近20倍。

NCCL支持的通信原语包括AllReduce、Broadcast、Reduce、AllGather、ReduceScatter[2]，大模型推理最常用的是AllReduce，tensor parallel场景下每张卡算完一层要把结果同步给所有卡，vLLM的tensor parallel实现依赖NCCL的AllReduce完成跨卡权重同步[5]。

### ⭐ ▎ **单机多卡：没有NVLink也能跑，基本线性增长**
4090没有NVLink，很多人以为这就废了。不是的。NCCL走PCIe单机内的延迟是纳秒级，通信开销在实际推理里占比不高，**单机多卡的吞吐基本随卡数线性增长。** 体感上区别很明显：TP=1是一小段一小段出来，TP=2是一大段一大段往外蹦，都正常能用。

我们生产环境跑Qwen3.6-35B-A3B-FP8，TP=2两张4090，启动命令：
```
#!/bin/bash
# LLM 节点启动 - Qwen3.6-35B-A3B-FP8 TP=2

docker run -d --name vllm-35b-a3b-tp2 \
    --gpus all --shm-size=32g --network host \
    -e NCCL_P2P_DISABLE=1 \
    -e NCCL_IB_DISABLE=1 \
    -v /opt/powagt/vllm/models:/models \
    --restart unless-stopped \
    vllm/vllm-openai:v0.19.0 \
    /models/Qwen3.6-35B-A3B-FP8 \
    --served-model-name qwen3.6-35b-a3b \
    --tensor-parallel-size 2 \
    --max-model-len 131072 \
    --dtype auto \
    --kv-cache-dtype fp8_e4m3 \
    --gpu-memory-utilization 0.95 \
    --enable-prefix-caching \
    --enable-chunked-prefill \
    --max-num-seqs 16 \
    --max-num-batched-tokens 32768 \
    --host 0.0.0.0 --port 8000 \
    --trust-remote-code \
    --disable-log-stats \
    --reasoning-parser qwen3 \
    --default-chat-template-kwargs '{"enable_thinking": false}' \
    --enable-auto-tool-choice \
    --tool-call-parser hermes
```

`--shm-size=32g`是因为vLLM的NCCL通信依赖共享内存做跨进程同步，Docker默认的64MB根本不够，不设这个多卡直接起不来。`--gpu-memory-utilization 0.95`打得很满，因为FP8量化后显存压力小了不少，可以多留给KV cache。`--enable-prefix-caching`和`--enable-chunked-prefill`是vLLM的优化参数，跟NCCL没有直接关系但能提高整体吞吐。

用nccl-tests测了all-reduce带宽：单次1GB数据，理论PCIe x16双向64GB/s，实测约18GB/s，损失了70%以上。调过几个NCCL参数，`NCCL_BUFFSIZE=1048576`（1MB）稳定在约18.5GB/s，`NCCL_MAX_NCHANNELS=1`限制通道数避免PCIe争抢约15GB/s但更稳定，Tree算法在8×4090 PCIe系统上约17GB/s[9]。说实话调来调去都是杯水车薪，物理层就是PCIe 4.0 x16没有NVLink，软件怎么优化也突破不了32GB/s的天花板。

### ⭐ ▎ **跨节点TP=4实测：能跑，但效率是另一个故事**
这个坑我们踩得最深。先说结论：跨节点tensor parallel在4090上万兆网环境下跑得通，服务稳定，API正常。但到了性能账算起来的时候，数据会告诉你真相。

先说我们的真实部署。两台机器各插2张4090 48GB，一共4张卡，跑Qwen3-235B-A22B-AWQ（AWQ量化），TP=4跨节点。网络走万兆（10GbE），Head节点在node-02，Worker在node-03。

Head节点启动命令：
```
docker run -d --name vllm-ray-head-tp4-awq \
    --gpus all --shm-size=16g --network host \
    -e VLLM_HOST_IP=10.0.0.2 \
    -e GLOO_SOCKET_IFNAME=ens111f1 \
    -e TP_SOCKET_IFNAME=ens111f1 \
    -e NCCL_SOCKET_IFNAME=ens111f1 \
    -e NCCL_P2P_DISABLE=1 \
    -e NCCL_IB_DISABLE=1 \
    -v /opt/powagt/vllm/models:/models \
    --entrypoint bash \
    vllm/vllm-openai:v0.10.0 \
    -c 'ray start --head --port=6379 --node-ip-address=10.0.0.2 --disable-usage-stats && \
    vllm serve /models/Qwen3-235B-A22B-AWQ \
        --served-model-name qwen3-235b-awq \
        --tensor-parallel-size 4 \
        --max-model-len 4096 \
        --quantization awq_marlin \
        --host 0.0.0.0 --port 8000'
```

Worker节点：
```
docker run -d --name vllm-ray-worker-tp4-awq \
    --gpus all --shm-size=16g --network host \
    -e VLLM_HOST_IP=10.0.0.3 \
    -e NCCL_SOCKET_IFNAME=ens111f1 \
    -e NCCL_P2P_DISABLE=1 -e NCCL_IB_DISABLE=1 \
    -v /opt/powagt/vllm/models:/models \
    --entrypoint bash \
    vllm/vllm-openai:v0.10.0 \
    -c 'ray start --address=10.0.0.2:6379 --node-ip-address=10.0.0.3 --disable-usage-stats && sleep infinity'
```

注意几个关键点：`NCCL_SOCKET_IFNAME=ens111f1`指定走万兆网口而不是千兆管理口；`--shm-size=16g`给NCCL共享内存留够空间；用Ray做跨节点编排而不是vLLM原生的multiprocessing。

部署成功了，模型加载约五分钟，服务健康检查正常，API响应正常。

但体感上完全不行。字是一个一个慢慢冒出来的，肉眼可见的卡顿。问个简单问题等十几秒才答完，用户体验跟单机单卡比差太多了。原因不复杂：235B模型94层transformer，每层都要跨万兆网做一次all-reduce同步，94次叠上去，通信时间把计算时间盖住了。

但我们不死心。万兆不行，升级到十万兆（100GbE RoCE）行不行？

买了Mellanox ConnectX-5网卡，三千一块，换上以后延迟从50微秒降到约5微秒，带宽从1.25GB/s提到12.5GB/s[10]。实测结果：性能虽有提升但还是逊于单卡。用户本来期望很大，以为一上集群性能和质量一齐并进呢，这一看立马不满意了。

为什么升级了十倍带宽还是不行？因为tensor parallel的all-reduce频次太高了，94层transformer每层都要跨网络同步一次，94次叠加。十万兆的延迟再低，这94次叠上去也是巨大的开销。而且这还只是跑一个请求，如果同时来几个用户，通信冲突更严重。

搞到最后，结论很清楚了：**跨节点tensor parallel这条路，在消费级硬件上走不通。** 不是网卡不够好，是tensor parallel这个通信模式本身就不适合跨节点。万兆到十万兆的升级证明了这一点，十倍带宽的提升只换来”勉强持平”，这投入产出比没法接受。

推翻了整个方案，回到单机多卡。跨节点只做数据并行，每张卡独立跑模型副本，参数同步频次远低于TP，十万兆网络完全够用。

### 💡 ▎ **数据中心是怎么做的：不是网卡的问题，是整个拓扑设计的问题**
我们踩了坑以后去研究了数据中心的做法，发现差距远不止”他们用了更好的网卡”。

Meta在2025年公开了其60万GPU集群的网络架构：标准化采用NVIDIA Spectrum-X 800G以太网，配合Spectrum-4交换机+BlueField-3 DPU+ConnectX-7 SuperNIC。关键创新是包级自适应路由和包喷洒（packet spraying），数据吞吐量实测达到95%，而同等规模的标准以太网只有约60%[12][13]。

InfiniBand NDR 400G是目前AI训练集群的事实标准，端口间延迟仅0.6微秒，支持SHARP v3网络内计算（In-Network Computing），把AllReduce的部分归约计算直接卸载到交换机硬件上完成，GPU不必等所有数据到齐再做，实测加速比最高可达32倍[14]。

Google的TPU集群走的是完全不同的技术路线：Ironwood架构采用3D Torus拓扑，通过光路交换机（OCS）实现芯片间直连，单芯片带宽9.6Tb/s，一个SuperPod包含9216颗TPU和1.77PB HBM。Google完全不依赖NVIDIA的网络堆栈，从芯片到互联全自研[15]。

成本对比很直观：十万卡级别集群，InfiniBand方案交换机占GPU节点数9.6%，光模块与GPU配比3.6:1；Spectrum-X以太网方案交换机占比3.2%，光模块配比2.6:1，InfiniBand的TCO约为Spectrum-X的2.3倍[16]。所以Meta选了Spectrum-X，不是因为性能更好（InfiniBand平均性能优势约15%），是因为60万张卡乘2.3倍的TCO溢价算不过来账。

我们的万兆网线在它面前，就像**拿根吸管给消防水带送水**。

### ⭐ ▎ **回到现实：4090多卡的正确用法**
总结就两句话。**单机多卡放心用，跨节点别搞。**

4090没有NVLink不是致命伤，PCIe单机内的带宽对大模型推理完全够。我们生产环境TP=2跑35B模型，加速比1.4倍，日常推理没问题。TP=4大约1.6倍，基本线性增长。单机多卡尽量把GPU插同一个PCIe switch下面，`nvidia-smi topo -m`看拓扑，标PIX的通信效率最高。

跨节点tensor parallel我们已经替你们交过学费了，万兆不行，升级到十万兆还是不行，不是网卡的问题，是tensor parallel这种每层都要全网同步的通信模式从根本上不适合跨节点。验证环境可以留着玩，生产环境千万别当真。

建议先收藏，下次多卡部署翻出来对照。

### ⚠️ ▎ **先搞清楚你能跑啥**
搜HuggingFace搜出来一堆DeepSeek模型，很容易懵。说白了很多跟你没关系。

DeepSeek-V3是671B参数，DeepSeek-R1也是671B，DeepSeek-V4-Pro更夸张1.6T。这几个你家里的4090连个零头都跑不了。量化？极限量化1-bit也得130GB往上。多卡集群的活，不是个人能搞的。

**真正能在消费级显卡上跑的是蒸馏系列。** Distill。

原理不复杂：用R1那个671B的大模型生成一堆推理数据，拿这些数据去微调小模型。基座用的是Qwen2.5和Llama3，不是DeepSeek自己的架构。

模型基座参数量AWQ-4bit4090(24G)4090魔改(48G)Distill-Qwen-1.5BQwen2.51.5B~1.5GB✅ 轻松✅ 轻松Distill-Qwen-7BQwen2.57B~5GB✅ 轻松✅ 轻松Distill-Llama-8BLlama-3.18B~6GB✅ 轻松✅ 轻松Distill-Qwen-14BQwen2.514B~9GB✅ 可以✅ 轻松Distill-Qwen-32BQwen2.532B~18GB✅ 刚好✅ 充裕Distill-Llama-70BLlama-3.370B~40GB❌⚠️ 勉强

32B这个性价比最高。AWQ-4bit量化后大概18GB，标准4090（24G）就能跑，还有余量给KV cache。实测下来推理速度也不错，单用户够用，十几二十个并发也能扛住。

我们正在下载的就是这个：`casperhansen/deepseek-r1-distill-qwen-32b-awq`，从hf-mirror下，大小大概18GB。

但有个事得说清楚。**Distill-Qwen-32B的基座是Qwen2.5-32B**，不是DeepSeek自己的模型。它只是吃了R1的推理数据做了微调。所以别觉得你在本地跑的就是”DeepSeek”，准确说是Qwen2.5喝了R1的奶。

另外有个常见误解得提醒一下。有人看到DeepSeek-V4-Flash标着A13B激活就以为能跑在消费级显卡上。想多了。MoE的激活参数只减少计算量，总参数全要加载到显存。量化后也得一百多GB。你那24G的4090跟它没有半毛钱关系。

### ⭐ ▎ **API到底多少钱，算给你看**

## 0x03. 实现 LLM 复杂推理（Reasoning）目前有哪些主要方法？

> 赞同数：19
> 原文链接：[实现 LLM 复杂推理（Reasoning）目前有哪些主要方法？](https://www.zhihu.com/question/12292274612/answer/2043295569230161093)

我们用Qwen3.6-35B-A3B跑的生产环境，**把推理模型的thinking功能关了**。

对，你没看错。一个带推理能力的MoE模型，我们部署的时候第一件事就是把思考过程关掉。听起来很浪费对吧？但这是跑了大量真实用户请求之后做的决定。

先说结论：LLM推理目前有三个流派，prompt工程，推理模型，隐空间推理。各有各的坑，我一个个说。最后讲讲我们为什么关了thinking，以及什么时候该开。

### ⭐ ▎ **三个流派，三个思路**
LLM做推理这事，说白了就是解决一个问题：模型怎么从”快速给答案”变成”想清楚了再给答案”。

第一种思路是最古老的，**用prompt逼模型一步步想**。代表就是CoT（Chain-of-Thought），在prompt里加一句”让我们一步步思考”，模型就会输出推理过程。这个方法2022年就火了，到现在还是很多项目的标配。

第二种是**让模型天生就会推理**。2024年下半年开始，OpenAI o1，DeepSeek-R1，Qwen3这些模型内置了thinking能力。模型不再需要你提醒它”一步步想”，它自己会先在内部做推理，再输出答案。这叫”慢思考模型”，对照卡尼曼的那本《思考：快与慢》。

第三种最前沿，**让模型在隐空间里推理**，不输出任何文字，直接用hidden state做推理。代表是Meta的Coconut（Continuous Chain of Thought），把50个token的思考过程压缩成2个连续向量。听起来很科幻，但目前还在实验室阶段。

**三种方法的本质区别在哪？token消耗和延迟。**

![image](https://pic1.zhimg.com/50/v2-d559f334e8ee3de9457f0d1d4f79a18c_720w.jpg?source=1def8aca)

![image](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1296' height='497'></svg>)

### ⚠️ ▎ **CoT：便宜但不可靠**
CoT是最容易上手的方案。不需要换模型，不需要改部署方式，加一行prompt就行。

我们在RAG项目里用过很长一段时间CoT。效果怎么说呢，**简单的三段式推理还行，复杂一点就崩**。

举个例子，用户问”XX规程第3.2条和第4.1条有什么区别”。模型需要先理解两条规程各自在说什么，找到差异点，再组织语言回答。用CoT，模型会输出”首先我需要理解3.2条的内容…然后理解4.1条…最后对比差异”。听起来很合理对吧？

问题是**模型经常在中间步骤就跑偏了**。它”理解”3.2条的内容时可能就已经理解错了，后面全错。而且CoT有个致命缺陷：模型的推理过程不一定忠实地反映它真正的决策路径。Google有篇论文叫”Language Models Don’t Always Say What They Think”，说的就是这事。**CoT输出的推理过程可能是”编”的**，模型先有了答案，再反推一个看似合理的推理链给你看。

Self-Consistency是CoT的一个改进，让模型生成多个推理链，然后投票选最一致的答案。效果确实好了，但**token消耗直接翻5倍**。Tree-of-Thought更夸张，把推理展开成树形搜索，复杂问题是能解了，但一次请求的token成本能到普通请求的10倍以上。

**说到底，CoT是在一个没有推理能力的模型上”外挂”推理。** 模型本身不会推理，你用prompt教它假装推理。真遇到需要推理的活，这个伪装就很脆弱。

### ⭐ ▎ **推理模型：能力强但代价高**
2024年下半年，OpenAI o1出来以后，”推理模型”这个概念才算真正落地。

推理模型和普通模型的核心区别：**模型在输出答案之前，会先输出一段thinking过程**。这段过程可能是几百token，也可能几千token，取决于问题复杂度。

DeepSeek-R1是开源推理模型的代表作。Qwen3系列也内置了thinking能力，通过 `enable_thinking` 参数控制开关。

我们目前用的是Qwen3.6-35B-A3B，MoE架构，35B参数量但只激活3B。**这个模型自带thinking能力**，部署在vLLM v0.19.0上，双卡4090定制48GB。

![image](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1296' height='638'></svg>)

### ⚠️ ▎ **为什么我们关了thinking**
这是我们最核心的踩坑经历。

部署的时候，vLLM有个启动参数 `--default-chat-template-kwargs '{"enable_thinking": false}'`。我们一行代码就把thinking关了。

**关的原因很现实：thinking过程会打印到用户界面上。**

用户问一个电力规程的问题，结果先看到一大段模型的”内心独白”：”让我分析一下这个问题…首先需要考虑…根据XX规程…“。关键还是英文的！等了好几秒，真正的答案才出来。

用户体验极差。专业客户看着屏幕刷一堆”废话”，第一反应是”这什么东西”。

然后是token成本。**thinking过程本身可能比答案还长**。一个简单的知识问答，答案200 token，thinking可能消耗500 token。推理成本直接翻2到3倍。我们用的是自己搭的GPU集群，电费和硬件折旧都是真金白银。

还有延迟。模型要先”想”完才能输出答案，**用户多等3到5秒**。实时对话里这个延迟不可接受。

**所以我们做了个决定：企业RAG业务，thinking关掉。**

在PowAgt平台里，应用设置里有个”输出思考”开关。关掉以后，模型走普通chat模式，直接给答案。快，准，省。

### 💡 ▎ **什么时候该开thinking**
关了不等于没用。thinking在特定情况下确实强。

**数学计算，逻辑推理，多步骤分析，这三种情况值得开。**

举个例子，用户问”这个变电站的短路电流计算结果和规程限值差多少”。模型需要：理解短路电流计算公式，从文档里找到相关参数，计算结果，对比规程限值，给出差异。这种多步推理，thinking模式下准确率明显高于直接回答。

**但这类问题在我们的用户请求里占比不到20%。** 剩下80%都是”XX条款怎么规定的”“这个流程的第三步是什么”这类知识检索型问题，根本不需要推理。

所以理想方案是做**动态路由**：简单问题关thinking，复杂问题开thinking。OpenAI的API现在支持调节reasoning effort，就是这个思路。

我们的做法更粗暴：**全局关thinking，只有特定应用开。** 需要推理能力的应用（比如故障分析智能体）单独在PowAgt后台打开”输出思考”开关。

### ⭐ ▎ **RL到底能不能提升推理能力？**
这个问题2025年吵得很凶。

2025年NeurIPS有一篇满分论文，清华大学和上交联合做的，标题是”Does RL Really Incentivize Reasoning Capacity in LLMs Beyond the Base Model?“。

结论很炸裂：**RL训练后的推理模型，它的推理能力上限已经被基座模型锁死了。**

什么意思呢？研究者发现，RL训练模型生成的所有正确推理路径，**其实早就存在于基座模型的采样分布里**。RL做的是”提高采样效率”，让模型更容易采到正确的推理路径，而不是让它学会了新的推理方法。

换句话说，**RL是把模型”本来就会但不太稳定的推理能力”稳定化，而不是”教模型学会推理”。**

DeepSeek-Math的实验也证实了这一点。RL提升了Maj@K（多次采样取多数的结果），但没有提升Pass@K（单次采样的上限）。这说明RL让模型输出更稳定，但天花板没动。

那新知识从哪来？论文指出，**蒸馏比RL更有效**。把大模型的推理能力蒸馏到小模型上，效果比直接用RL训练小模型好得多。

**这个发现对我们做生产部署有实际指导意义。** 你不需要一个超大的推理模型来处理所有请求。大部分问题用轻量模型就能搞定，少数复杂问题才需要推理模型。而且推理模型的能力天花板取决于基座模型，不是取决于你用了多少RL技巧。

### ⭐ ▎ **隐空间推理：前沿但还不能用**
Meta的Coconut（Continuous Chain of Thought）代表了一个很有想象力的方向：**让模型在隐空间里推理，不输出任何文字**。

具体做法是，用模型最后一层的hidden state作为”推理token”，替换掉CoT里的文字推理过程。原本需要50个token的思考，变成2个连续向量就搞定了。

听起来很美好对吧？**推理速度快了，token省了，用户也看不到中间过程。**

但实际情况是：**没有做到等效替换。** Coconut在推理路径的探索上确实比离散CoT强，但最终推理质量还达不到文字CoT的水平。而且训练方法复杂，需要特殊的训练管线，目前没有开源的实现可以直接用。

CODI是Coconut的一个变体，做了一些改进，但核心问题没解决。**隐空间推理目前还是学术探索阶段，生产环境别碰。**

### 💡 ▎ **我们的生产环境配置（供参考）**
实际配置长这样，两个层级控制thinking：

vLLM启动参数：
```
--reasoning-parser qwen3
--default-chat-template-kwargs '{"enable_thinking": false}'
```

应用层控制（PowAgt平台）：
```
extra_body = {
    "chat_template_kwargs": {
        "enable_thinking": false
    }
}
```

**服务端全局默认关，应用层按需开。** 这样既保证大部分请求快且省，又保留了需要推理时打开的能力。

硬件环境是双卡4090定制48GB，MoE模型3B激活参数。thinking关了以后，单请求延迟从5到8秒降到1到2秒。**这个体感差异，用户是直接能感知到的。**

### ⚠️ ▎ **三条实操建议**
![image](https://picx.zhimg.com/50/v2-fcf8acfc82c6e8b4774afff52af38a93_720w.jpg?source=1def8aca)

![image](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1296' height='971'></svg>)

第一，**别被”推理模型”四个字唬住。** 大部分企业落地不需要推理能力。知识库问答，文档检索，流程查询，这些用普通模型就够了。推理模型真正的价值在数学计算，逻辑判断，多步分析这些活。

第二，**如果用推理模型，一定要做thinking开关。** 不是所有请求都需要推理。我们实测80%以上的请求是知识检索型，开thinking纯粹浪费token和延迟。做动态路由，或者按应用级别控制，投入产出比高得多。

第三，**CoT仍然是性价比最高的推理方案。** 如果你暂时不想上推理模型，用CoT + Self-Consistency（采样3到5次取多数）就能解决大部分推理问题。效果可能不如推理模型，但成本可控，延迟可控，部署门槛也低。

**推理能力很重要，但不是所有问题都需要推理。选对用法，比选对模型更重要。**
